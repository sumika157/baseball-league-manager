レビューで挙がった指摘を、このプロジェクトの規約（`CLAUDE.md`）に沿って修正する。

## 1. 指摘を集める

- この会話にレビュー結果があればそれを使う。無ければ先に `ddd-boundary-reviewer` エージェント（層境界・不変条件）または `/code-review`（一般的なバグ）を実行する。
- 指摘を「不変条件・正しさの問題 → 層境界違反 → 性能（SQLite の prefetch 罠など）→ その他」の順に並べる。上から直す。

## 2. 修正前に指摘の妥当性を確認する

- 該当コードを実際に読み、指摘が正しいか確かめる。**誤検出だと判断したら修正せず、理由を添えて報告する**（無理に変更をひねり出さない）。
- 指摘に含まれない箇所は直さない。ついで修正をしたくなったら、別の作業として提案に留める。

## 3. 正しい層で直す

対症療法（画面側で握りつぶす等）ではなく、責務を持つ層で直す。

| 指摘の種類 | 直す場所 |
| --- | --- |
| 業務ルール・不変条件の欠落 | `myapp/domain/`（集約・値オブジェクト） |
| domain 層への Django 混入 | import を除去し、必要な変換は infrastructure 側へ移す |
| ユースケースの手順・検査漏れ | `myapp/application/services.py` |
| ORM・クエリの問題（prefetch 罠など） | `myapp/infrastructure/`（回避例: repositories.py の `Prefetch(...)`） |
| 画面・フォーム・導線 | `myapp/presentation/`・templates |

- 「同じ事実の出典を2つ作らない」「選択肢はドメインが唯一の出典」等の原則に反する指摘は、フィールドやロジックの**削除**が正しい修正になることが多い。追加で繕う前に消す案を検討する。

## 4. 再発防止テストを添える

- バグ・不変条件の欠落を直したら、**同じ修正の中に再発防止テストを書く**（CLAUDE.md の規約）。業務ルールなら `tests/test_domain_*.py`（DB 不要）、画面・永続化なら `tests/test_integration.py`。
- 純粋なリファクタリング指摘（重複除去・簡素化）は既存テストが通ることの確認でよい。

## 5. 検証と報告

1. 修正した層に応じてテストを実行する（`run-tests` スキル参照）。domain 層だけの修正でも、最後にフルスイートを1回通す。`ruff check .` と `mypy .` も通す。
2. 報告は「指摘ごとに: 修正した／誤検出として見送った（理由）」の形でまとめる。
3. コミットはユーザーに求められた場合のみ。その場合は規約どおり**論理的なまとまりごと**に分け（無関係な指摘の修正を1コミットに混ぜない）、日本語のメッセージで main に直接コミットする。

## 6. 修正後にメモリへ記録する

修正が終わったら、必ずメモリへの記録を行う。記録の基準は [[record-problems-encountered]] に従う。

- **記録する**: 再発する性質のもの。環境・ツールの癖が原因だった指摘、原因の特定に手間取った不具合の根本原因、レビューで繰り返し出る種類の違反（同じ層境界違反が2回目なら、なぜ起きやすいかを記録する）。既存のメモリ（例: [[sqlite-prefetch-related-expression-depth]]）に該当する再発なら、新規作成せずそのメモリに追記する。
- **記録しない**: 修正内容そのもの（git 履歴が持つ）、その場限りの単純ミス。
- 該当するものが1件も無ければ「メモリに記録する事項なし」と報告に明記する（記録の検討を忘れたのか、検討して無しと判断したのかを区別できるようにする）。
