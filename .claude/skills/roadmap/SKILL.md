`docs/ROADMAP.md` はこのプロジェクトの実装計画で、README と並ぶ一次ドキュメント。
更新の際は既存の形式を必ず守る。

## ROADMAP.md の形式

- **現在地**: 実装済みの土台の箇条書き。機能が完成したらここにも反映する（フェーズ側の ✅ だけで終わらせない）。
- **フェーズ**: `## フェーズN: タイトル` + 状態（`✅ 完了` / `（進行中）` / 無印=未着手）。
  - 本文は必ず **なぜ:** から始まる（現状の問題と、なぜこのフェーズで解決するのか）。
  - 項目は `✅` / `⬜` で進捗を付ける。
  - 実装しながら決めた設計判断（「下書き保存は見送った。〜ため」など）は、完了後もフェーズ内に残す。**完了したフェーズは削除しない**（判断の記録として残す）。
- **保留**: 見送った項目は `### 保留: 〜` の小見出しで、**見送った理由**と**再開する条件**（「必要になる場面が出てきた時点で入れる」）をセットで書く。理由なしの保留は書かない。
- **依存関係**: 末尾にフェーズ間の依存を図示。フェーズを追加・完了したらここも見直す。

## 更新の手順

1. `docs/ROADMAP.md` と直近の `git log --oneline -10` を読み、現状とのずれを確認する。
2. 完成した機能があれば: 該当項目を `✅` にし、「現在地」に1行追加する。フェーズ内の全項目が済んだら見出しを `✅ 完了` にする。
3. 新しい機能を計画に入れる場合:
   - 既存フェーズに収まるならそこへ `⬜` で追加する。
   - 収まらないなら新フェーズを追加する。**なぜ:** を必ず書く（書けない場合はユーザーに問題意識を確認する）。フェーズは「都度確認してから次へ進む」単位＝動作確認できる単位で切る。
   - 要件・設計まで詰める必要があるものは、先に `feature-designer` エージェントで設計してから、その結論（スコープ・フェーズ分割・保留判断）をロードマップに反映する。
4. 見送り・縮小の判断をしたら「保留」として理由と再開条件を残す（前例: フェーズ2の `Season` エンティティ化）。
5. 依存関係の図が現状と合っているか確認する。

## 書かないこと

- 実装の詳細（クラス名・関数名レベル）。ロードマップは「何を・なぜ・どの順で」まで。詳細は設計書や README に書く。
- 期日。このプロジェクトは順序と依存関係だけで管理している。
