# テストの入力の選び方と書き方（技法とこのプロジェクトでの前例）

`SKILL.md` §0 で置く層を決めた後に、**何を入力にして何を確かめるか**を選ぶための一覧。
世の中のテスト技法のうち、このアプリ（単一コンテナ・SQLite・Django＋一部 React）で効くものだけを、前例とあわせて載せる。
ファイルの置き場所・分割・共通の土台は `.claude/rules/tests.md` が出典。

## まず観点を選ぶ（変更の種類 → 使う技法）

| 変更の種類 | まず使う技法 |
| --- | --- |
| 数値・件数・年の判定を足した／変えた | 境界値分析・同値分割 |
| 条件が2つ以上組み合わさる判定（勝敗・S・H、枠、資格） | デシジョンテーブル（＋表駆動） |
| 状態を持つもの（シーズンの進行・締め・オフ・ドラフト） | 状態遷移テスト（できる遷移と、拒まれる遷移の両方） |
| 乱数を使うもの（シミュレーション・仮想データ） | 出目の固定＋性質テスト（種を変えても成り立つこと） |
| 同じ事実を2か所に持つもの（明細と打席、値オブジェクトと列） | 突き合わせテスト（契約テスト） |
| 画面・URL・書き込みの導線 | 権限の行列（未ログイン・一般・担当者・スタッフ）と世界の隔離 |
| 挙動を変えないリファクタリング | 特性テスト（ゴールデン）を先に置く |
| バグの修正 | 再発防止テスト＋修正を外すと落ちる確認（`SKILL.md` §6.5） |

## 入力の選び方

### 境界値分析・同値分割

入力を「同じ扱いになるまとまり」（同値クラス）に分け、各まとまりから1つと、**まとまりの境目の両側**を選ぶ。
境目では `<` と `<=` の取り違えが起きる。境目の値・その1つ手前・1つ先（3値）を並べる。

- 投球回の表記（`InningsPitched.from_notation`）: `5.0` / `5.2` / `5.3`（繰り上げて `6.0`）/ 空・`None`（0）/ 負（例外）
- 人数の上限（支配下の登録枠 `DEFAULT_REGISTERED_PLAYER_LIMIT` など）: 上限ちょうど・上限＋1
- 年の境目: 締めた年と締める前の年（`is_season_closed`）、FA 権の短縮の「2007年以降のドラフト」（`test_free_agency.py` の境界の前例）
- 年齢: 誕生日の前日・当日（年齢は生年月日から算出。CLAUDE.md）
- 空: 選手0人・試合0件・成績の無い選手（集計の分母が0）

### デシジョンテーブル（＋表駆動テスト）

条件の組み合わせごとに期待する結果を表にし、**表の1行を1ケース**にする。
表は `subTest` を回すループかテストメソッドの並びで書く（`test_value_objects.py` の背番号の前例）。

```python
CASES = [
    # (登板時のリード, 投球回) → 最後に投げた投手に付くもの（勝ち試合を最後まで投げた場合）
    ((3, "1.0"), "セーブ"),
    ((4, "1.0"), None),  # 3点差を超えると1回だけではセーブにならない（境界の両側）
    ((4, "3.0"), "セーブ"),
    ...,
]
for args, expected in CASES:
    with self.subTest(args=args):
        ...
```

- 前例: `tests/domain/test_decisions.py`（勝敗・セーブ・ホールドをイニングスコアと継投から決める）
- 表にすると、条件の組み合わせの抜け（どの行も当てはまらない組み合わせ）が見える。抜けは仕様の穴なので、テストで埋める前にユーザーに確かめる。
- 全組み合わせが多すぎるときは、2つの条件の組だけを網羅する（ペアワイズ）。ただし規則が3つ以上の条件の同時成立に依存するときは、その組を明示的に足す。

### 状態遷移テスト

状態（例: シーズン中 → シーズン終了 → ポストシーズン → 締め → オフ → 翌年）と、その間を動かす操作を書き出し、
**どの状態で何ができて（活性）、何が拒まれるか（安全性）**を両方確かめる。拒まれる側は抜けやすい。

- 前例: 締めた年の試合の書き込みを `AlreadyClosed` で拒む（`test_pennant_season.py`・`test_pennant_awards.py` など）
- 同じ操作の連打（2回締める・2回進める）、戻る操作（締めた後に試合を直す）も遷移として並べる
- 画面では、拒まれる操作の導線そのものを出さない（CLAUDE.md「UI・設計方針」）。導線が出ていないことも integration で確かめる

### 乱数を含む処理: 出目の固定と性質テスト

- **個々の結果を確かめる**ときは出目を固定する: 種を固定した `make_random(seed)`、または出目を順に返す `ScriptedRandom`
  （`test_simulation_engine.py` など）。種を固定しないテストはフレーキーになる。
- **どの出目でも成り立つ性質**は、種を複数回して確かめる（性質ベースのテスト）。
  前例: `test_simulation_engine.py` の `for seed in range(...)`（種が違えば違う試合になる・上書きを渡さなくても同じ打席列・抑えにセーブが付く）。
  使える性質: 1イニングのアウトは3つ・明細は打席から数え直した値と一致する（`ensure_lines_match_plate_appearances`）・
  合計が保存される・同じ種なら同じ結果（再現性）。
- 分布の検査（打率が NPB の帯に入るか）は `simulate_sample` などの実測で見る。帯の端を詰めるテストは書かない。
- 性質テストの専用ライブラリ（Hypothesis など）は入れていない。入れるなら依存の追加なのでユーザーに提示する。

### 突き合わせテスト（同じ事実の2つの出典をそろえる）

同じ事実を2か所に持つと、ずれても例外にならず静かに壊れる。**片方を足したら、両方を突き合わせるテストを同じコミットに置く。**
ソースや設定を見るだけなら `SimpleTestCase`（DB 不要）で書く。

- `test_stat_fields.py`（成績の値オブジェクトのフィールドと永続化の列）
- `test_wiring.py`（`build_*()` が依存をすべて渡しているか）
- `test_templates.py`（テンプレートのコメント記法）

### 権限の行列と世界の隔離

書き込みの導線と URL は、利用者の種類ごとに行列で確かめる: 未ログイン・一般ユーザー・チーム担当者・スタッフ ×
（導線が見えるか・GET が通るか・POST が通るか）。前例: `test_permissions.py`・`test_navigation.py`。
ペナントの世界を扱う変更は、**別の世界・実データにデータが漏れない・書かれない**ことも確かめる
（`test_world_isolation.py`・`test_pennant_write_scope.py`・`test_seed_commands_scope.py`）。

### エラー推測

過去に実際に起きた不具合の型を狙う（CLAUDE.md「既知の罠」とメモリーがその一覧）:

- JSON API でキーを欠落させる（空リストと同じ扱いにして全消去した）
- テンプレートのコメントが画面に漏れる（`test_templates.py`）
- 年の既定値が現実の今日になる（`add_player` など）
- 多段の `prefetch_related` が関連1000件超で落ちる（テストのデータ量では出ない → `measure_pages`）
- 選手名などの利用者の入力を JS の文字列に埋める（エスケープ。#320）

## テストの組み立て方

### 準備・実行・確認（AAA）とフィクスチャ

- 1つのテストは「準備 → 実行 → 確認」の3段に分け、確認は実行した操作の結果だけを見る。
- 準備が重いもの（選手の登録・世界の分岐・シーズンを回す）は `setUpTestData` でクラスに1回（`.claude/rules/tests.md`）。
  `setUpTestData` で作ったオブジェクトをテストの中で書き換えない（次のテストに漏れてフレーキーになる）。
- 成績は `helpers.play_game` などで試合から作る（成績を直接持たせられない）。

### テストダブル（モック・スタブ・フェイク）は最小限

- domain のテストは本物の値オブジェクトと集約で組む（Django が無いので速い）。
- integration は本物のリポジトリと SQLite を使う。モックに置き換えると、本物と違う振る舞い（例外の条件・境界）を正解にしてしまう。
- 差し替えるのは、本物では再現できないか遅いものだけ: 乱数（`ScriptedRandom`）、現在時刻、外部への送信、
  特定の失敗を起こしたい保存（`test_team_save_diff.py` のリポジトリのサブクラス）。
- 呼ばれた回数を数える（スパイ）より、結果の状態を確かめる。回数や順序が仕様そのもののとき（クエリ数 `assertNumQueries` など）だけ数える。

### 特性テスト（ゴールデンファイル）

挙動を変えない置き換え（DTO への移し替え・クエリの書き換え）の**前に**、今の出力をファイルに固定してから手を入れる。
前例: `tests/integration/golden/game_edit_payload.json` と `test_game_edit_payload.py`（DB の id は名前の記号に置き換えて固定）。

- 固定するのは「変えないと決めた出力」だけ。仕様を変える変更でゴールデンを更新するときは差分を1行ずつ読む（`SKILL.md` §6）。
- 画面の見た目の差分を画像で比べるテスト（ビジュアル回帰）は入れていない。崩れやすいレイアウトは要素の位置・重なり・はみ出しを数値で確かめる
  （`test_usage_map_layout.py`・`test_header_layout.py`・`test_roster_table.py`）。

## E2E を書くとき

- **待つのは状態であって時間ではない。** `time.sleep` を使わず、`page.wait_for_url(...)`・`locator(...).wait_for()` で待つ。
- **ログインなどの共通の操作は1か所にまとめる。** 同じ手順が2つ目の E2E ファイルに現れたら `tests/e2e/base.py` に移す
  （画面の部品が変わったときの修正を1か所にする。PageObject の考え方）。
- **検証の対象でない準備は ORM・`helpers` で作ってよい**（画面で選手を何十人も登録しない）。ただし、そのシナリオで確かめたい導線そのものは画面で操作する
  （準備を飛ばした部分は実際には通っていないので、そこで起きる結合の不具合は見つからない）。
- 1シナリオに確認を詰め込みすぎない。途中で落ちると後ろの確認が全部見えなくなる。
- 前例: `test_pennant_flow.py`（作る → 日を進める → 順位・試合を読む、締める → 翌年）・`test_game_edit_react.py`（React の編集画面）。

## このプロジェクトでは使わないもの

負荷・ストレス・スパイク・ソーク・スケーラビリティ・カオス・フェイルオーバー・クロスブラウザ・ファジングのテストは、
今の構成（単一コンテナ・SQLite・Chromium のみ）では置いていない。遅さは `measure_pages` で実測する（`SKILL.md` §5.5）。
一般公開（`docs/ROADMAP.md`）に合わせて必要になったら、何を足すかをユーザーに提示する。
