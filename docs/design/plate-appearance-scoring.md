# 打席を出典にする（スコアブックと同じ手順で試合を記録する）

## なぜ

今の試合の記録は「**完成したボックススコアの転記**」になっている。

| 画面 | 今の操作 |
| --- | --- |
| `/games/new/` | シーズン・日付・両チーム・**最終得点を手入力**して登録 |
| `/games/<id>/edit/` | イニングスコア ＋ **ロスター全員**の行に、打数・単打・二塁打…**9列を手入力** |

実データでは編集画面に**平均34人ぶんの行**が並ぶ（実際に出場するのは打者19人・投手10人）。
そして `打数・単打・二塁打・打点` は、**本来スコアラーが試合後に数える値**である。
つまり集計作業を人にやらせている。

実際のスコアラーの手順はこうである。

1. **試合前** — メンバー表から打順1〜9・守備位置・先発投手を書き写す
2. **試合中** — 「打順9行 × イニング」のマス目に、**1打席ずつ結果**を記号で書く。
   交代は同じ打順のマスを縦に割る。走者の進塁・アウト・得点も同じマスに書く
3. **試合後** — 縦計・横計を取って集計し、**打点の合計＝得点**で検算する

この差は入力の手間だけの問題ではない。**検算が存在しない**ため、打点の合計と
イニングスコアが矛盾しても気づけない。

方向はプロジェクトの既存方針とまっすぐ噛み合う。README の「導出できるものは
入力させない」に従って**勝敗・セーブ・ホールドは既にイニングスコアと継投から導出**
済みで、得点もイニングスコアから自動計算される。打撃成績だけが手入力で
取り残されている。

さらに、**経過と集計を両方持って集約が照合する形には既に前例がある** —
`entities.py` の `ensure_line_score_matches()`（イニングスコア↔最終得点）。
打席の列と `BattingLine` を同じ関係に置く。

## 決めたこと

| 論点 | 決定 |
| --- | --- |
| 範囲 | ラインアップ先行 ＋ 打席ごとの記録 ＋ 投球成績も導出（段階A＋B＋C） |
| 打席の粒度 | **走者の進塁まで**記録する |
| 既存データ | **全試合を打席入力に移行**（`seed_virtual_games` を書き換えて全再生成） |
| 失策 | 記録する。自責点を導出可能にする前提であり、進塁の理由としても必須 |

全 3,480 試合は `seed_virtual_games` 由来の仮想データで、実データの印は無く、
README にシーズン単位の作り直し手順もある。**全再生成は安全**。

### 範囲外（明示的に入れない）

- **投球数・球種・ボールカウント（1球ごとの記録）**。打席より一段深い粒度で、
  入力が「1球ずつクリック」になり負荷が跳ね上がる。打席を出典にする目的
  （集計を人にやらせない・検算を入れる）はこれ無しで達成できる
- 審判・立会人・記録員

## 記録項目の棚卸し

NPB の公式成績項目と突き合わせた結果。**「欠け」が想定よりずっと多い。**

### 打撃

| 項目 | 今 | 移行後 |
| --- | --- | --- |
| 打数・安打・二塁打・三塁打・本塁打・塁打 | ある | 打席から導出 |
| 打点・四球・死球・犠飛 | ある | 打席から導出 |
| **得点** | **無い** | 進塁から導出 |
| **三振** | **無い**（奪三振はある） | 打席から導出 |
| **盗塁・盗塁刺** | **無い** | 進塁の理由から導出 |
| **犠打** | **無い**（docstring で自認） | 打席から導出 |
| **故意四球** | **無い** | 打席から導出 |
| **併殺打** | **無い** | 進塁から導出（1打席でアウト2つ） |
| **失策出塁・野選出塁** | **無い** | 打席結果の種別 |
| 打率・出塁率・長打率・OPS | ある | 変わらず |

打撃成績表を並べたら半分近くが空欄になる状態だった。

**犠打を記録すると規定打席の分母が変わる。** `BattingLine.plate_appearances` の
docstring が「本来は犠打も含むが、このアプリでは記録していない」と自認している
箇所が解消される。規定打席（試合数 × 3.1）の判定結果が現状と変わるため、
タイトルの受賞者が変動しうる。

## ドメインモデル

`myapp/domain/value_objects.py` と `entities.py` に置く。Django を import しない。

### 値オブジェクト

```
Base (Enum)                    打者席(0) / 一塁(1) / 二塁(2) / 三塁(3) / 本塁(4) / アウト(-1)

PlateAppearanceResult (Enum)   打者の結果。各値が以下を知っている:
                                 counts_as_at_bat  打数に数えるか
                                 is_hit / bases    安打か・何塁打か
                                 retires_batter    打者アウトか
  単打 / 二塁打 / 三塁打 / 本塁打
  四球 / 故意四球 / 死球
  三振（空振り）/ 三振（見逃し）
  ゴロアウト / フライアウト / ライナーアウト / 邪飛
  犠打 / 犠飛
  失策出塁 / 野選出塁
  打撃妨害 / 守備妨害

AdvanceReason (Enum)           進塁・アウトの理由。各値が以下を知っている:
                                 is_out             アウトになる理由か
                                 earns_run_batted_in 還ったとき打点が付くか
                                 is_unearned_cause  自責点の判定から除くか
  打撃 / 四死球・妨害 / 押し出し / タッチアップ
  盗塁 / 盗塁刺 / 牽制死
  失策 / 暴投 / 捕逸 / ボーク
  野選 / アウト / 封殺 / 走塁死

ErrorKind (Enum)               失策の種類
  捕球 / 送球 / 落球
```

実装して分かった追加が3つある。

- **`アウト`（`PUT_OUT`）** — 打球・三振でそのままアウトになる場合に当てはまる理由が
  無かった。三振は封殺でも走塁死でもない。打者アウトの大半がこれになる。
- **`四死球・妨害`（`AWARDED_BASE`）** — 打者が四死球で一塁を与えられる場合の理由も
  無かった。塁を詰められて進む走者の `押し出し` とは別概念で、**押し出しは還れば
  打点が付くが、こちらは付かない**（打者は自分の四球で還れない）。
- **`捕逸` を `ErrorKind` から外した** — 捕逸は公式記録では失策として数えない別の記録。
  進塁の理由（`PASSED_BALL`）としてだけ持つ。

打数に数えるかの判定表（`counts_as_at_bat`）:
四死球・故意四球・犠打・犠飛・妨害は**数えない**。失策出塁・野選出塁・三振・凡打は**数える**。

**併殺打は種別として持たない。** 「その打席でアウトが2つ記録された」として進塁から
導出する。種別にも持たせると同じ事実の出典が2つになる。

### エンティティ

```
RunnerAdvance (frozen)
  runner_id     走者（打者自身も含む）
  from_base     Base
  to_base       Base（アウトなら Base.OUT）
  reason        AdvanceReason
  error_index   失策に起因するなら、その失策の位置
  is_earned     本塁に達したとき、自責点か（推定値）

FieldingError (frozen)
  player_id / position / kind

RunnerSubstitution (frozen)    代走。塁上の走者を入れ替える
  base / leaving_runner_id / entering_runner_id

PlateAppearance
  sequence        試合内の通し番号。**時系列の唯一の出典**
  inning / is_bottom
  batter_id / pitcher_id
  batting_order / slot_sequence
  result          PlateAppearanceResult
  fielded_by      打球の処理経路（6-3 なら (遊, 一)）。刺殺・補殺の出典
  advances        list[RunnerAdvance]
  substitutions   list[RunnerSubstitution]
  errors          list[FieldingError]
```

- **`outs_before`（打席前のアウト数）は持たない。** 塁の状態を再生すれば求まるので、
  持つと同じ事実の出典が2つになる（当初の設計から外した）。
- **`RunnerSubstitution`（代走）を足した。** 交代は進塁ではないため `RunnerAdvance` では
  表せず、走者が入れ替わっていないと塁の再生が「その塁にいない走者が進んだ」と
  誤って弾いてしまう。**失点の責任投手は塁について回るので、代走にも自動で引き継がれる。**

`Game` 集約が `plate_appearances: list[PlateAppearance]` を持つ。
1試合あたり約 76打席・約 200進塁・約 1.3失策。集約の読み込みは1試合 約280行になる
（今は約30行）。**参照は既に `infrastructure/queries.py` 経由で集約を組み立てないので、
影響は更新経路だけ。**

## 導出の一覧

| 導出物 | 出典 |
| --- | --- |
| `BattingLine` | 打席結果の集計 ＋ 進塁（得点・盗塁・併殺打） |
| `PitchingLine` | 打席結果を投手ごとに集計 ＋ アウト数から投球回 |
| `FieldingLine`（新） | `fielded_by` から刺殺・補殺、`errors` から失策 |
| `LineScore` | 本塁に達した進塁を回・表裏ごとに数える |
| 最終得点 | `LineScore`（既にそう） |
| 勝敗・セーブ・ホールド | `LineScore` と継投（既にそう。変更なし） |
| イニングごとの安打・失策 | 打席結果・`errors` |
| 残塁 | イニング終了時に塁上に残った走者 |
| 完投・完封・無四球 | 投球回・失点・与四球 |

**手入力として残るのは:**
試合日・対戦カード・球場・（任意で試合時間・観客数）／ラインアップ（打順・守備位置・
先発投手）／打席ごとの結果・打球の処理経路／走者の進塁／失策（守備者・種類）／
交代／**自責点の上書き**（推定と違うときだけ）。

**消える手入力:**
最終得点・イニングスコア・打撃成績9列・投球成績のカウント6列・投球回。

### 自責点は「推定＋上書き」にする

NPB 公式規則 9.16 の自責点は「**失策・捕逸が無かったものと仮定して、そのイニングを
再構成する**」定義である。再構成には記録員の裁量が入る余地があり、
**完全な自動導出は規則上できない。**

実装方針:

1. 失策・捕逸・暴投に起因する進塁を取り除いてイニングを再構成し、
   それでも本塁に達したはずの走者を自責点とする（推定値）
2. 推定値を既定として表示し、**上書きできる欄を1つ残す**
3. 上書きされた試合には印を出す（推定と違うことが読み取れるように）

これは「導出できるものは入力させない」と規則の限界の折り合いである。
**設計上の例外として意識的に残すもので、他の項目に広げない。**

## 検算（集約が守る不変条件）

スコアブックの「縦計・横計」に相当する。`Game` 集約が自分で検査する。

- 各回のアウトは3以下（最終回・サヨナラは3未満で終わりうる）
- 同じ塁に2人の走者がいない
- アウトになった走者はそれ以降進まない
- 打者の到達塁が結果と整合する（本塁打なら本塁、単打なら一塁以上）
- **打順は1〜9を巡回する**（前の打者の次は打順+1、9の次は1）。
  スコアブックを横に読む性質そのもので、入力ミスを強く捕まえる
- 得点の合計 ＝ イニングスコア ＝ 最終得点
- 打点の合計 ＝ 本塁到達のうち打撃に起因するもの
  （失策・野選・暴投による得点は打点にならない）
- アウトの合計 ＝ 投手の投球回の合計（アウト数）
- 被本塁打 ≦ 被安打（既存の検査を維持）

ORM へ直接書き込むデータ投入コマンドは集約の検査を素通りするため、
`seed_virtual_games` は自分で同じ検査を行う（CLAUDE.md の既存規則）。

### 新テーブル

| --- | --- | --- |
| `GamePlateAppearance` | 打席 | 76 × 3,480 ≒ **264,000** |
| `GameRunnerAdvance` | 進塁 | 約1.5/打席 ≒ **400,000** |

| `GameFieldingError` | 失策 | 1.3 × 3,480 ≒ **4,500** |

合計 **約68万行**（今の打撃 68,091 ＋ 投球 27,589 ＋ イニング 62,640 = 約16万行から4倍強）。

**代走のテーブルは当初の3つに入っていなかった**（P1 で `RunnerSubstitution` を足したときに
必要になった。進塁では表せず、無いと塁の再生が誤って弾く）。

`Game` に `stadium` FK（null 許容。中立地開催のため）と、任意の試合時間・観客数を追加。

### 打席を読むのは1試合を編集するときだけ（P2 で決めたこと）

集約の読み込みは1試合 約280行になる。**まとめて読む経路（`find_all` /
`find_by_team` / `find_between_teams`）には打席を付けない。** リーグ集計のために
呼ぶと数十万行を組み立てることになるためで、打席が要るのは1試合の編集だけ
（`find_by_id`）。

このとき **「打席を読んでいない」と「打席の記録が無い」を区別しなければならない。**
区別しないと、順位表や集計のために読んだ試合を保存しただけで、記録済みの打席が
全部消える（既知の罠「キーの欠落を空リストと同じ扱いにする」と同じ形で、
エラーにならないので気づけない）。`Game.plate_appearances_loaded` がその印で、
False の集約を保存したときは打席に触れない。

### 既存テーブルの去就 — 決着（P4）

`GameBattingLine` / `GamePitchingLine` / `GameInningScore` は**すべて導出値になる**。
「出典を完全に1つにする」方針なので消す方向だったが、**実測の結果、残すことにした。**

当初の判断基準はこうだった。

| 実測結果 | 判断 |
| --- | --- |
| 主要画面が現状の応答時間を保てる | **消す**（出典が完全に1つ） |
| 保てない | 導出値として保存する形で残し、集約が照合する（`ensure_line_score_matches` と同じ形）。この場合 **CLAUDE.md に例外として明記する** |

**決め手になったのは応答時間ではなく、「自責点は SQL で集計できない」という構造だった。**

「消す」判断の下限**とする。

### 移行手順

既存の打撃成績からは打席を逆算できない（打数5・安打2 からどの回に何が起きたかは
復元不能）。したがって:

1. 新テーブルを追加するマイグレーション
2. `seed_virtual_games` を打席ベースに書き換え
3. 全データ再生成（既存の試合を消してから投入）
4. 旧テーブルを削除するマイグレーション（上記の判断で「消す」になった場合）

## 画面

### 記録の編集 `/games/<id>/edit/`（React）

今の4カード（試合情報・イニングスコア・打撃成績・投球成績）を置き換える。

段階単体では main に入れられない（P1 は永続化が無く、P2 は画面が無い）ため、
統合ブランチの上にタスクブランチを乗せる（CLAUDE.md「段階単体では main に
入れられない機能は `epic/` に積む」）。

| | ブランチ |
| --- | --- |
| 統合（main への PR はここだけ） | `epic/plate-appearance-scoring` |
| P1 ドメイン層 | 統合ブランチに直接（着手時はこの運用が無かった） |
| P2 永続化 | `feature/pa-persistence`（統合ブランチを基点に切り、base も統合ブランチ） |
| P3 以降 | 同じ形で統合ブランチの上に積む |

worktree は origin/main を基点に作られるので、統合ブランチの上に乗せるには
`git worktree add -b <タスク> .claude/worktrees/<名前> epic/plate-appearance-scoring`。

**段階の区切りごとに main を取り込む。** 並行して別のタスクが main にマージされていく
（P1 完了時点で4コミット遅れており、取り込んで検証済み）。

**P3 は既存の seed が楽になる可能性がある。** 今の seed は「明細どうしが食い違わない
ように片方から他方を導く」ために手の込んだ作りになっている（打点の合計＝得点、
投手の被安打＝相手打線の安打、被本塁打の割り当てに多変量超幾何分布）。
**打席を先に生成すれば整合は自動的に取れる**ため、この配分ロジックの大半が不要になる。

→ **そのとおりになった。** 配分のための多項分布・多変量超幾何分布と、回ごとの得点を
投手の力量で重み付けして配る処理、継投の受け持ちを先に割り振る5つのメソッド
（`_split_innings` `_shave_outs` `_merge_innings` ほか）はすべて消えた。代わりに
「半回を3アウトまで進める」ループが入り、得点・イニングスコア・引分・サヨナラは
**引かずに結果として決まる**ようになった（TIE_SURVIVAL_RATIO のような、同点を
後から壊す調整値も要らなくなった）。

## P4 の実測と決定 — 既存テーブルは残す

打席ベースの集計を実際に書いて、旧テーブルからの集計と突き合わせた
（3,480試合・271,907打席・345,828進塁）。

### 値は完全に一致した

| 対象 | 結果 |
| --- | --- |
| 打撃（打数・安打・本塁打・打点） | **850選手すべて一致** |
| 投球回 | **777投手すべて一致** |

打席の記録は旧テーブルと矛盾していない。**移行の前提は成立している。**

### 速度は 4〜7倍かかる

| 集計 | 旧テーブル | 打席ベース |
| --- | --- | --- |
| 打撃・1リーグ（198選手） | 8ms | 50ms |
| 打撃・全選手（1,629人） | 53ms | **375ms** |
| 投球・全選手（自責点を除く） | 152ms | **243ms** |

リーグタイトルは既に 771ms あり、ここに +42ms（1リーグぶん）が乗る。
**この時点ではまだ「遅いが許容できる」範囲**だった。

### 決め手 — 自責点は SQL で集計できない

**自責点と失点は、走者ごとに「誰が塁に出したか」「失策が絡んだか」を追う
逐次再生でしか出せない**（`runs_scored_in`）。責任投手は塁について回り、
代走にも引き継がれるので、打席や進塁を単独で数えても求まらない。SQL の
`GROUP BY` で表せる形ではない。

実測すると **200試合の再生に 3.9秒 → 3,480試合で約68秒**。防御率を出すたびに
これが必要になる。**1画面 68秒は成立しない。**

さらに、旧テーブルを消すと `domain/services/records.py` の通算・月別・年度別の集計が
`Game` 集約の `batting` / `pitching` を読めなくなり、**まとめて読む経路でも打席を
組み立てざるを得なくなる**（1試合280行 × 3,480試合）。P2 で意識的に避けた形に戻る。

### 決定

**`GameBattingLine` / `GamePitchingLine` / `GameInningScore` は導出値として残す。**
出典は打席で、これらはその集計結果を保存したものと位置づける。同じ事実が2か所に
あることになるので、**集約が照合する** — `domain/services/scoring.py` の
`ensure_lines_match_plate_appearances()` が、保存しようとしている明細が打席から
導ける値と一致しているかを見る（イニングスコアと最終得点を突き合わせる
`ensure_line_score_matches()` と同じ形）。

- `DjangoGameRepository.save()` が保存前に必ず通す
- `seed_virtual_games` も自分で呼ぶ（`bulk_create` は集約の検査を素通りするため）。
  **3,480試合すべてが通ることを確認済み**
- 照合しないのは勝敗・セーブ・ホールド・先発登板だけ。これらは打席からは決まらない
  （イニングスコアと継投から決まる別の関心事）

**この例外は CLAUDE.md の「同じ事実の出典を2つ作らない」に明記した。**
打席から導ける値を手入力で書き換えようとすると、日本語のメッセージで弾かれる。

### 画面の応答は据え置き（読み取り経路を変えていないため）

打席ベースの集計は**実測のために書いて、採用しなかった**。`save()` に照合を足しただけで、
参照の経路は1行も変えていない。

参考までに P4 完了時の実測は リーグタイトル 834ms・ダッシュボード 500ms・試合詳細 446ms
だったが、**P3 の 771 / 473 / 394ms との差は P4 の変更によるものではない**
（同じシードで作り直した DB と測定環境のばらつき。3回測って ±5ms 以内に安定していた）。
**段階をまたいだ絶対値の比較は当てにならない**ので、次に判断が要るときは同じ DB で
前後を測ること。

### この判断が P5 に持ち込む前提

**試合編集画面（`/games/<id>/edit/`）で打撃・投球成績を手入力できる状態は、
打席の記録がある試合では成立しなくなった**（照合で弾かれる）。P5b でこの画面を
スコアブック入力に置き換えるまでの間だけ、打席のある試合は編集できない。
弾かれたときは日本語のメッセージが 400 で返る（500 にはならない）。

## P5a — スコアブックの保存

### 見つけたバグ: `update_game` が打席の記録を消していた

**P4 の時点では「照合で弾かれる」と書いたが、実際は弾かれずに消えていた。**
`TeamApplicationService.update_game` は現在の試合を読んだうえで `Game` を
組み立て直すのだが、そこに `plate_appearances` を載せていなかった。空の集約は
「打席を読んでいない」ではなく**「記録が無い」**として保存され、リポジトリが
その試合の打席を全部消す。P2 で用意した `plate_appearances_loaded` の印を、
別の入口からすり抜けていた形。

集約を組み立て直すコードは**打席の記録も引き継ぐ**。再発防止テストを添えた。

### `GameRecordingService`（新設）

`TeamApplicationService` は既に約50メソッド・1,500行あるため、**打席の記録を
保存する関心事は別のサービスに置いた**（CLAUDE.md の規則に従いユーザーに確認）。
依存は3つ（`games` / `teams` / `leagues`）で、チームの一覧も試合の一覧も要らない。

**受け取るのは試合の基本情報・ラインアップ・打席だけ。** 得点・イニングスコア・
登板順・登板した回・勝敗・セーブ・ホールドはすべて導出する。得点を引数で受け取らない
のは、受け取ると「記録と食い違う得点」を保存できてしまうため。

チーム所属の判定に**選手の索引を引かない**。表の攻撃で打っているのはビジター、
投げているのはホーム —— **スコアブック自身が答えを持っている**。索引を引くと
全チームのロスターと通算成績まで読むことになる。

### API

`POST /api/games/<id>/scorebook/`（`api_game_scorebook`）。進塁と失策は打席の中に
入れ子で送る（並びが変わっても走者の動きが別の打席に付かない）。

**組み立ての途中でもドメインが弾く**（進塁の理由と到達の食い違いなど）。
値オブジェクトの `__post_init__` が投げるので、フォームの検証を通った後に
例外が出る。ここを捕まえないと 500 になるため、フォームの誤りと同じ 400 にしている。

旧 API（`api_game_update`）は成績を手入力する今の画面のために残してある。

## P5b — スコアブックの入力画面

4つのカードに置き換えた（試合の情報・ラインアップ・スコアブック・導出値の確認）。
入力するのは試合日・打順・打席だけで、**得点の入力欄は無くなった**。

### 入力は順番に積む

打席の通し番号は1から欠けずに続き、打順は1〜9を巡回する。**任意のマスに後から
差し込む形にすると、この2つを画面側で守らせることになる。** マス目は記録済みの
打席を読むためのものにして、追加は常に末尾（「次の打席を記録する」）、取り消しも
末尾（「最後の打席を取り消す」）だけにした。マスをクリックすればその打席は直せる。

### 語彙と既定値は payload で払い出す

**打席の結果・進塁の理由・塁・失策の種類と、既定の進塁の対応表は、すべて
ドメインの値オブジェクトから payload に載せる。** TypeScript から Python の Enum は
読めないので、画面側に同じ表を書くとずれても例外にならず、選択肢や既定値だけが
静かに古くなる。払い出せば出典は1つのままになる。

そのために `PlateAppearanceResult` へ `default_runner_advance` と
`default_runner_reason` を足した（`default_batter_base` の走者版）。

**TypeScript に残った重複は塁の番号だけ。** 番号の大小がそのまま「進んだか」を
表すので、ずれると画面の進塁の判定だけが静かに壊れる（表示名は payload から届くため
見た目では気づけない）。`test_stat_fields.py` がドメインの `Base` と突き合わせる。
成績のカウント項目の TS↔Python 突き合わせは、React が成績を持たなくなったので消えた。

## P6a — 成績を手入力する経路を消した

`api_game_update`（旧 API）・`InningScoreForm` / `BattingEntryForm` /
`PitchingEntryForm`・`TeamApplicationService.update_game` をすべて削除した。
**成績を保存する経路はスコアブック1本になった。**

### テストの移し替え

`build_scorebook()` をテストヘルパーに足した。**得点は本塁打、アウトは三振**で
表すので走者が塁に残らず、「何回に何点入ったか」と「誰がいつ投げたか」を渡すだけで
成立する打席の並びが作れる。勝敗・セーブ・ホールドや登板順の結合テストはこれで書き直した。

**移し替えずに消したテストもある。** 打席から導くようになったことで、
**そもそも起こりえなくなった**もの:

| 消したテスト | なぜ起こりえないか |
| --- | --- |
| イニングスコアの合計と最終得点の不一致 | 得点を打席から導くので、食い違う値を送れない |
| 得点の訂正 | 同上（訂正は打席を直すこと） |
| 被本塁打が被安打を超える入力 | 本塁打は安打の一種として1打席から数える |
| 空欄の行を記録しない／行を消して出場を取り消す | 出場はラインアップで決まる |

いずれも規則そのものの検査は値オブジェクトのテスト（`tests/domain/`）に残っている。
テストは 737件から 716件になったが、**減った21件はすべて「もう起こりえない入力」の検査**。

### `build_scorebook` で踏んだ間違い

守備側の投手を選ぶときに**表と裏を取り違えていた**（ホームの投手は表に投げる）。
テストは通らなかったが、症状は「相手の先発が9回投げて勝利投手になっている」という
一見それらしい形で出た。**攻撃側と守備側を取り違えても記録としては成立してしまう**ので、
このあたりを書くときは投球回の合計を見ると早い。

## P6b — 打撃・投球の成績項目を増やした

設計書の冒頭で「欠けている」と数えた項目を、打席から導いて保存するようにした。

| 対象 | 増えた項目 |
| --- | --- |
| 打撃 | 得点・三振・犠打・故意四球・盗塁・盗塁刺・併殺打 |
| 投球 | 失点 |

**犠打を数えるようになったので規定打席の分母が変わった。** `BattingLine.plate_appearances`
の docstring が「本来は犠打も含むが、このアプリでは記録していない」と自認していた箇所が
解消され、タイトルの受賞者が動きうる（全再生成するので実質的な問題は無い）。

### 併殺の定義を直した

**盗塁刺と三振が同じ打席に入ると、併殺打として数えられていた。** `is_double_play` が
「アウトが2つ以上」だったため。走塁のアウトは打者への守備ではないので、
`AdvanceReason.is_baserunning_out`（盗塁刺・牽制死）を除いて数えるようにした。

これは投入データの水準合わせで見つかった。**盗塁刺が NPB の目安 0.2 に対して 0.04**
しか出ておらず、追うと「打者がアウトになる打席では盗塁刺を起こさない」という制限を
投入側に入れていた。制限の理由がこの誤判定だったので、定義を直して制限を外した。
打点も同時に直っている（併殺の間の得点は打点にならないが、走塁のアウトは関係ない）。

### 同じ列挙を3か所で踏んだ

項目を増やしたら**投入コマンドの3か所が古いまま**で、新項目が 0 のまま保存された。

1. `_batting_orm_rows` が打撃の項目を並べていた
2. `_pitching_orm_rows` が投球の項目を並べていた
3. `_pitching_lines` が勝敗を載せるために `PitchingLine` を組み立て直していた

**どれも例外にならず、画面の欄が空になるまで気づけない形。** 1と2は
`fields(BattingLine)` から流し込む形に、3は `replace()` で持ち越す形に直した。
`test_seed_virtual_games.py` の突き合わせも、項目を1つずつ並べるのをやめて
**値オブジェクトの全フィールドを比べる**ようにした（これがあれば最初から落ちていた）。

### 全再生成の水準（1チーム1試合あたり）

| 指標 | 投入結果 | NPB の目安 |
| --- | --- | --- |
| 得点 | 3.79 | 3.9 |
| リーグ打率 | .252 | .255 |
| リーグ防御率 | 3.50 | 3.50 |
| 三振 | 7.39 | 7.5 |
| 犠打 | 0.58 | 0.6 |
| 故意四球 | 0.10 | 0.1 |
| 盗塁 / 盗塁刺 | 0.57 / 0.22 | 0.55 / 0.2 |
| 併殺打 | 0.66 | 0.7 |
| 失点（自責率） | 3.79（92%） | 3.9（90%前後） |

投入の最後に表示される「リーグ全体の水準」に、増えた項目も並べるようにした。

## P6c — ボックススコアに新しい項目を出した

並びは NPB のボックススコアにならい、打率 → 打数・得点・安打・打点 → 長打の内訳 →
四球・死球・三振 → 犠打・犠飛・盗塁・併殺打 の順にした。

`strikeouts_batting` という別の名前にした**（`strikeouts` は投手の奪三振）。
同じ欄に別の事実を入れると、表のどちらを見ているかで意味が変わってしまう。
