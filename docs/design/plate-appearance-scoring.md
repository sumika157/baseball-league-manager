# 打席を出典にする（スコアブックと同じ手順で試合を記録する）

## なぜ

今の試合の記録は「**完成したボックススコアの転記**」になっている。

| 画面 | 今の操作 |
| --- | --- |
| `/games/new/` | シーズン・日付・両チーム・**最終得点を手入力**して登録 |
| `/games/<id>/edit/` | イニングスコア ＋ **ロスター全員**の行に、打数・単打・二塁打…**9列を手入力** |

実データでは編集画面に**平均34人ぶんの行**が並ぶ（実際に出場するのは打者19人・投手10人）。
そして `打数・単打・二塁打・打点` は、**本来スコアラーが試合後に数える値**である。
つまり集計作業を人にやらせている。

実際のスコアラーの手順はこうである。

1. **試合前** — メンバー表から打順1〜9・守備位置・先発投手を書き写す
2. **試合中** — 「打順9行 × イニング」のマス目に、**1打席ずつ結果**を記号で書く。
   交代は同じ打順のマスを縦に割る。走者の進塁・アウト・得点も同じマスに書く
3. **試合後** — 縦計・横計を取って集計し、**打点の合計＝得点**で検算する

この差は入力の手間だけの問題ではない。**検算が存在しない**ため、打点の合計と
イニングスコアが矛盾しても気づけない。

方向はプロジェクトの既存方針とまっすぐ噛み合う。README の「導出できるものは
入力させない」に従って**勝敗・セーブ・ホールドは既にイニングスコアと継投から導出**
済みで、得点もイニングスコアから自動計算される。打撃成績だけが手入力で
取り残されている。

さらに、**経過と集計を両方持って集約が照合する形には既に前例がある** —
`entities.py` の `ensure_line_score_matches()`（イニングスコア↔最終得点）。
打席の列と `BattingLine` を同じ関係に置く。

## 決めたこと

| 論点 | 決定 |
| --- | --- |
| 範囲 | ラインアップ先行 ＋ 打席ごとの記録 ＋ 投球成績も導出（段階A＋B＋C） |
| 打席の粒度 | **走者の進塁まで**記録する |
| 既存データ | **全試合を打席入力に移行**（`seed_virtual_games` を書き換えて全再生成） |
| 失策 | 記録する。自責点を導出可能にする前提であり、進塁の理由としても必須 |

全 3,480 試合は `seed_virtual_games` 由来の仮想データで、実データの印は無く、
README にシーズン単位の作り直し手順もある。**全再生成は安全**。

### 範囲外（明示的に入れない）

- **投球数・球種・ボールカウント（1球ごとの記録）**。打席より一段深い粒度で、
  入力が「1球ずつクリック」になり負荷が跳ね上がる。打席を出典にする目的
  （集計を人にやらせない・検算を入れる）はこれ無しで達成できる
- 審判・立会人・記録員

## 記録項目の棚卸し

NPB の公式成績項目と突き合わせた結果。**「欠け」が想定よりずっと多い。**

### 打撃

| 項目 | 今 | 移行後 |
| --- | --- | --- |
| 打数・安打・二塁打・三塁打・本塁打・塁打 | ある | 打席から導出 |
| 打点・四球・死球・犠飛 | ある | 打席から導出 |
| **得点** | **無い** | 進塁から導出 |
| **三振** | **無い**（奪三振はある） | 打席から導出 |
| **盗塁・盗塁刺** | **無い** | 進塁の理由から導出 |
| **犠打** | **無い**（docstring で自認） | 打席から導出 |
| **故意四球** | **無い** | 打席から導出 |
| **併殺打** | **無い** | 進塁から導出（1打席でアウト2つ） |
| **失策出塁・野選出塁** | **無い** | 打席結果の種別 |
| 打率・出塁率・長打率・OPS | ある | 変わらず |

得点・三振・盗塁・犠打・故意四球・併殺打の **6項目が欠けている**。NPB の
打撃成績表を並べたら半分近くが空欄になる状態だった。

**犠打を記録すると規定打席の分母が変わる。** `BattingLine.plate_appearances` の
docstring が「本来は犠打も含むが、このアプリでは記録していない」と自認している
箇所が解消される。規定打席（試合数 × 3.1）の判定結果が現状と変わるため、
タイトルの受賞者が変動しうる。

### 投球

| 項目 | 今 | 移行後 |
| --- | --- | --- |
| 投球回・被安打・与四球・奪三振・被本塁打・与死球 | ある（手入力） | 打席から導出 |
| 勝敗・セーブ・ホールド | 導出済み | 変わらず |
| 自責点 | **手入力** | 失策から**推定**＋上書き（下記参照） |
| **失点** | **無い** | 進塁から導出 |
| **完投・完封・無四球試合** | **無い** | 導出 |
| **対戦打者数** | **無い** | 打席から導出 |
| **故意四球** | **無い** | 打席から導出 |
| **暴投・ボーク** | **無い** | 進塁の理由から導出 |
| **被犠打・被犠飛** | **無い** | 打席から導出 |
| 防御率・WHIP・K/9・BB/9・FIP | ある | 変わらず |

投手を評価できない。失策を記録すれば両方が出る。

### 守備

**丸ごと無い。** `FieldingPosition` は「この試合でどこを守ったか」だけを持ち、
守備の成績は1項目も存在しない。

| 項目 | 今 | 移行後 |
| --- | --- | --- |
| **失策** | **無い** | 記録する |
| **刺殺・補殺** | **無い** | 打球の処理経路から導出 |
| **守備機会・守備率** | **無い** | 導出 |
| **併殺参加** | **無い** | 導出 |
| **捕逸**（捕手） | **無い** | 進塁の理由から導出 |
| **盗塁阻止率**（捕手） | **無い** | 盗塁刺から導出 |

新しく `FieldingLine` 値オブジェクトを作る（`BattingLine` / `PitchingLine` と対になる）。

### 試合

| 項目 | 今 | 移行後 |
| --- | --- | --- |
| シーズン・日付・両チーム・得点 | ある | 得点は導出 |
| イニングごとの得点 | ある（手入力） | 打席から導出 |

### 値オブジェクト

```
Base (Enum)                    打者席(0) / 一塁(1) / 二塁(2) / 三塁(3) / 本塁(4) / アウト(-1)

PlateAppearanceResult (Enum)   打者の結果。各値が以下を知っている:
                                 counts_as_at_bat  打数に数えるか
                                 is_hit / bases    安打か・何塁打か
                                 retires_batter    打者アウトか
  単打 / 二塁打 / 三塁打 / 本塁打
  四球 / 故意四球 / 死球
  三振（空振り）/ 三振（見逃し）
  ゴロアウト / フライアウト / ライナーアウト / 邪飛
  犠打 / 犠飛
  失策出塁 / 野選出塁
  打撃妨害 / 守備妨害

AdvanceReason (Enum)           進塁・アウトの理由
  打撃 / 押し出し / タッチアップ
  盗塁 / 盗塁刺 / 牽制死
  失策 / 暴投 / 捕逸 / ボーク
  野選 / 封殺 / 走塁死 / 併殺

ErrorKind (Enum)               失策の種類
  捕球 / 送球 / 落球 / 悪送球 / 捕逸
```

打数に数えるかの判定表（`counts_as_at_bat`）:
四死球・故意四球・犠打・犠飛・妨害は**数えない**。失策出塁・野選出塁・三振・凡打は**数える**。

**併殺打は種別として持たない。** 「その打席でアウトが2つ記録された」として進塁から
導出する。種別にも持たせると同じ事実の出典が2つになる。


1試合あたり約 76打席・約 200進塁・約 1.3失策。集約の読み込みは1試合 約280行になる
（今は約30行）。**参照は既に `infrastructure/queries.py` 経由で集約を組み立てないので、
影響は更新経路だけ。**

## 導出の一覧

| 導出物 | 出典 |
| --- | --- |
| `BattingLine` | 打席結果の集計 ＋ 進塁（得点・盗塁・併殺打） |
| `PitchingLine` | 打席結果を投手ごとに集計 ＋ アウト数から投球回 |
| `FieldingLine`（新） | `fielded_by` から刺殺・補殺、`errors` から失策 |
| `LineScore` | 本塁に達した進塁を回・表裏ごとに数える |
| 最終得点 | `LineScore`（既にそう） |
| 勝敗・セーブ・ホールド | `LineScore` と継投（既にそう。変更なし） |
| イニングごとの安打・失策 | 打席結果・`errors` |
| 残塁 | イニング終了時に塁上に残った走者 |
| 完投・完封・無四球 | 投球回・失点・与四球 |

**手入力として残るのは:**
試合日・対戦カード・球場・（任意で試合時間・観客数）／ラインアップ（打順・守備位置・
先発投手）／打席ごとの結果・打球の処理経路／走者の進塁／失策（守備者・種類）／
交代／**自責点の上書き**（推定と違うときだけ）。

**消える手入力:**
最終得点・イニングスコア・打撃成績9列・投球成績のカウント6列・投球回。

### 自責点は「推定＋上書き」にする

NPB 公式規則 9.16 の自責点は「**失策・捕逸が無かったものと仮定して、そのイニングを
再構成する**」定義である。再構成には記録員の裁量が入る余地があり、
**完全な自動導出は規則上できない。**

実装方針:

1. 失策・捕逸・暴投に起因する進塁を取り除いてイニングを再構成し、
   それでも本塁に達したはずの走者を自責点とする（推定値）
2. 推定値を既定として表示し、**上書きできる欄を1つ残す**
3. 上書きされた試合には印を出す（推定と違うことが読み取れるように）

これは「導出できるものは入力させない」と規則の限界の折り合いである。
**設計上の例外として意識的に残すもので、他の項目に広げない。**

## 検算（集約が守る不変条件）

スコアブックの「縦計・横計」に相当する。`Game` 集約が自分で検査する。

- 各回のアウトは3以下（最終回・サヨナラは3未満で終わりうる）
- 同じ塁に2人の走者がいない
- アウトになった走者はそれ以降進まない
- 打者の到達塁が結果と整合する（本塁打なら本塁、単打なら一塁以上）
- **打順は1〜9を巡回する**（前の打者の次は打順+1、9の次は1）。
  スコアブックを横に読む性質そのもので、入力ミスを強く捕まえる
- 得点の合計 ＝ イニングスコア ＝ 最終得点
- 打点の合計 ＝ 本塁到達のうち打撃に起因するもの
  （失策・野選・暴投による得点は打点にならない）
- アウトの合計 ＝ 投手の投球回の合計（アウト数）
- 被本塁打 ≦ 被安打（既存の検査を維持）

ORM へ直接書き込むデータ投入コマンドは集約の検査を素通りするため、
`seed_virtual_games` は自分で同じ検査を行う（CLAUDE.md の既存規則）。

### 既存テーブルの去就 — P2 で実測して決める

`GameBattingLine` / `GamePitchingLine` / `GameInningScore` は**すべて導出値になる**。
「出典を完全に1つにする」方針なので消す方向だが、**通算成績の集計が 26万行の
打席テーブルへの条件付き集計になる。**

**判断は測ってから行う。**

| 実測結果 | 判断 |
| --- | --- |
| 主要画面が現状の応答時間を保てる | **消す**（出典が完全に1つ） |
| 保てない | 導出値として保存する形で残し、集約が照合する（`ensure_line_score_matches` と同じ形）。この場合 **CLAUDE.md に例外として明記する** |

逃げ道を用意しておくのは、既知の罠（SQLite の式木上限・「落ちずにただ遅い」形で出る）
を踏み直さないためである。

### 移行手順

既存の打撃成績からは打席を逆算できない（打数5・安打2 からどの回に何が起きたかは
復元不能）。したがって:

1. 新テーブルを追加するマイグレーション
2. `seed_virtual_games` を打席ベースに書き換え
3. 全データ再生成（既存の試合を消してから投入）
4. 旧テーブルを削除するマイグレーション（上記の判断で「消す」になった場合）

## 画面

### 記録の編集 `/games/<id>/edit/`（React）

今の4カード（試合情報・イニングスコア・打撃成績・投球成績）を置き換える。

1. **試合情報** — 日付・球場・（任意で試合時間・観客数）。得点は導出値の表示のみ
2. **ラインアップ** — 両チームの打順1〜9・守備位置・先発投手をロスターから選ぶ。
   交代はここで打順に追加する（`slot_sequence` を自動採番）。
   これだけで「34人ぶんの行が並ぶ」問題が解消する
3. **スコアブック** — 打順9行 × イニング列のマス目。**入力の中心**。
   マスをクリックすると打席入力パネルが開く
4. **導出値の確認** — イニングスコア・打撃・投球・守備成績を**読み取り専用**で表示し、
   検算の結果（打点合計＝得点 など）を出す

### 走者の進塁の入力負荷を既定値で吸収する

「走者の進塁まで記録する」と決めたが、素朴に作ると1打席あたり3〜5操作になる。
**結果を選んだ時点で進塁の既定値を自動で埋める**ことで、大半の打席は
「結果を選ぶだけ」で終わるようにする。

| 結果 | 自動で埋まる進塁 |
| --- | --- |
| 単打 | 打者→一塁、走者は1つ進む |
| 二塁打 | 打者→二塁、走者は2つ進む |
| 本塁打 | 打者と全走者→本塁 |
| 四球・死球 | 打者→一塁、埋まっている塁は押し出しで1つ進む |
| 三振・凡打 | 打者→アウト、走者は動かない |
| 犠打 | 打者→アウト、走者は1つ進む |
| 犠飛 | 打者→アウト、三塁走者→本塁 |

既定と違うときだけ触る。**この既定値はあくまで入力補助**で、確定はサーバー
（フォームとドメイン層）が行う（`.claude/rules/frontend.md` の既存規則）。

無四球を追加。**守備成績のカードを新設**（守備機会・刺殺・補殺・失策・守備率、
捕手は捕逸・盗塁阻止率）。

## テスト計画

置き場所は CLAUDE.md の規則に従う。

**`tests/domain/`（DB 不要・Django 非依存・最速）**
- 打席結果の種別ごとの `counts_as_at_bat` / `is_hit` / `bases` / `retires_batter`
- 進塁の整合（同じ塁に2人・アウト後の進塁・打者の到達塁と結果の不整合）
- 打順の巡回の検算
- `BattingLine` / `PitchingLine` / `FieldingLine` / `LineScore` の導出
- 自責点の推定（失策絡みの得点が自責点にならないこと）
- 打点が失策・野選による得点に付かないこと

**`tests/integration/`**
- リポジトリ往復（1試合の打席・進塁・失策）
- 保存 API の部分更新でキーが欠けたときに既存データを全消去しないこと
  （既知の罠。行は位置ではなく識別子で組み立てる）
- 編集画面・試合詳細・選手ページの表示
- `test_stat_fields.py` の突き合わせを**打席結果の種別**に拡張
  （TypeScript ↔ Python の列挙のずれは例外にならず静かな不具合になるため）

**性能**
- `measure_pages` を P0（ベースライン）・P2・P3 の完了時に実測

## 実装フェーズ

| | 内容 | 検証 |
| --- | --- | --- |
| **P0** ✅ | `measure_pages` でベースラインを取る | 実測値を上表に記録済み |
| **P1** | ドメイン層（値オブジェクト・`PlateAppearance`・導出・検算） | `tests/domain/`（DB 不要） |
| **P2** | 新テーブル3つ ＋ リポジトリ ＋ 集計クエリを打席ベースに | 実測 → **既存テーブルの去就を決める** |
| **P3** | `seed_virtual_games` を打席ベースに書き換え、全再生成 | 実測 ＋ NPB 水準の維持を確認 |
| **P4** | React の入力画面（ラインアップ・スコアブックのマス目・進塁の既定値） | integration ＋ e2e |
| **P5** | 参照画面（試合詳細・選手ページ・守備成績）＋ README 更新 | integration |

各フェーズを1コミットにまとめる（実装＋テスト＋該当ドキュメント）。

**P3 は既存の seed が楽になる可能性がある。** 今の seed は「明細どうしが食い違わない
ように片方から他方を導く」ために手の込んだ作りになっている（打点の合計＝得点、
投手の被安打＝相手打線の安打、被本塁打の割り当てに多変量超幾何分布）。
**打席を先に生成すれば整合は自動的に取れる**ため、この配分ロジックの大半が不要になる。

## 未決事項

1. **既存テーブルを消すか導出値として残すか** — P2 の実測で決める（上記）
2. **`fielded_by` の粒度** — 刺殺・補殺を出すには処理経路（6-3 の全体）が要る。
   打球方向だけで足りるかは、守備成績をどこまで出すかで決まる
3. **試合時間・観客数を入れるか** — スコアブックのヘッダ項目だが成績には効かない。
   球場と違い、無くても表現力は落ちない
4. **規定打席の変動** — 犠打を記録すると分母が変わり、過去のタイトル受賞者が
   変動しうる。全再生成するので実質的な問題は無いが、README の数値例は更新が必要
