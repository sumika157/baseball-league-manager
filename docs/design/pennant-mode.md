## 1. なぜ

今のアプリは**試合を記録して読む道具**です。成績を生む仕組み（`seed_virtual_games`）は、開発用コマンドの中に閉じています。打席モデル・勝敗の導出・順位とタイトルの集計は揃っているのに、**「編成の判断が成績として返ってくる」使い方ができません。**

ペナントモードは、能力 → 打席 → 既存の導出・集計という経路を本番の機能に昇格させます。そのうえで、GM が編成してシーズンを見守る遊びにします。

**目的は「遊べるゲーム（GM 体験）」に決定済み**です（ユーザーの判断）。重心は GM で、1試合ごとの采配はしません。そのため、複数シーズンとオフの処理まで（P1〜P6）を初期範囲とします。

## 2. やること / やらないこと

### やること（初期範囲 = P1〜P6）

- **別の世界（セーブデータ）**: 実データのリーグを分岐元にして作る。実データの画面・集計には一切混ざらない
- **能力値**: 野手5項目・投手4項目。成績は能力から生まれる結果として、既存の打席モデルに保存する
- **試合シミュレーション**: ドメイン層に置く（Django にも numpy にも依存しない）。乱数のシードで再現できる。NPB の水準に合わせる
- **シーズン進行**: NPB 形式の日程（1チーム143試合）を作り、1日・1週間・次の自軍の試合まで、の単位で進める
- **GM の操作**: 受け持つ球団は1つ。1軍登録と2軍、オーダーとローテーションの自動編成と上書き
- **オフ**: 成長・衰え・引退・ドラフト（自動指名）を経て次のシーズンへ

### やらないこと（理由つき）

| 項目 | 理由 |
| --- | --- |
| 1試合ごとの采配・選手の操作 | ユーザーの決定（重心は GM） |
| トレード・FA・年俸 | AI の評価関数と経済の仕組みがまるごと要り、初期範囲の倍の量になる。編成を見守る体験は、ドラフトと成長だけで一巡する |
| ポストシーズン（CS・日本シリーズ） | 順位表とタイトルで1年の区切りは付く。後から日程の種類を増やす形で足せる |
| 故障 | 1軍登録の入れ替えを AI に毎日させる必要が生じる。登録の履歴を期間として持つ判断とも連動する |
| 2軍の試合 | 2軍は「1軍に登録されていない」という状態だけにする。2軍の成績は作らない（試合が増えて、保存量が倍になる） |
| 投手の打席（DH なし） | 投手への代打・ダブルスイッチが要る。`seed_virtual_games` も DH 制だけ |
| 代走・暴投・捕逸・守備交代 | `seed_virtual_games` の簡略化をそのまま引き継ぐ（打席モデルは代走を表せるので、後から足せる） |
| 球場補正（パークファクター） | `StadiumProfile` はあるが、効かせる根拠となる水準が未定 |
| シミュレーションした試合の手動編集 | 結果は出力であって、記録の入力ではない。編集画面は実データの側にだけ置く |
| 実データの `Season` エンティティ化 | 3.4 で述べるとおり、ペナントでも不要だった |

## 3. ドメインへの影響

### 3.1 別世界の表し方

#### 比べた案

| 案 | 内容 | 混ざらない保証 | 既存コードへの影響 | 弱点 |
| --- | --- | --- | --- | --- |
| **A. リーグにだけ世界 ID を持たせる（推奨）** | `League.world`（null なら実データ）を足す。Team・Game・Player はリーグを辿って世界が決まる | **リポジトリと参照クエリが、組み立て時に世界の範囲を必須で受け取る。** 範囲外の id は NotFound | 絞り込みを入れる場所が約20か所（下の 4.2）。ドメインの集約・導出・集計はそのまま使える | どこか1か所の絞り忘れが混入になる → 混入検査のテストで機械的に捕まえる（7.） |
| B. 全テーブルに世界 ID | Team・Player・Game・明細まで `world_id` を持つ | A と同じ | A より広い | **世界の出典が2つになる**（Team.world と Team.league.world が食い違いうる）。不採用 |
| C. 世界ごとに SQLite ファイルを分ける | Django の複数 DB と、contextvar で振り分けるルーターを使う | 物理的に分かれる。絞り込みは要らない | クエリはそのまま使える | `Team.managers`（auth_user への M2M）が DB をまたげない。DB の別名を実行時に作る、世界ごとにマイグレーションを流す、PostgreSQL へ移すとき（ROADMAP フェーズ5）に作り直し、と運用の仕組みが重い |
| D. ペナント専用の ORM モデルを並列に作る | `PennantTeam`、`PennantGame` など約12モデルを別に持つ | 型で分かれる | ORM・マッピング・集計クエリの二重実装になる | **成績項目を増やすたびに2か所を直す。** P6b で「3か所踏んだ」と同じ形の、静かな不具合の温床になる。不採用 |

**推奨は A です。** ドメイン層（`Team` / `Game` / 導出 / 集計）とアプリケーション層の参照ユースケース（順位表・タイトル・成績一覧・選手ページ・ボックススコア）を、**世界の範囲を変えるだけで丸ごと再利用できます。** 世界の出典は `League.world` の1か所だけです。

#### 混ざらないことの保証

1. **範囲の値オブジェクト `WorldScope`**（`WorldScope.real()` / `WorldScope.pennant(world_id)`）を作る。全リポジトリと参照クエリのコンストラクタで**必須の引数**にする（既定値なし）。
   - 「None なら全世界」という読み方をする API は作らない
   - 既存の呼び出し（`build_service()`、`tests/helpers.py`）は引数が増えて mypy で落ちるので、渡し忘れが残らない
2. **id で引く経路も範囲で絞る**（`find_by_id` を含む）。例えば `/team/<ペナントの球団id>/` は 404、`/api/games/<ペナントの試合id>/scorebook/` も `GameNotFound` で 404 になる。
3. **絞り込みは SQL 側で行う**（`.claude/rules/performance.md`）。Python で捨てると、捨てる分の組み立て費用がかかる。
4. **混入検査のテスト**（7.）
   - 実データ側の全 URL を開いて、ペナント側の目印の名前が HTML に出ないことを確かめる
   - ペナントの id で実データ側の URL を開いて 404 になることを確かめる
   - 加えて、myapp の全モデルを「リーグ経由で世界に属す／選手経由／試合経由／共有（`Stadium`）／ペナント専用」に分類した表を持つ。分類されていないモデルがあれば落とす（`test_stat_fields.py` と同じ突き合わせの形）

#### 開始時に実データを元にするか

**元にします（推奨）。** 世界を作るときに、実データのリーグを選んで**分岐（スナップショット）**させます。

- 複製するもの: リーグ・球団・選手（プロフィール）・**現在の在籍だけ**（加入年は世界の開幕年にする）
- 複製しないもの: 試合と過去の在籍（分岐前の事実は実データの側に1つだけある）
- 球場は共有（本拠地は実データの `Stadium` を参照するだけで、読み取り専用の参照データとして扱う）

**分岐した後は同期しません。** これは同じ事実の二重化ではなく、別の世界の初期状態です。実データで生年月日を直しても世界には波及しません。同期が要ると言われたら、この判断を見直します。

選手に `origin_player_id`（実データの選手への任意の参照）を持たせるかは選択肢にします（11. の判断6）。持たせると「分岐前の経歴は実データの選手ページへ」というリンクが作れます。

### 3.2 能力値

#### 項目（シミュレーションに効くものだけを持つ）

効かない項目を持つと、能力を上げても何も変わらない「飾り」になります。各項目は**主に1つの事象に効く**ようにして、GM が意味を読めるようにします。

| 区分 | 項目 | 主に効く事象 |
| --- | --- | --- |
| 野手 | ミート | 三振率↓、インプレーの安打率（BABIP）↑ |
| | パワー | 本塁打率、長打の割合 |
| | 選球眼 | 四球率 |
| | 走力 | 盗塁の企図と成功、安打での余分な進塁、併殺の回避 |
| | 守備力 | 失策率、チームの被 BABIP（守備位置で重みを変える） |
| 投手 | 球威 | 奪三振率 |
| | 制球 | 与四球率 |
| | 一発回避 | 被本塁打率 |
| | スタミナ | 先発の受け持ち（対戦打者数の目安）、救援の連投の可否 |

- 投手の3項目が FIP の構成要素（K・BB・HR）と一致するように切っています
- 隠し値の「成長型」（早熟・普通・晩成）を持つ（P6 で使う）
- 肩力・捕球・球速・変化球（パワプロの項目）は持ちません。効かせる事象が無いか、他の項目と重なるためです（11. の判断7）

#### 値の幅

- **1〜100 の整数で、50 = 1軍の平均**とする
- 表示は S（90〜）/ A（80〜）/ B（70〜）/ C（60〜）/ D（50〜）/ E（40〜）/ F（20〜）/ G（〜19）。この区分は値オブジェクト `RatingGrade` が唯一の出典で、画面に区分の表を複製しない
- 能力から各事象の個人の率への変換は `rate = 基準値 × exp(β × (r − 50) / 15)` の形にする。β は項目ごとに P1 の調整で決める

#### 能力と成績を二重の出典にしない

- 能力は**入力**、成績は**出力**。成績から能力を作り直すことはしない
- 唯一の例外は世界の作成時です。実データの通算成績から初期能力を推定します。収縮推定（安定するまでの打席数 k で平均へ寄せる。目安は K 60・BB 120・HR 170・BABIP 800）を使い、作成の1回だけ行います
  - 式は `odds.py` の逆: `率 = (起きた回数 + k × 寄せ先の率) ÷ (機会 + k)`、`能力 = 50 + 15 / β × ln(率 / 基準値)`。寄せ先は能力 50 の率だが、**出場の少ない選手ほど 50 より低い方**へ寄せる（2軍の控えが1軍の平均並みに見えて水準が狂うため）
  - 推定したままでは選手どうしの差が小さく（収縮するため）、タイトルの水準が P1 の目標帯に届かない。そこで**順位を保ったまま、項目ごとに散らばりだけを P1 の分布（`samples.py`）に合わせる**（`domain/simulation/spread.py`。世界に写す選手全員で標準化して、目標の平均・標準偏差に写す）
  - 実装は `domain/simulation/estimate.py`（1人ぶんの式）、`domain/simulation/spread.py`（散らばりの調整）、`domain/pennant/initial_ratings.py`（材料の組み立て・選手全員の推定・成長型）。値と実測は 12. の「P2b の詳細」
- 成長の規則が成績を参照するのは構いません（成績を読んで翌年の能力を出す関数であって、事実の複製ではない）

#### 年齢との関係

**年齢は保持しません。** `Profile.age(as_of)` に**世界の日付**を渡して求めます。現実の今日を渡しません。

- 成長・衰え・引退の規則は、この年齢を引数として受け取る
- 生年月日が空の選手は、世界の作成時に入団年から推定した生年月日を補う（世界の側の事実として持つ）

**既存コードの罠:** `Team.add_player()` / `retire_player()` / `appoint_captain()` は、年を省くと `date.today().year` を使います。ペナントのサービスは**必ず世界の年を渡します**（渡し忘れると、現実の年の在籍ができる）。

#### ドメインの型（案）

`domain/simulation/ratings.py` に置きます。

- `BatterRatings` / `PitcherRatings`（frozen。1〜100 を検査する）
- `GrowthType`（Enum）
- `RatingGrade`（Enum。`from_value(int)`）

### 3.3 試合シミュレーション

**置き場所:** `myapp/domain/simulation/`（Django も numpy も import しない）

| モジュール | 内容 |
| --- | --- |
| `baseline.py` | `LeagueBaseline`（NPB の打席あたりの事象の率。K 19%・BB 7.5%・死球 1%・HR 2.4%・BABIP .290、二塁打と三塁打の割合、失策率など）。**定数の唯一の出典** |
| `odds.py` | 能力 → 個人の率 → 対戦の確率 |
| `baserunning.py` | 結果と走者の走力から `RunnerAdvance` を組み立てる |
| `manager.py` | AI 監督（スタメン・継投・代打の最小限） |
| `engine.py` | 1試合を打席単位で進める |
| `levels.py` | リーグの水準を数える（`seed_virtual_games._report_levels` を移して共有する） |

#### 1打席の確率（log5 を逐次の二択に適用する）

`seed_virtual_games._draw_result` の判定順（死球 → 四球 → 犠打・犠飛 → 打数）を踏襲し、各段の二択を **odds ratio 法**で合成します。

`odds(対戦) = odds(打者) × odds(投手) ÷ odds(リーグ)`

1. 死球 → 四球（選球眼 × 制球）→ 犠打・犠飛（状況。率は seed の値）
2. 三振（ミート × 球威）→ 本塁打（パワー × 一発回避）
3. インプレーの安打（ミート × 守備側の守備力）→ 長打の内訳（パワー・走力）→ 凡打の内訳（失策出塁・野選・ゴロ・フライ・ライナー・邪飛。seed の配分）

**性質:** 能力50どうしなら、どの段も `LeagueBaseline` と正確に一致します（log5 の恒等性）。水準の調整は基準値で、ばらつきの調整は β で、と分けられます。

#### 走者の進塁

`seed_virtual_games` の `_build_advances` / `_destination_on_hit` / `_ground_out` を移します。調整済みの定数を出発点にします（`SCORE_ON_SINGLE_FROM_SECOND = 0.48`、`ADVANCE_ON_GROUND_OUT_RATIO = 0.18` など）。そのうえで走者の走力で増減させます。

**打撃の指標を合わせても得点が多いときは、ここを下げる**（打席 epic の P3 で得た知見）。

`fielded_by`（打球の処理経路）は、seed の `_fielded_by()` のような結果ごとの固定経路ではなく、守備位置の重みで散らします。打席 epic に残っている守備成績（`FieldingLine`）の作業が同じことを求めているので、エンジンで1回だけ実装します。

#### AI 監督（最小限）

| 判断 | 規則 | 根拠 |
| --- | --- | --- |
| 1軍登録（自動） | 能力順に29人。捕手2人以上・投手13〜14人。外国人は `League.foreign_player_roster_limit` の範囲で | 既存の外国人枠 |
| スタメン | 登録位置に合う枠を守備力の順に埋め、DH は残りの最強打者。打順は出塁（1・2番）→ 長打（3〜5番）の定型 | `seed._defensive_alignment` / `_assign_depth_chart` |
| ローテーション | 先発6人。前回の先発から中5日以上空ける | **疲労は保存しない。** 世界の直近の試合（`GamePitchingLine`）から導く |
| 継投 | スタミナと抑える力から受け持ちの目安を決め（エースには長く任せる。#63）、失点が嵩めば早めに代える。抑えはセーブの状況で出す（`SAVE_LEAD_LIMIT` をドメインから借りる） | `seed._pick_reliever`、`decisions.SAVE_LEAD_LIMIT` |
| 救援の連投 | 3連投はさせない | 直近の試合から導く |
| 代打 | 7回以降、負けている、控えに明確に上の打者がいる、の3つが揃えば。1試合2人まで | `seed._maybe_pinch_hit` |
| 外国人の出場枠 | `foreign_player_game_limit` を守る | `seed._quota_allows` |

#### 出力を既存の打席モデルに保存し、既存の導出を通す

エンジンの出力は `list[PlateAppearance]` と打順の記録です。これを**共通の組み立て関数**に渡します。

**今、組み立てが2つ並んでいます。**

- `GameRecordingService._record_pitching()`: 打席で最初に投げた順から登板順を導く
- `seed_virtual_games._pitching_lines()`: シミュレーションの登板記録から登板順を導く

どちらも `pitching_decisions()` を呼ぶ形で、同じことを2回書いています。

**P0 で、これを domain の関数にまとめます。** `domain/services/scoring.py` に置き、名前は `assemble_game(header, lineup: list[LineupEntry], plate_appearances) -> Game` とします。中身は次の4段です。

1. `derived_line_score()` で得点とイニングスコア
2. 打順ごとに `batting_line_for`
3. 初登板の順で `pitching_line_for` と登板順
4. `pitching_decisions` で勝敗・セーブ・ホールド

スコアブックの保存・seed・ペナントの3つがここを通るので、勝敗・セーブ・ホールドは手入力の試合と同じ関数で決まります。`LineupEntry` は domain の値オブジェクトで、`application/dto.py` の `LineupSlot` から写して作ります。

#### 乱数と再現性

- `random.Random` を使い、**`rng.random()` だけを呼びます。** Python の公式ドキュメントが、版をまたいで同じ列を保証しているのはこのメソッドだけです。`gauss` や `choice` は版で変わりうるので、正規分布（Box–Muller）や重み付きの選択は `random()` の上に自前で書きます
- 乱数源は `Protocol`（`GameRandom.random() -> float`）として受け取ります。テストでは固定の列を差し込みます
- **試合ごとのシードは `blake2b(世界のシード, 年, 試合の識別)` から作ります**（`hash()` は `PYTHONHASHSEED` で実行ごとに変わるので使わない）
  - 「1日ずつ進める」と「1週間まとめて進める」で同じ結果になります
  - 同じ世界を同じ操作で進めれば、同じシーズンになります

#### NPB の水準への調整と検証

| 段階 | 方法 |
| --- | --- |
| 水準（平均） | 能力50の球団どうしで N 試合を回し、`levels.py` の表を `LeagueBaseline` で合わせる |
| ばらつき（分布） | 世界作成の能力分布で1シーズン（858試合）を回し、首位打者・本塁打王などを β と能力の分布で合わせる |
| 確認の道具 | 管理コマンド `simulate_sample --games N --seed S`（**DB に書かない**）。ボックススコアを1試合ぶん文字で出し、水準の表を出す |

### 3.4 シーズン進行

**`Season` エンティティは入れません。** ROADMAP の保留理由はペナントでも成り立ちます。

- 参加チーム = 世界のリーグに属する球団（導ける）
- 開幕日・最終日 = 日程と試合の最小・最大（導ける）
- 年度の一覧 = `seasons_of`（導ける）

#### 日程: `Fixture`（未消化の対戦）を新設する

- 持つ項目は日付・ホーム・ビジター
- **消化したら `Game` を作って `Fixture` を消します。** 試合のあとまで残すと、日付と対戦カードの出典が2つになるためです
- 未実施の試合を `Game` で表すことはできません（得点 0-0 の試合として `team_record` に引分で数えられてしまう）

#### 日程の生成

ドメインサービス `generate_schedule(leagues, rules, start, rng, season=None) -> list[Fixture]` を置きます（`leagues` はリーグ id → 球団 id の並び。**1〜8リーグ、各リーグの球団数は同じとは限らない**。ユーザー決定 2026-10-02）。規則は `ScheduleRules` の値で、変えられます。

- **1球団の年間試合数は143**（`games_per_team`）= 交流戦 + リーグ内の総当たり
- **交流戦**: 各リーグは毎年**他の2リーグ**と当たる（2リーグの世界なら相手の1リーグ、1リーグなら交流戦なし）。相手リーグの全球団と**3連戦を1回ずつ**。組み合わせは `interleague_pairs(league_ids, season)` で、**対称**（A が B と当たるなら B も A と当たる）で**年ごとに入れ替わる**。リーグを輪に並べて年ごとにずらした両隣と当たる（3リーグは総当たり、4リーグは輪のつなぎ方3通りを回す）
- **リーグ内**: 残り（143 − 交流戦）を同じリーグの相手に総当たりで配る。割り切れないときは相手ごとに**1試合差まで**（余りを持つカードは、リーグを正則グラフにして選ぶ）。ホームとビジターの差は相手ごとに1以内。交流戦の3連戦は同じ球場
- **2リーグ6球団ずつ**なら NPB 形式（リーグ内25 × 5 ＋ 交流戦3 × 6 = 143、**858試合**）と一致する。8リーグ6球団なら交流戦 3 × 12 = 36、リーグ内107を5相手に21〜22で、**3,432試合**
- 月曜は休み。交流戦は5月下旬（既定 5/24）から、**相手リーグごとのフェーズ（偶数の輪なら2つ、奇数なら3つ）を連続で置き**、7/31 までに収める。2リーグなら6月中旬に終わる（NPB と同じ）。8リーグ（2フェーズ）は7月上旬に終わる。収まらなければ `InvalidSchedule`（`interleague_end` で延ばせる）。交流戦のないリーグはそのフェーズの間、リーグ内の試合を進める
- 連続ホーム・連続ビジターは上限（既定12。2リーグの NPB 形式は9に収まる）。リーグ内の連戦は3か2（余りのカードだけ1試合長い）
- 球団数が奇数のリーグは休みの球団を入れて組む。余りが配れない組み合わせ（例: 5球団だけのリーグで余りが奇数）は `InvalidSchedule` で弾く
- 検査: 同じ日に2試合する球団が無い、組み合わせの試合数、ホームとビジターの偏り、交流戦の相手の対称性と入れ替わり

**将来の課題（ユーザー決定）:** 2リーグ × 4地区制（MLB 型）は今回入れません（9. 参照）。

#### 進行の状態は持たない

| 状態 | 導き方 |
| --- | --- |
| 「今日」 | 消化した最後の試合日（未消化ならその年の開幕前日） |
| シーズン中か | その年に未消化の `Fixture` が残っているか |
| オフか | 未消化が無く、翌年の日程がまだ無い |

カーソルや段階のフィールドを `World` に持つと、日程・試合と食い違いえます。オフの処理は**1つのトランザクション**（「シーズンを締める」）にするので、途中の状態も生じません。

#### 進める単位

`AdvanceTarget`（Enum）を domain に置きます。値は「1日」「1週間」「次の自軍の試合まで」「月末まで」「シーズン終了まで」です。「1日」は、次に試合がある日までを1日として数えます。

#### 順位・タイトル

既存の `domain_services.standings` / `rankings` と、`TeamApplicationService` の `get_standings` / `get_league_titles` / `get_league_stats` を、**世界の範囲で組み立てたサービス**から呼びます。新しい集計は書きません。交流戦も `standings()` の既存の数え方（その球団が関わる試合をすべて数える）でリーグの順位に入るので、NPB と同じになります。

### 3.5 GM の操作

| 操作 | 初期範囲 | 持ち方 |
| --- | --- | --- |
| 受け持つ球団 | ○（1球団。作成時に選ぶ） | `World.managed_team_id` |
| 1軍・2軍 | ○ | **現在の登録だけを持つ**（履歴は持たない）。2軍 =「登録されていない」 |
| オーダー・守備位置・ローテ・抑え | ○ 自動＋上書き | 上書きだけを保存する。持っていなければ毎日自動で編成する |
| 成長・衰え・引退 | ○（P6） | 翌年の能力を新しい行として作る。引退は在籍を閉じる（`Team.retire_player(year=)`） |
| ドラフト | ○ 自動指名（P6） | 新人を生成して在籍を作る。GM が指名する画面は後回し |
| トレード・FA・年俸 | ×（後の段階） | 2. のとおり |

#### 新しい集約 `ClubPlan`（球団の編成）

球団ごとに1つ置きます。持つものは1軍登録の選手 id、オーダーの上書き、ローテーションの上書き、抑えの指定です。

**不変条件**（ロスターを引数に受け取って検査する。背番号の一意性を `Team` が全ロスターで見る前例に倣う）:

- 1軍登録は29人まで
- 外国人の登録は、リーグの枠（`foreign_player_roster_limit`）まで
- 登録できるのは、その球団に在籍している選手だけ
- オーダーは1軍登録の中から9人。重複なし、守備位置が9つを満たす（捕手は登録位置が捕手の選手）
- ローテーションは1軍登録の投手

**`Team` 集約には入れません。** `Team` は実データと共有していて、ロスターの読み込みは通算成績の集計まで連れてきます。`ClubPlan` は選手 id だけを持ち、検査のときにロスターを渡されます。

#### 期間を持つ概念か

1軍登録は本来「いつからいつまで」を持ちます（NPB の再登録10日ルール）。初期範囲は**現在の状態だけ**にします。抹消の履歴を使う規則（10日ルール・故障者の登録）を入れる段階で、`Stint` / `Captaincy` と同型の並列の型 `Registration(from_date, to_date)` を作ります。軸は年ではなく日付なので、型は再利用しません（11. の判断11）。

#### 自動と手動を同じ画面に並べない

「自動編成」の状態では、提案されたオーダーを読み取り専用で出し、「手動にする」の1つだけを置きます。「手動」の状態では、編集欄と「自動に戻す」を置きます。両方を同時に編集可能にはしません。

上書きの中身が無効になったら（登録を抹消した選手がオーダーにいる、など）、その日は自動に落とし、ホームで知らせます。エラーで進行を止めません。不正なソートキーを既定の並びに落とす規則と同じ扱いです。

### 5.3 速さの見積り（`.claude/rules/performance.md`）

| 処理 | 見積り | 根拠 |
| --- | --- | --- |
| 1試合の生成と検査 | 約10〜20ms | seed は3,480試合を70秒（bulk 保存込み） |
| 1シーズン（858試合）を `add_all` で一括保存 | **約15〜30秒** | 同上。**実測 23.4秒**（P3b。12.） |
| 8リーグ48球団（3,432試合）の1シーズン | 生成だけで1試合約9msとして約30秒、保存込みで約2分 | 上の4倍。日程の生成自体は約9ms（P3 の domain で実測）。**実測は 12.**（静かな環境で約93秒と見積もる） |
| 同じく、1試合ずつ `save()` | 約45〜130秒（未実測） | 1試合ごとに明細の update_or_create が約50回。**測っていない**（`add_all` があるので使わない） |
| 1日（6試合）を進める | 1秒以内 | 文脈の読み込み1回＋6試合。**実測 0.19〜0.25秒** |
| 1週間（約36試合） | 数秒 | **実測 約1.0秒**（8リーグの約140試合は 4秒前後、負荷時 8〜11秒） |

- **P3b の実測で置き換えた（12.）。** 1試合は静かな環境で約27ms（シミュレーション約18ms＋保存・照合約9ms）
- **画面から進める上限は、1回の「進める」で約150試合まで**（12. の案）。「シーズン終了まで」は管理コマンド（`pennant_advance --world --to season-end`）か、画面から分割して繰り返し POST する形のどちらかです（11. の判断10）
- seed の `FLUSH_EVERY_GAMES = 200` に倣い、メモリに溜める試合数に上限を設けます

**実データの画面への影響**は、範囲の JOIN（Game → Team → League）が1段増えることだけです。League は数行なので無視できる見込みですが、P2 の前後で**同じ DB で** `measure_pages` を測ります（打席 epic の P4 で「段階をまたいだ絶対値は当てにならない」と分かっている）。

**SQLite の `prefetch_related` の罠:** ペナントの参照は既存のリポジトリの `Prefetch(..., select_related)` をそのまま通るので、新しい多段 prefetch は作りません。新しいクエリ（能力・直近の登板）は **id の巨大なリストではなく、世界での JOIN で絞ります。**

### 6.3 画面ごとの構成

#### 世界の一覧と作成（`/pennant/`）

1. 見出し「ペナント」と説明（「実データのリーグを元に別の世界を作り、GM として編成してシーズンを見守ります。ここでの試合と成績は実データに混ざりません。」）

#### GM ホーム（`/pennant/<w>/`）

状態は保存せず導く（3.4）。上から順に:

1. **自軍の帯**（`stat-strip`）: 順位・勝-敗-分・勝率・首位との差・直近10試合・連続（3連勝など）・残り試合。開幕前は「開幕まで N 日」と前年の順位、シーズン終了後は最終成績
2. **注意**（オーナーだけ。`alert-warning`）: 編成の指定が無効で自動に落ちた日とその理由、連投で翌日使えない抑えなど。進める前に読ませるので帯の直後
3. **結果のまとめ**（`?since=<進める前の今日>` があるときだけ）: 期間の勝敗・順位の変動（3位 → 2位）・首位差の変動、自軍の試合を1行ずつ（日付・相手・○●△・スコア・責任投手・本塁打・詳細へ）、期間の活躍（打者は打率・本塁打・打点の上位、投手は勝利・セーブ）、ほかの試合は `<details>` で畳む。自軍の試合が1試合だけならスコアボード（`linescore-table`）を出す。不正な `since` や今日より後の日付はエラーにせずまとめを出さない。期間は31日程度に丸める
4. **進める**（オーナーだけ）: 「1日進める」（目立つ方。判断8）・「次の自軍の試合まで」・「1週間進める」。ボタンの横に、終わる日付と試合数を事前に出す（`dates_to_play()`）。「月末まで」「シーズン終了まで」は P3b の実測で決めるまで出さない。シーズン終了後は出さず、P6 から同じ場所に「シーズンを締める」を置く（両方を同時には出さない）
5. **次の試合**: 日付・相手・ホームかビジターか・予告先発（両軍。能力の区分つき）と、今後の日程5件
6. **順位表**: 自軍のリーグを最初に出し、**ほかのリーグは選んで切り替える**（8リーグまであるので、タブではなく `form-select` かリンクの並び。リーグが2つまでなら `segmented`）。自軍の行に「自軍」の印
7. **主力打者**（1軍の野手の OPS 上位5人。打率・本塁打・打点・OPS・直近15日の打率）と**投手陣**（ローテーション6人と抑え。勝-敗/S・防御率・次回の登板予定）
8. **タイトル争い**: 自軍の選手が上位5位以内にいる部門（順位・値・首位）
9. 最下部に「この世界を削除する」（オーナーだけ。`btn-link-quiet`）

進めた後は `/pennant/<w>/?since=<進める前の今日>` へリダイレクトする（結果は URL に残るので再読み込みしても消えない。判断4）。二重送信は hidden の `expected_today` で防ぎ、世界の今日がずれていたら進めずに「既に進んでいます」を `messages` で出す。独自の JavaScript は書かない。

### 6.4 GM 体験として大事な情報

- ホームで最初に目に入るのは、自軍の位置（順位・勢い）→ 今回進めた結果 → 注意 → 進める／次の試合 → 順位表・主力・タイトル争い の順
- 故障が無い代わりに見せるもの（どれも保存せず導く）: チームの勢い（直近10試合・連続）、選手の調子（直近15日の成績。**表示だけの値で、シミュレーションに効く隠し能力は作らない**）、使える投手（次回の先発予定、救援の連投と翌日の可否）、編成の健全さ（1軍の人数・外国人枠）、個人の見どころ（タイトル争い）、2軍の選手（能力と年齢だけ。2軍の試合は無い）

### 6.5 共有テンプレートの URL の引き方

テンプレートタグ `{% scoped_url 'player_list' team_id %}` を作り、共有テンプレートの約57か所の `{% url %}` を置き換える。context に世界（`WorldContext`）があれば `pennant_<名前>` を `world_id` を先頭にして引き、無ければ今の `{% url %}` と同じ結果を返す（実データ側の HTML は1文字も変わらない）。DTO に URL を載せる案は全 DTO に presentation の事情が入るので採らない。URL の名前空間はインスタンスの名前空間が `world_id` を運べないので使えない。

検査（`test_world_isolation.py`）: ペナントの全画面の HTML の `href` が、ヘッダーの許可リスト（`/`・`/players/`・`/accounts/...`・`/admin/`・`/pennant/`）以外は `/pennant/<w>/` で始まること。

## 10. 段階計画

### 打席 epic との関係

**打席 epic を main にマージすることを前提条件にします（推奨）。**

- epic の上に epic を積むと、`epic/pennant-mode` から main への PR に打席 epic の差分まで入り、統合ブランチが2本とも長生きして衝突が増えます
- 残っている作業（選手ページの新項目・`FieldingLine`・スコアボードの H と E・README への吸収）は、表示が中心の量です
- **例外:** P1（エンジン）は domain に新しいファイルを足すだけで、打席 epic の安定した部分（P1〜P6b）にしか依存しません。早く着手したい場合は、P1 だけを `epic/plate-appearance-scoring` を基点に切って進め、打席 epic のマージ後に main の上へ載せ直します（衝突は小さい見込み）
- 守備成績（`FieldingLine`）の作業とエンジンの `fielded_by` は同じことを求めるので、どちらで先にやるかを合わせます（11. の判断3）

### ブランチ

- 統合: `epic/pennant-mode`（打席 epic のマージ後の main を基点）
- タスク: `feature/xxx`（`epic/pennant-mode/xxx` は ref の衝突で作れない）
- **P0 は単体で main に入れられるリファクタ**なので、epic に積まず `refactor/assemble-game` から main へ直接 PR を出します

#### 設計と違えたところ・足したところ

- **追加モジュール**: `randomness.py`（乱数源の Protocol・blake2b のシード・Box–Muller・重み付き選択）、`fielding.py`（打球の処理経路・失策を犯す守備者・チームの守備力）、
  `samples.py`（調整用の球団と簡易な日程。本番の日程は P3 の `generate_schedule`）。
- **`seed_virtual_games` は水準の集計だけ `levels.py` に寄せた**（確率モデルには触れていない）。水準の表示が「NPB の目安」の一点から目標帯に変わった。
- **代打のあとの守備位置**: 代打に出た選手がその位置を守れるなら、代打の行にその守備位置を付けて次の守備からそのまま就く（`entered_sequence` は代打に立った打席）。
  守れないなら代打の行は「打」とし、その位置を守れる控えが次の守備の半回の最初の打席から入る（`entered_sequence` はその打席）。守れる控えがいない捕手には代打を出さない。
  どちらの場合も、`fielders_by_plate_appearance` で全打席に9つの守備位置が埋まることを検査している。
- **ブルペンが全員使えない日は続投**: 先発陣から救援を出すと、中5日と3連投禁止が崩れる（試すと、先発が3日続けて投げる試合が出た）。
- **打球の処理経路の限界**: 盗塁刺・牽制死は打球の処理ではないので、刺殺に数えない（`scoring.fielding_credits` の既存の仕様）。

### P2b の詳細（初期能力の推定。実測と決めた値）

測定は `simulate_sample --from-real-leagues 1 2 3 4 5 6 7 8`（DB には書かない）。実データの8リーグ・48球団・1,619人（1シーズン 3,480 試合ぶんの成績）から、世界の作成と同じ推定をして、
その能力で `generate_schedule` の1シーズン（3,432 試合）を回し、元の成績と同じ式（選手ごとの通算から）で数え直した。

#### 推定の式

- **逆写像**: `能力 = 50 + 15 / β × ln(率 / 基準値)`（`odds.scaled_rate` の逆）。β は `RatingSensitivity` と `BaserunningRules` の値をそのまま使う（出典を増やさない）
- **収縮**: `率 = (起きた回数 + k × 寄せ先の率) ÷ (機会 + k)`。機会 = その項目の分母（三振は打数、本塁打は三振でない打数、インプレーの安打はインプレー、四球は打席 − 死球）
- **寄せ先の率** = 基準値を能力 `50 − 6 × (1 − 出場の割合)` で読み替えた率。出場の割合 = 野手は打席 ÷ 400、投手は アウト ÷ 180（60回）で、1 を上限にする。**成績の無い選手は 44 になる**
- **2つ以上の根拠がある項目**（ミート = 三振 + インプレーの安打、パワー = 本塁打 + 二塁打、走力 = 三塁打 + 盗塁の企図 + 盗塁の成功率）は、情報量（β² × 起きた回数）で重みづけた平均
- 対戦打者数は成績に無いので `アウト + 被安打 + 与四球 + 与死球` で数える

| 項目 | 使う実数 | k |
| --- | --- | --- |
| ミート | 三振 / 打数、インプレーの安打 / インプレー | 60、800 |
| パワー | 本塁打 / 三振でない打数、二塁打 / 安打（本塁打除く） | 170、300 |
| 選球眼 | 四球 / 打席（死球除く） | 120 |
| 走力 | 三塁打 / 安打、盗塁の企図 / 出塁、盗塁の成功率 | 600、100、60 |
| 守備力 | 失策 / 守備機会（`GameFieldingLine`） | 600 |
| 球威・制球・一発回避 | 奪三振 / 打数、与四球 / 対戦打者、被本塁打 / 三振でない打数 | 70、170、1000 |
| スタミナ | 先発登板数、1先発あたりの対戦打者数 | 3、10（先発登板数） |

- k は設計書の目安（K 60・BB 120・HR 170・BABIP 800）を野手に使った。**設計に無い値**（二塁打 300・三塁打 600・盗塁 100/60・失策 600・投手の 70/170/1000）は、起きにくい事象ほど長くかかるという一般の傾向から置いた。実データでは決め手が無いので、変えるときは水準の再現度（下）を見直す
- **盗塁の企図と失策は、基準値が定数にならない**（企図は「一塁走者で二塁が空く」機会の数え方に、失策は打球の質に依存する）。選手全員（世界の作成なら分岐元の全選手）の合計を能力 50 の目印にする（`LeagueNorms`）。企図と失策の合計が少ないリーグ（30 企図・500 機会未満）では根拠にしない
- **守備力**は登録位置の傾向（捕手 +4・内野手 +2・外野手 0・指名打者 −8、`samples.spread_club` と同じ向き）に、先発の選択で上振れするぶん（−5）を足した値を事前の平均にする。失策率は守備位置の区分（捕手・内野手・外野手・指名打者）ごとのリーグの率を目印にして、`fielding.ERROR_SKILL_BETA` で能力に直す
- **スタミナ**: 先発登板数 s から事前の平均（先発 62・救援 38）を `s ÷ (s + 3)` で決め、先発なら `manager.STARTER_BATTERS` の逆（1先発の対戦打者数 = 24 + 0.22 × (スタミナ − 50)）を `s ÷ (s + 10)` の重みで効かせる。成績の全く無い投手は 45
- **成長型**: 事前の分布は 早熟 0.2・普通 0.6・晩成 0.2。26 歳以下は、今の能力が高いほど早熟、低いほど晩成へ傾ける（重みを `exp(±0.4 × (総合値 − 50) / 10)` 倍。±2 で頭打ち）。年齢は**世界の開幕年の4月1日**で数え、生年月日が無ければ傾けない。乱数は `blake2b(世界のシード, 開幕年, "growth-" + 分岐元の選手 id)` から選手ごとに作る（**写した先の id は世界ごとに違うので、分岐元の id で引く**。同じシード・同じ分岐元なら同じ成長型。選手を足し引きしても他の選手は動かない）

#### 散らばりの調整（決めた式と値）

推定のあと、世界に写す選手全員を母集団にして、**項目ごと・野手 / 投手ごと**に標準化し、目標の平均・標準偏差に写して 1〜100 に丸める（`spread.py`）。

    能力 = 目標の平均 + 目標の標準偏差 × (推定値 − 母集団の平均) ÷ 母集団の標準偏差

- 目標は P1 の分布で、出典は `samples.py` の定数（`BATTER_MEAN` 44.5・`BATTER_SD` 8.5・`PITCHER_MEAN` 45.0・`PITCHER_SD` 8.0・`BATTER_ITEM_OFFSET`）。`spread_club` も同じ定数を使う（数字を複製しない）
- 一次式なので**順位は変わらない**。平均より低く寄せた選手（成績の少ない選手）は、広げても平均より低いまま（テスト: `test_simulation_spread.py`）
- スタミナは動かさない（先発の割合から決まる2つの山で、すでに P1 と同じ幅）。守備力は位置による差を含めて全体で標準化する
- 人数が 30 に満たない区分は標準偏差が安定しないので、そのまま返す（`MIN_POPULATION`）
- 成長型は調整後の能力で傾ける（調整の後に引く）。世界の作成と確認用のコマンドが同じ関数（`estimate_initial_ratings`）を通る

調整後の分布は、野手・投手とも標準偏差が 8.0〜8.7、平均は野手 43.4〜45.5・投手 45.0（目標どおり。丸めと 1〜100 の頭打ちで 0.1 前後ずれる）。

**平均を動かさず標準偏差だけ広げる案**（推定の平均を保つ）も測ったが、防御率 3.84 / 3.88、失点 4.16 / 4.19 と、P1 の平均へ写す案（3.70 / 3.67、4.01 / 3.96）より元の実データ（3.45・3.73）から遠かった。標準偏差を広げると、平均の周りの凸性で失点が増えるため。採らなかった。

#### 設計と違えたところ・足したところ

- **日程は世界の作成時ではなく、最初の「進める」で作る**（`PennantSeasonService.ensure_schedule()`。「日程も試合もまだ無い」ときだけ。世界の作成が日程の生成規則を知らずに済む。
  ホームが「開幕まで N 日」を出すときは同じ `ensure_schedule()` を呼ぶ）。開幕日は `default_opening_day`（3月25日以降で最初の金曜）
- **`advance(target)` は世界の id を引数に取らない**。世界の id は組み立て口 `build_pennant_season_service(world_id)` で渡し、リポジトリと参照クエリを世界の範囲に固定する
  （`advance(world_id, target)` の形にすると、組み立てた範囲と引数の世界が食い違いうる）
- **`PennantFixture` は世界の列を持たない**（ホームの球団のリーグで世界が決まる。試合と同じ。設計書 5.1 は「世界・日付・ホーム・ビジター」だった）。`(日付, ホーム, ビジター)` の一意制約と日付の索引
- **保存と対戦の削除は同じトランザクション**。application は Django を知らないので、`transaction.atomic` を組み立て口から渡す（`AtomicBlock`）。同じ世界を同時に進めたときは、
  先に対戦を消す（`FixtureRepository.remove` が消化済みを `InvalidSchedule` で弾く）ので、同じ対戦の試合が2つできない
- **`GameRepository.add_all` は検査を書き込みの前に全試合ぶん済ませる**。`save()` と同じ照合・範囲の検査で、保存済みの試合（id がある）は渡せない。種類ごとの bulk_create で、1試合ごとの
  `save()`（update_or_create 約50回）を避ける。`save()` と `add_all` が同じ行の写し方を使う（`_batting_values` / `_pitching_values`）。打席の bulk 保存は `_create_plate_appearances` に切り出して共有した
- **疲労の読み方**: 先発の間隔は「世界の全試合の最後の先発」（期間で切らない。切ると、まとめて進めるか1日ずつかで「中何日か」の答えが変わる）、連投は直近3日の登板
- **交流戦の外国人出場枠は、ホーム球団のリーグの枠**（エンジンは1試合に1つの枠しか受け取らない。球団ごとの枠が要るなら、エンジンの引数の形を変える必要がある。#63 と調整する）
- **1軍登録は1回の「進める」ごとに AI が選ぶ**（能力だけから決まるので、同じ世界・同じ年なら変わらない）。能力が無い選手（その年の能力の行が無い）は出られない
- **試合の識別は球団の id を含む**（`日付:ホーム:ビジター`）。同じ世界の中では安定するが、同じシードの別の世界とは結果が一致しない（分岐のたびに球団の id が変わるため）。
  テストは同じ世界をセーブポイントで巻き戻して突き合わせる
- 世界の削除と混入検査の分類表に `PennantFixture` を加えた。管理画面には登録しない
