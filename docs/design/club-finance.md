## 1. なぜ

ペナントの世界には球団の人気やファンの要素が無く、成績や優勝が「勝った」という結果で終わり、次のシーズンの球団運営に返ってこない。
人気を足し、成績 → 人気 → 観客数（収入）→ 予算 → 補強、という循環を作ると、GM の判断に長い目の目標ができる。
E1 はその土台（人気と観客数）、E2 はお金の流れ（チケットの値段と収支）。

## 2. ユーザーの決定（2026-11-14。#208 のコメント）

| | 決定 |
| --- | --- |
| 順番 | 人気・観客数・収支の土台が先（E1 人気と観客数 → E2 チケットの値段と収支 → E3 投資の振り分け → E4 オーナーの目標・評価） |
| 人気の持ち方 | **年ごとの値として保存**（世界の作成と締める処理だけが書く）。人気は試合の集計ではなく、初期値・ぶれ・宣伝の投資を含む「年ごとの状態」（能力の行と同じ型）なので、CLAUDE.md の「集計を保存する例外」は広げない |
| 人気の初期値 | **全球団50**（収容人数や勝率は使わない） |
| 収容人数の無い球団 | **ペナントの世界だけ**、標準の収容人数 `PENNANT_DEFAULT_CAPACITY`（3万人前後）で観客数を作る。実データの側は変えない。#44 の「根拠の無い数を作らない」をペナントでだけ緩めることを Wiki に明記する |
| 解任 | 別の球団で続けられる（E4 で具体化） |
| AI 球団の経営 | AI も簡単な規則でチケットの値段と投資の振り分けを決める（保存せず導く。E2・E3） |
| 支出と予算 | 人件費は仮に「契約区分ごとの定額 × 人数」（#40 で年俸の合計に置き換える）。資金の繰越は持たず、翌年の予算は前年1年の収支から（赤字は親会社が補填）。収支は保存せず導く |
| 区切り | E1・E2 を `epic/club-finance` に積んで main へ1本（ユーザーのマージ）。E3・E4 は単独で main へ |

保存するのは「決めた事実」（GM が手動にしたチケットの値段・投資の振り分け）と「状態」（人気の年ごとの値）だけ。
収入・支出・収支・予算は保存せず導く。

## 3. 計画を左右する事実（main 58076aa）

- ペナントの試合には観客数がある（#44。`domain/simulation/game_day.py` の `simulated_attendance`）。収容人数 × 入場率で、人気は効いていない。
  入場率は試合の結果とは別の乱数の列（`<試合の識別>:game-day`）なので、人気を足しても得点と打席は変わらない。
- 開発 DB の48球団のうち28球団が本拠地の収容人数を持たない（→ 標準の収容人数の決定）。実データの試合に観客数は無い。
- 球場は実データと世界で共有（読み取り専用）。E3 の「球場の改修」で `Stadium` は書き換えられない。
- スカウトの精度 `ScoutingAccuracy`（`domain/pennant/outlook.py`）は今は会議全体で1つ（E3 で球団ごとに）。
- 締める処理は最終順位・実績・受賞・日本一をもう読んでいる（人気の変化の材料はクエリを足さずに揃う）。

## 5. E1 の設計

### domain

- 新規 `domain/pennant/popularity.py`:
  - `Popularity`（1〜100 の整数、平均50）・`initial_popularity()`（全球団50）・`PENNANT_DEFAULT_CAPACITY`（標準の収容人数）
  - `PopularityFactors`（勝率・リーグ優勝・日本一・スター）・`star_power(...)`（タイトル・生え抜き・在籍年数から。上限あり）
  - `next_popularity(current, factors, *, world_seed, year, team_id)`: 平均への戻り＋勝率＋優勝＋日本一＋スター＋ぶれ。乱数の用途は `popularity-{球団}`
  - 値の行 `ClubPopularity(team_id, year, popularity)`
- `domain/repositories.py` の `PopularityRepository`（`WorldScope` 必須。`find_by_year`・`add_all`。締めた年は `AlreadyClosed`。実データには書けない）
- `simulated_attendance(..., home_popularity=None, away_popularity=None)`: 入場率の平均に人気の項（ホームが主、相手は従）を足す。**乱数を引く回数は変えず、人気50と None は今と完全に同じ値**

### application

- `PopularityReader.for_year`: 行が無い球団は初期値で補う（この機能より前の世界のため。補う場所はここ1つ）
- 世界の作成で開幕年の行を書く。締める処理は `_prepare`（ロックの外）で翌年の人気を計算し、`_commit` で書く（行の無い世界は締める年の補った値も書く）
- 進める処理: `DaySimulator` に人気と収容人数（無ければ標準で補う）を渡す
- 画面の材料（DTO）: GM ホームの「人気と観客動員」カード・球団史の人気の列・オフの結果の「人気」節。観客数の合計は参照クエリ（区分は必須）

### infrastructure

- `PennantClubPopularity`（`team` FK・`year`・`value`。(team, year) で一意。世界の列は持たず、球団のリーグで世界が決まる）・`popularities_in(scope)`・`DjangoPopularityRepository`
- 世界の削除の子テーブル・`test_world_isolation` の分類表。管理画面には出さない
- マイグレーションは表を1つ足すだけ。backfill は作らない（補いの規則は domain の1か所）

### presentation

- `build_*` に依存を足す（`test_wiring`）。テンプレート（GM ホームのカード・球団史の列・オフの結果の節）。書き込みの導線は無い。人気の無い年は「—」

### 見送り

人気だけで止める（使い道が表示だけ）／お金を使わない予算ポイント（10-12 の決定に合わない）／期中の人気の変化（進める処理が重くなる。E2 の後に実測して決める）／世界ごとの収容人数の写し（E3 で決める）。

## 6. 実測の目安（E1）

`simulate_sample --seasons 8` に人気と入場率の表を足して見る。

- 人気の平均が 45〜55 で漂流しない・標準偏差が年を追って安定する
- 入場率の全体が今の 0.83 前後、上位 0.95・下位 0.6〜0.7
- 優勝で +5〜8 点、3年続けて最下位で −10 点前後
- `measure_pages` の主要画面が悪化しない、締める処理の増加 0.1 秒未満

帯は目安で、端を詰める調整はしない（大きく外れたときだけ直す）。
