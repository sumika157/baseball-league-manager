ワークスペース（データの区切り。使い方は [ワークスペースと共有](ワークスペースと共有)）の作り、決めたこととその理由、実測値をまとめます。
層の分け方・組み立て口の一覧・URL の入口と権限の置き場所は [アーキテクチャ](アーキテクチャ)、ペナントの世界の分け方は
[ペナントモードの仕組み](ペナントモードの仕組み)、公開と運用の手順は [本番公開](本番公開) を参照してください。

ワークスペースは、全データの上に足した「持ち主がその中で全権を持つ」区切りです。親 Issue は
[#74](https://github.com/sumika157/baseball-league-manager/issues/74)、統合ブランチ `epic/workspaces` に段階 W1a〜W6 と仕上げを積みました（下の「経緯」）。
**新しい集計は書いていません。** 範囲で絞る仕組み（`WorldScope`）はペナントの世界のものを一般化し、今ある画面・集計・リポジトリを範囲つきで組み立てるだけです。

## 方式

### なぜ

ワークスペースを入れる前は、データの置き場所が1つしかありませんでした。新規登録した人は何も書けず（書けるのは管理ユーザーとチーム担当者だけ）、
書けるようにすれば全員が同じリーグを書き換えることになります。来た人が自分のチーム・選手・試合で遊べるように、全データの上に区切りを足しました。

**一番重かったのは区切りを足すことではなく、管理画面でしかできなかった登録（リーグ・チーム・球場・選手のプロフィール）をサイトの画面にすること**でした（W3）。
一般の利用者に管理画面は渡せないため、これが無いと「登録して遊べる」になりません。

### やること・やらないこと

| やること | 内容 |
| --- | --- |
| ワークスペース | 作成・名前の変更・公開/非公開・削除。1人が持てる数は3まで |
| 範囲で絞る | すべてのリポジトリと参照クエリが範囲を必須の引数で受け取る。世界の台帳もワークスペースで絞る |
| URL | `/w/<key>/...`（セッションで切り替えない。下の「URL にワークスペースを入れる」） |
| 権限 | 持ち主＝全権・編集者＝全体を編集・チーム担当＝担当チームの範囲。公開なら未ログインでも読める。**サイト側の `is_staff` の特権は廃止** |
| 招待 | 持ち主が招待リンク（トークン）を発行し、自分で渡す（メールは送らない）。期限7日 |
| 登録画面 | リーグ・チーム・球場の作成・編集・削除（空のときだけ）、選手のプロフィール |
| 見本 | 作成のときに小さい見本のリーグを生成する（既定はオン） |
| 既存データ | 全データを1つの公開ワークスペースへ移す（バックフィル）。運営者が持ち主 |

| やらないこと | 理由 |
| --- | --- |
| 古い URL（`/teams/` など）からのリダイレクト | 公開していないので、外から張られたリンクが無い。古い URL は 404 |
| 公開ワークスペースの一覧（ディレクトリ） | 荒らしや不適切な名前を全員の目に触れさせる経路になり、通報と非表示の運用が要る。公開ワークスペースは URL を知っている人だけが開ける |
| 持ち主の譲渡・アカウントの削除の画面 | 要望が出てから。それまでは運営者が管理画面で行う |
| 過去の在籍・主将の在任歴をサイトで編集 | 現在の在籍の追加・退団・移籍と主将の指名はサイトにある。過去の経歴を組み立て直す画面は量が大きい |
| ほかのワークスペースのリーグを元にしたペナントの世界 | ワークスペースをまたいでデータを写すことになり、範囲の保証が崩れる |
| メール（招待・パスワード再設定） | 当面は送らない |
| PostgreSQL への移行・スキーマの分割 | 当面は SQLite、区切りは同じ DB の中で行う（移る条件は [本番公開](本番公開#postgresql-へ移る条件)） |

### ペナントの世界との入れ子

名前は、コードでは `Workspace`、画面では「ワークスペース」です。「世界」はペナントが既に使っている（世界バー）ので、テナントの名前には使いません。
関係は入れ子で、**ワークスペース ⊃ { 実データ（1つ）, ペナントの世界（0個以上） }** です。

| 案 | 内容 | 判定 |
| --- | --- | --- |
| **A. 入れ子にし、リーグの親は1つだけ（採用）** | 実データのリーグは `League.workspace`、ペナントのリーグは `League.world` を持ち、ちょうど片方だけを持つことを CheckConstraint（`league_workspace_xor_world`）で強制する。世界は `PennantWorld.workspace` でワークスペースに属す | 同じ事実の出典が重ならない。ペナントのリーグのワークスペースは世界からたどれる |
| B. 全リーグに `workspace`、ペナントのリーグは `world` も | 実装は単純 | ペナントのリーグでワークスペースが2か所（`League.workspace` と `League.world.workspace`）になる |
| C. 実データも世界の1行にする | 最終形は一番きれい | 実データの行では世界の列（シード・開幕年・受け持つ球団）が意味を持たない。ペナントの模型と制約を作り直すことになる |
| D. 世界とテナントを別々の仕組みで二重に絞る | — | 絞り込みの層が2つになり、片方の絞り忘れがそのまま漏れになる |

A なら一意制約はむしろ単純になります。実データのリーグ名は `(workspace, name)`（`unique_workspace_league_name`）、ペナントのリーグは今までどおり `(world, name)`（`unique_world_league_name`）で、
ペナントのリーグは workspace が NULL なので前者に引っかかりません。球場名も `(workspace, name)`（`unique_workspace_stadium_name`）です。

**選手にワークスペースの列は持たせません。** 選手の範囲は在籍 → チーム → リーグから導けるので、持つと出典が2つになります。
その代わり「選手は少なくとも1つ在籍を持つ」を前提にしています（サイトでの選手の登録は必ずチームの下、ペナントの分岐とドラフトも在籍を作る）。
在籍の無い選手を作れるのは管理画面（運営者）だけで、どの範囲にも入らないため、管理画面は専用の関数（下の「範囲の例外」）で拾います。

### URL にワークスペースを入れる

セッションで切り替える方式にしなかった理由は3つです。

1. 公開したワークスペースを URL で共有する、という要件をセッションでは満たせない
2. タブを2つ開いて別々のワークスペースを見ると、POST の宛先がずれて別のワークスペースに書き込む事故が起きる
3. URL だけで権限が決まるので、テストで全 URL を機械的に回せる（下の「漏れの検査」）

## 範囲と例外

**範囲は `WorldScope(workspace_id, world_id)` です**（[domain/pennant/world.py](https://github.com/sumika157/baseball-league-manager/blob/main/myapp/domain/pennant/world.py)）。
作り方は `WorldScope.real(workspace_id)`（そのワークスペースの実データ）と `WorldScope.pennant(workspace_id, world_id)`（その世界）の2つで、どちらも引数は必須です。
ペナントの世界からワークスペースを導けるのに、ペナントの範囲にもワークスペースの id を持たせたのは、世界が球場をワークスペースと共有し、
`stadiums_in(scope)` が `scope.workspace_id` で引くためです。引数を増やしたことで、古い呼び出しは mypy ですべて落ち、直し漏れが残りませんでした（W1b）。

`scoping` の条件は、実データなら `league.workspace_id = X`、ペナントなら `league.world_id = W` です。ペナントの範囲は、組み立てるときに
世界の台帳（ワークスペースで絞ってある）で引けた世界だけから作るので、URL を書き換えてほかのワークスペースの世界を開くことはできません。
選手は在籍から導きます（`players_in(scope)` は範囲のリーグ → 球団 → 在籍 → 選手の向きで引く。仕上げ T2b で、選手の表を全部走査する相関した `Exists` から直した）。

範囲を作るのは、views の `_real_scope(request)`・`_world_scope(request, world_id)`、管理コマンドの `--workspace`・`--world`、テストの `real_scope()`・`world_scope()` だけです。
ワークスペースは URL の key から `workspace_view` が1要求に1回だけ解決し、`workspace_view` を通っていない要求で範囲を作ろうとすると `WorkspaceNotResolved` です（黙って既定のワークスペースに落とさない）。

### 範囲の例外

「範囲が無ければ全部読む」API は作りません。例外は次の3つだけで、どれも使ってよい場所を
[test_wiring.py](https://github.com/sumika157/baseball-league-manager/blob/main/myapp/tests/integration/test_wiring.py) が検査します（CLAUDE.md の規則と同じ）。

| 例外 | 読むもの | 使ってよい場所 | 検査 |
| --- | --- | --- | --- |
| `admin_real_queryset(model)` | 全ワークスペースの実データ（在籍の無い選手を含む） | `admin.py` だけ（運営向けの概況 `operator_overview()` もここ） | `AdminOnlyScopeExceptionTest` |
| ワークスペースそのものの台帳（`WorkspaceRepository`・`WorkspaceAccessQuery`・`WorkspaceListQuery`・`InvitationPreviewQuery`・`InvitationRepository`） | key・id・利用者・招待のトークンから、ワークスペースとそのメンバー・招待。中のデータ（リーグ・試合など）は読まない（担当の読み書きは、そのワークスペースの実データのチームに絞る） | 定義と `views.py`、管理画面（`admin.py`）、管理コマンド `workspace_delete`・`seed_sample_workspaces` | `WorkspaceLedgerUsersTest` |
| `real_teams_of_outer_workspace()` | 外側のワークスペースの行に相関する、実データのチーム（台帳の副問い合わせ用） | `infrastructure/queries.py` だけ | `OuterWorkspaceTeamsTest` |

台帳のうち、ワークスペースの中のデータに触れるのは2つだけです。**ワークスペースの削除**は中のデータを消しますが、そのワークスペースの範囲（`WorldScope.real(ws)`）で絞って消します。
**作成で見本のリーグを入れるとき**は、新しいワークスペースの範囲で組み立てた `WorkspaceSampleService` が書きます（範囲を作るのは組み立て口）。
世界の台帳（`WorldRepository`・`WorldSummaryQuery`）は範囲の代わりにワークスペースの id を必須で受け取ります（W1b で `test_wiring.py` の `UNSCOPED` を空にした。W6 で
1人の世界の数を全ワークスペースで数える `count_by_owner` を消し、台帳は完全にワークスペースで絞られた）。

## 不変条件と守る場所

| 不変条件 | 置き場所 | 理由 |
| --- | --- | --- |
| 1人の役割は1つ（持ち主は編集者にも担当にも入らない・編集者は担当に入らない・担当は1チーム以上） | `Workspace` 集約（`ensure_one_role_each`）。管理画面の割り当ても同じ集約の操作（`replace_editors`・`replace_team_managers`）を `WorkspaceMemberService` 経由で通す | メンバー全体を見ないと判定できない |
| チーム担当のチームは、そのワークスペースの実データのチーム | 集約の `ensure_assignments_within(team_ids)`。範囲のチームの id は保存のときに `WorkspaceRepository.save` が読んで渡す | 集約はチームを持たない |
| 1人が持てるワークスペースの数 | `WorkspaceQuota`。持っている数は `WorkspaceService.create` が数え、数える → 検査 → 保存を1つのトランザクションで行う | 数は保存しない |
| 招待は期限内（7日）に1回だけ使える。`EDIT_TEAMS` はチームが1つ以上で、どれもそのワークスペースの実データのチーム | `Invitation`（`issue`・`is_expired`・`ensure_teams_within`）。1回だけは、受諾の保存と招待の削除を1つのトランザクションにして守る | — |
| ペナントの世界が1つでもあるワークスペースは消せない | `workspace_deletion_blocker(world_count)`。リポジトリの削除・削除の確認の画面・管理画面が同じ関数を通す | 世界の削除は重いので、世界の画面で1つずつ確かめてから消す |
| 実データのリーグ名・球場名・チーム名はワークスペースの中で一意 | リーグ・球場は DB の一意制約と、保存の前の確認＋`IntegrityError` の訳しの2段（`DuplicateName`）。チーム名はリポジトリ | 範囲を変えただけ |
| チームの本拠地・所属リーグ・移籍先、試合の両チームは、同じワークスペースのもの | 範囲で絞ったリポジトリ（範囲外の id は見つからない）。本拠地は `DjangoTeamRepository.save` が球場を範囲で検査する | **漏れを止める本体**。フォームに隠しフィールドで id を載せる画面があるため |
| 選手の在籍はすべて同じワークスペースのチーム | Team 集約（移籍先は範囲内）と、管理画面の在籍・主将在任のフォームの検査（`clean()`） | 在籍経由で範囲が決まるモデルの前提で、DB では強制できない |
| 背番号・在籍・主将・外国人枠 | 変更なし（`Team` / `Game`） | 範囲の外の行は集約に入ってこない |

**`Team.managers` の扱い**: 「チーム担当」というメンバーの種別の行は作っていません。メンバーは、持ち主（`Workspace.owner`）・`WorkspaceEditor` の行・
そのワークスペースのチームの `managers` を合わせたもので、役割は保存せず毎回導きます（`WorkspaceRole.of`）。役割を列で持つと `Team.managers` と食い違いうるためです。
書き込みは `Workspace` 集約に1本化し、保存先は既存の M2M のままです。メンバーと担当は「今の状態」だけを持ち、期間は持ちません（ペナントの1軍登録と同じ判断）。

**招待のトークンは保存しません**（SHA-256 のダイジェストだけ。リンクは発行の直後に1回だけ見せる）。招待に作った人の列も持ちません（招待を出せるのは持ち主だけで、
持ち主と同じ事実の出典が2つになる）。受諾した招待は消します（残すと、メンバーである事実が2か所になる）。

## 権限

サイトの権限は、ワークスペースの役割**だけ**で決まります。役割は `WorkspaceRole`（`OWNER`・`EDITOR`・`TEAM_MANAGER`・`VIEWER`・`NONE`）で、
優先は 持ち主 > 編集者 > チーム担当 > 閲覧です。未ログインとログインした部外者は、公開なら閲覧、非公開なら関係なし（404）。
`is_staff`・`is_superuser` は役割を導く引数に入っておらず、管理画面に入る条件（superuser だけ）にしか使いません。

| `WorkspaceAccess` のメソッド | 許す人 |
| --- | --- |
| `can_view()` | 関係なし以外（公開なら誰でも、非公開ならメンバー） |
| `can_edit_all()` | 持ち主・編集者 |
| `can_edit_teams(team_ids)` | 持ち主・編集者と、渡したチームのどれか1つの担当（試合は2チームにまたがるので、どちらかの担当で可） |
| `can_set_up()` | 持ち主・編集者（登録画面はフォームだけなので、書けない人には画面ごと見せない） |
| `can_create_world()` | 持ち主・編集者（2026-10-24 決定） |
| `can_write_world(is_creator=)` | 世界の作成者で、**今も**全体の編集権を持つ人（進める・締める・編成・設定・削除）。除名された・担当に変えられた作成者は読むだけ。持ち主・編集者でも、ほかの人の世界には書けない |
| `can_delete_world(is_creator=)` | 上に加えて、ワークスペースの持ち主（ほかの人の世界も消せる。世界が残るワークスペースは消せないので、持ち主が自分で片付けられるように） |
| `can_change_settings()`・`can_manage_members()`・`can_delete()` | 持ち主だけ |

置き場所は3つに分けています。**事実**は参照クエリ `DjangoWorkspaceAccessQuery`（持ち主・公開範囲・編集者の行の有無を1クエリ、担当チームの id を2本目）、
**規則**は domain の `WorkspaceAccess`、**適用**は入口のデコレータ `workspace_view`（非公開に部外者が来たら 404・未ログインならログインへ、POST は権限を見て 403）。
`WorkspaceAccess` は渡したチームがこのワークスペースのものかを見ません。ほかのワークスペースの id を混ぜた書き込みは、範囲で絞ったリポジトリとサービスが「見つからない」として止めます。

## 上限

上限の出典は `WorkspaceQuota` の1か所です。値は環境変数から settings を経て、`presentation/views.py` の `_workspace_quota()` だけが組み立てます（domain は既定値を持たない）。
数える → 検査する → 保存するを1つのトランザクションで行い、**検査するのは画面の入口だけ**です（管理コマンドと管理画面は上限を見ない。運営者の道具のため）。

| 上限 | 環境変数（既定） | 数える単位と数え方 | 検査する入口 |
| --- | --- | --- | --- |
| 1人が持てるワークスペース | `WORKSPACE_MAX_OWNED`（3） | 持ち主ごと（`count_owned_by`） | `WorkspaceService.create` |
| ワークスペースの世界の数 | `PENNANT_MAX_WORLDS`（5） | ワークスペースごと。作成者を問わず、作成者のいない世界も数える（`WorldRepository.usage()`） | `PennantWorldService.create_world_with_schedule` |
| ワークスペースの試合の枠 | `PENNANT_MAX_GAMES`（40000） | 世界の見込みの合計。作るときに10シーズンぶんの公式戦を**予約**する（`world_game_reserve(球団数)`＝球団数 × 143 ÷ 2（切り上げ）× 10。6球団 4,290・12球団 8,580・48球団 34,320）。見込みは保存せず、世界の球団の数から毎回導く。ポストシーズンと実データの試合は数えない | 同上（分岐元を読んだ後、写す球団の数で） |

- 世界1つの形の上限（1世界10シーズン・元にするリーグ8・1回に進める150試合）は domain の定数のままです（ワークスペースの容量の話ではない）
- 既存の世界が上限を超えていても、消さない・止めない（上限は作るときだけ見る）
- 予約にしたのは、作った世界が途中で止まらないようにするためです。8リーグの世界1つか、NPB 規模（12球団）の世界4つが入ります
- 容量は試合の枠で頭打ちになります（設計の見積もりは1試合あたり約220行・約16KB だったが、仕上げ T2 の実測では8リーグ10シーズンの世界（試合 35,333）が約670MB で、1試合あたり約19KB。これで数えると、枠を使い切ったワークスペース1つで約780MB、1人（3つ）で最大約2.3GB）
- 回数制限（新規登録・ワークスペースと世界の作成）とボット対策はまだありません。公開の前に main で入れます（下の「決めたこと」の 2026-11-14 の 1）

## 見本のリーグ

ワークスペースの作成で「見本のリーグを入れる」（既定はオン）を選ぶと、1リーグ・6チーム（各25人）・球場6・約36試合（1チーム12試合）を、
新しいワークスペースの**実データ**として作成と同じトランザクションの中で入れます。順位表・ランキング・ボックススコアが空にならない最小限の量で、
試合はスコアブックで編集できます。

| 案 | 判定 |
| --- | --- |
| **生成（採用）**: 固定の架空の名前と、key と年から作る乱数で選手と能力を引き、シミュレーションのエンジンで試合を回し、集約とリポジトリで保存する | スキーマや成績の項目が増えても自動で追従する。本番に numpy は要らない |
| テンプレートの複製: 見本用のワークスペースを1つ持ち、id を振り直して約10の表を写す | 項目を増やすたびに複製も直す必要があり、直し漏れはその項目が静かに欠ける形で出る |
| 今の投入コマンドの流用 | numpy が開発用の依存にしか無い。3,480試合を作ると約70秒 |

- domain の `domain/sample/` が中身を作ります（Django を import しない）。乱数は key と年から作り（`random()` だけ）、保存後の id に依らない。
  年は試合がすべて今日より前になる年（`sample_year`）。日程は `generate_schedule` で、連戦の標準の長さを2にしています（3連戦では5つの相手に2〜3試合ずつを分けられない）
- 保存は `WorkspaceSampleService.seed(key=)`（集約とリポジトリだけを通す。背番号の一意性・支配下の上限・打席と明細の照合を素通りしない）。
  `WorkspaceService.create(with_sample_league=)` は、組み立て口から渡された関数を作成のトランザクションの中で呼びます
- 能力と「見本かどうか」は保存しません。後から見本を入れる・見本だけを消す導線は無く、要らなくなったらワークスペースごと作り直します
- 作成1回は約1.1秒で、そのほぼ全部が書き込みのロックの中です（下の「性能の代表値」）。ロックが2秒を超えるようになったら（見本を大きくするなど）、作成と見本を分けます
- 画面の呼び方は「見本の**リーグ**」で、運営者がトップから案内する「見本の**ワークスペース**」（`SAMPLE_WORKSPACE_KEY`。既存データを移したもの）とは別物です

## データとマイグレーション

main の `0073_pennant_staff` の後ろに続く5本です（epic の間は main を取り込むたびに付け直し、main に入るときの番号がこれです）。

| マイグレーション | 種類 | 内容 |
| --- | --- | --- |
| `0074_workspace` | スキーマ | `Workspace`（`key` は一意の10文字の英小文字と数字・`name`・`owner`（PROTECT）・`visibility`・`created_at`）と `WorkspaceEditor`（workspace と user の組で一意）。`League`・`Stadium`・`PennantWorld` に `workspace` を **null 可・PROTECT** で足す |
| `0075_backfill_default_workspace` | データ移行 | 既存のリーグ・球場・世界を、既定のワークスペース1つに付ける（下） |
| `0076_workspace_constraints` | スキーマ | `Stadium.workspace`・`PennantWorld.workspace` を null 不可に。一意制約を `(workspace, name)` に替え、`league_workspace_xor_world` を足す |
| `0077_team_managers_help_text` | 文言だけ | `Team.managers` の `help_text` を W2 の後の権限に合わせる |
| `0078_workspace_invitation` | スキーマ | `WorkspaceInvitation`（`token_digest` は一意・役割・チームの M2M・`expires_at`） |

**0075（バックフィル）** は次のとおりです。

- 既にワークスペースが1つでもあれば何もしない。リーグ・球場・世界のどれも無い DB でも何もしない（最初の1つは管理画面で作る）
- ワークスペースを1つ作る（名前「既定のワークスペース」・公開）。持ち主は `is_active` な superuser の最小 id、いなければ staff の最小 id。
  どちらもいなければ `RuntimeError`（「先に createsuperuser を実行してください」と本番の復旧コマンドを含む日本語）で止まる
- 持ち主以外の `is_active` な staff・superuser を `WorkspaceEditor` にする（それまで全権を持っていた人が権限を失わないため）。staff でない人は編集者にしない。`Team.managers` には触れない
- `world IS NULL` のリーグ・全球場・全世界をこのワークスペースに付ける（ペナントのリーグは世界からたどるので付けない）
- 逆方向は何もしない（`noop`）。消す形にすると、戻して再び当てたときに、後から作られたワークスペースを消したり、非公開のものを1つの公開ワークスペースに混ぜたりする
- 書き換えるのはリーグ・球場・世界の数十行だけで、試合と明細には触れません（範囲はリーグからたどる）

本番で止まったときの復旧は [本番公開](本番公開#ワークスペースのマイグレーションが止まったとき)、テストは
[test_workspace_migration.py](https://github.com/sumika157/baseball-league-manager/blob/main/myapp/tests/integration/test_workspace_migration.py)・
[test_workspace_constraints.py](https://github.com/sumika157/baseball-league-manager/blob/main/myapp/tests/integration/test_workspace_constraints.py) です。

**ワークスペースの削除**（`WorkspaceRepository.delete`）は、ペナントの世界の削除と同じく、子の表から順に範囲で絞った削除を発行します（Django の CASCADE の collector には任せない。
数十万行を Python に集めることになるため。`workspace` の外部キーが PROTECT なのもこのため）。消す前に、ほかのワークスペースにも在籍がある選手と、
ほかのワークスペースの行がこのワークスペースの行を外せない形で指している**迷子の参照**（管理画面の直書きでしか起きない）を検査し、あれば何も消さずに理由を出します。
本拠地・世界の受け持つ球団・編成の抑えの迷子は空にして外します（2026-10-25 ユーザー決定）。見る参照は手で並べず、全モデルのメタ情報から導きます。

## 漏れの検査

ワークスペースをまたぐ漏れは、テストの表で網羅的に検査します。**表に載っていないものを足すとテストが落ちる**形にして、検査の付け忘れを防いでいます。

| テスト | 検査すること |
| --- | --- |
| [test_workspace_isolation.py](https://github.com/sumika157/baseball-league-manager/blob/main/myapp/tests/integration/test_workspace_isolation.py)（中心） | (1) `repositories`・`queries` の `Django*` をモジュールから列挙し、すべてを検査の表 `CHECKS` で検査する（A の範囲で B の行を読めない・書けない・消せない。B の範囲では読めること（空振りの防止）も見る）。(2) URL の解決器から `/w/<key>/` の下の全パターンを列挙し、分類表 `URL_TABLE` で検査する（A の key の下で B の id は 404・A の画面に B の目印が出ない・非公開の B に部外者が入れない・全 POST を他人のワークスペースに送っても DB が変わらない・A の画面のリンクが A の中かワークスペースの外だけ） |
| [test_cross_workspace_ids.py](https://github.com/sumika157/baseball-league-manager/blob/main/myapp/tests/integration/test_cross_workspace_ids.py) | フォームと JSON に他所の id を混ぜる経路（試合の登録の `home_team`・スコアブック API の選手 id・チームの球場・移籍先・担当の割り当て・昇格と FA 宣言・戦力分析の `?team=` など）がすべて拒まれ、何も保存されない |

| [test_wiring.py](https://github.com/sumika157/baseball-league-manager/blob/main/myapp/tests/integration/test_wiring.py) | 組み立て口の分類（実データとペナントの両方・実データ専用・ペナント専用・台帳だけ・ワークスペースの台帳・メンバー）と、範囲が必須であること。範囲の例外を使ってよい場所。サービスから届く台帳・範囲がすべて同じワークスペースか（`LedgersAreScopedToTheWorkspaceTest`） |

| [test_workspace_delete.py](https://github.com/sumika157/baseball-league-manager/blob/main/myapp/tests/integration/test_workspace_delete.py) | B を消すと B の行がすべて消え、ほかは1行も変わらない（全表の比較）。迷子の参照・在籍がまたがる選手・世界が残る場合は何も消さない |
| [test_player_scope_plan.py](https://github.com/sumika157/baseball-league-manager/blob/main/myapp/tests/integration/test_player_scope_plan.py) | 選手を範囲で絞る SQL に、選手の表の全部走査（`SCAN`）が無いこと（`EXPLAIN QUERY PLAN`。仕上げ T2b） |

モデルの分類（`CLASSIFICATION`）:

| 分類 | モデル | ワークスペースへの道 |
| --- | --- | --- |
| 全体 | `Workspace` | 自身 |
| メンバー | `WorkspaceEditor`・`WorkspaceInvitation` | `workspace` |
| ワークスペース直属 | `PennantWorld`・`Stadium` | `workspace` |
| 2経路 | `League` | 実データは `workspace`、ペナントは `world__workspace`（`LEAGUE_ROUTES`。CheckConstraint で片方だけ） |
| リーグ経由 | `Team`・`PlayerStint`・`Captaincy`・ペナントの日程・編成の指名など | `…__league` |
| 選手の在籍経由 | `Player`・`PennantPlayerRatings`・`PlayerFreeAgentDeclaration`・`PennantDraftLottery` | `…stints__team__league` |
| 試合経由 | `Game` と明細 | 試合 → チーム → リーグ |
| 世界経由 | ドラフト会議の記録 | `world` |

`Team.managers` の中間表は `get_models()` に出ないので表に載りません（担当の読み書きは台帳が実データのチームに絞る）。

**変異の確かめ**: 各段階で、範囲の条件を外す・全件にするなどの変異を入れて、検査が落ちることを確かめています（例: 実データの条件を戻すと40件・世界の台帳を全件にすると30件・
球場の条件を全件にすると19件が落ちる（W1b）。数は段階ごとの記録）。空振り（範囲の検査ではない理由で弾かれていて、範囲の検査を外しても通る）を仕上げ T3 で埋めました。

## 性能の代表値

`measure_pages --workspace <key> [--as <利用者>] [--world <id>]` で測ります（SQL の時間ではなく応答時間とクエリ数を見る。[アーキテクチャ](アーキテクチャ)）。

| 項目 | 値 |
| --- | --- |
| 権限の解決 | 1要求に1回。未ログイン・持ち主・編集者は1クエリ、担当・ログインした部外者は2クエリ。ログインした人はヘッダーの切り替えの一覧で全画面 +1 |
| 範囲を入れた前後 | 実データの画面は W1b でクエリが全画面ちょうど +1（ワークスペースを引く1本）、応答は揺れの範囲。W3・W4 の前後も未ログインは全画面で同じ |
| 見本ありの作成 | 約1.1秒・337クエリ。**書き込みのロックも約1.1秒**（作成のトランザクションの中で生成・シミュレーション・保存。SQL は約35ms）。見本なしは 3ms・9クエリ（W5） |
| 見本1つの大きさ | 約9,300行・約0.7MB（索引を含む。1行あたり約76B）。大きいのは進塁・打席の表 |
| 見本のワークスペースの画面 | どれも100ms 未満（いちばん重いのは選手一覧の約70ms）。クエリ数は既定のワークスペースと同じ |
| 見本つきを200個作った DB（+184万行・+137.5MB。仕上げ T2） | クエリ数は全画面で前後同じ。打席・進塁・明細の表は全部走査していない。選手の表（3.5万行）を範囲の `Exists` で全部走査する4か所が選手の数に比例して遅くなったので、T2b で範囲のリーグ → 球団 → 在籍 → 選手の向きに直し、200個前との差を −9〜0% にした（管理画面の概況の全選手の数だけは意味のうちで走査が残る） |
| 200個ある状態での作成・削除 | 見本ありの作成 1,056ms（ロック 1,053ms）。見本のワークスペースの削除 96ms（T2b の後）。管理画面の概況・一覧 40ms・44ms |
| ワークスペースの削除（既定のワークスペース。約87万行） | 2.8秒（うち消す前の検査が約1秒） |
| 8リーグ10シーズンの世界の削除 | **25.8秒・ロック1本で 25.8秒**（世界1つで約670MB・打席 274万行。仕上げ T2）。SQLite の待ちの上限（20秒）より長いので、削除の間にほかの人が書くと `database is locked` で失敗する。#98 の縮小版で小分けにする（下の「決めたこと」） |
| バックアップ（`backup_db`）と gzip | 205MB の DB で `backup_db` 約4.3秒・`gzip -6` 約6.2秒、圧縮比は中身によらず約 0.32。gzip なら R2 に30日残して無料枠（10GB）に収まるのは DB 約1GB まで（圧縮しなければ約330MB） |

SQLite の書き込みは DB 全体で1本しか通りません。見本の作成やペナントを進めるあいだ、ほかの全ユーザーの書き込みが待ちます（待ちの上限 20秒。
書き込みとロックの考え方は [ペナントモードの仕組み](ペナントモードの仕組み#書き込みとロック)）。

## 残した拡張

各段階のレビューで残した軽微なもののうち、内部の作りに関わるものです（仕上げ T3 で埋めた漏れの検査の穴は除く）。

**テストだけでは埋まらないもの**（コードを変えるので仕上げ T3 では行わなかった）:

- ペナントの条件に `world__workspace_id` を足す二重の防御（今はペナントの範囲を台帳で引けた世界だけから作ることで守る。測ってから決める）
- 管理画面のオートコンプリート（在籍のチーム・チームの本拠地）の候補を同じワークスペースに絞る（今は保存のときに弾く）
- 管理画面の編集者・担当のインラインが集約の検査を通らない（仕上げ T3 の記録で残したものに挙げた。W4 T6 で管理画面の割り当ては `WorkspaceMemberService` に通したので、まだ残る経路があるかは次にこのインラインを触るときに確かめる）

**作りの軽微**:

- `AtomicBlock` を `application/pennant_season.py` から import している（ペナントと無関係な登録・ワークスペースのサービスがペナントのモジュールに依存する。中立な置き場所へ移す余地）
- `WorkspaceQuota` が `pennant.world`（`WorldUsage`・`world_game_reserve`）を知る向き
- 世界の一覧の見込みは `list_teams_by_league()`、作成の検査は `load_source()` の名簿で球団を数える（どちらも実データのリーグの今の球団で、今は一致する）
- 持ち主の譲渡（持ち主の列）は管理画面のフォームが書き、サービスを通さない（`Workspace.hand_over` は検査の見立てだけ）
- 期限切れの招待は、そのワークスペースで次に発行するまで残る（使えず一覧にも出ない）
- 役割の変更の入力の誤りで、画面の上の案内と欄のエラーの両方を出す
- 招待の受諾と設定の画面のクエリ数はテストで固定していない
- 見本: 「空でない」を `InvalidWorkspace` で投げる（作成以外から `seed` を呼ぶ導線を足すなら専用の例外に）／「空か」で球場を見ない（`StadiumRepository` に一覧が無い）／
  スタミナの水準（62・38・10）が `samples.spread_club` のリテラルと同じ値／`veteran.py` が `pennant.draft.DraftRoute` を使う（パッケージの相互依存）／
  `seed_virtual_players` の経路の検査が `draw_veteran` の中と二重／クエリ数を減らすならプロフィールつきの加入（チームの保存を球団ごとに3回 → 2回）
- 範囲の条件: `ratings_in`・`draft_lotteries_in`・`declarations_in` は `players_in(scope).values("id")` を挟むので副問い合わせが1段深い（出典を `players_in` の1か所に保つ方を取った）
- 登録: 数えてから消すまでの間に別の要求が在籍や試合を書くと、空でないものを消しうる（管理画面では `NotDeletable` で 500。データは消えない。SQLite は書き込みが直列なので実害は小さい。外部キーを PROTECT にして訳す案は、PostgreSQL に移るときに見直す）
- 管理画面の `_get_validation_exclusions` は Django の非公開 API（Django を上げるときに確かめる）
- `test_workspace_isolation.py`（約2,370行）と `test_wiring.py`（約1,520行）が目安の600行を超えている（分割は #343 の範囲）
- 未ログインの人には、無い key（404）とある非公開の key（ログインへ）で応答が分かれる（key は推測しにくいので、ログインへ送る便利さを取った）

**要望が出たら**: メンバーが自分で抜ける・招待の再表示・編集者による招待・選手の削除・過去の在籍と主将の在任歴の編集・後から見本を入れる／見本だけを消す。
