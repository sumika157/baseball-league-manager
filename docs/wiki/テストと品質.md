テストの置き場所と実行方法、カバレッジ、Lint と型チェックをまとめます。

## テスト

```bash
# フルテスト（WSL からは make test が同じ2つを流す）
docker compose exec web python manage.py test myapp.tests.domain myapp.tests.integration --parallel 4
docker compose exec web python manage.py test myapp.tests.e2e
```

domain + integration は並列で、e2e は直列で流します（e2e は並列にすると Chromium が重なってかえって遅くなる）。
`python manage.py test` だけでも全部流れますが、直列なので約4分かかります。

テストは層ごとのディレクトリに分かれています。

| ディレクトリ | 内容 | DB |
| --- | --- | --- |
| `tests/domain/` | 業務ルール（指標計算・投球回の変換・背番号の一意性・規定打席など） | 不要 |
| `tests/integration/` | リポジトリの往復・画面の動作・権限・テンプレートの検査・保存 API | 必要 |
| `tests/e2e/` | Playwright による実ブラウザでのE2Eスモークテスト（React 画面の操作を含む） | 必要 |

> E2E は React 画面を実ブラウザで操作するため、**実行前にビルド成果物が必要**です
> （`make frontend-build`、または `make up` で watch ビルドが動いていれば常に最新です）。

各ディレクトリの中は**対象ごとにファイルを分けます**（`test_players.py`・`test_games.py`・
`test_admin_validation.py` など）。結合テストの共通の土台は
[tests/integration/base.py](https://github.com/sumika157/baseball-league-manager/blob/main/myapp/tests/integration/base.py) の `BaseCase` で、
リーグ・球場・チーム2つと組み立て済みのサービスを用意します。

ドメイン層のテストは Django の設定すら読み込まずに実行できます。

```bash
docker compose exec -e DJANGO_SETTINGS_MODULE= web \
  python -m unittest discover -s myapp/tests/domain -t .
```

ディレクトリ単位で実行する場合:

```bash
docker compose exec web python manage.py test myapp.tests.integration
docker compose exec web python manage.py test myapp.tests.e2e
```

### 所要時間と遅いテストの探し方

フルテストは約2分です（domain と integration 約2,700件を4本の並列で約85秒、e2e 約13秒。直列なら約235秒。2026-10 の実測）。

並列数は `make test PARALLEL=8` のように変えられます（既定は 4。8本なら domain と integration が約55秒）。**`auto`（CPU の数）にはしません。**
手元のコンテナは複数のエージェントが同時にテストを流すことがあり、CPU 20 個の機械で `auto`（20本）にしたところ、
他のテストと重なって（コンテナのメモリは約8GB）Docker のエンジンが応答しなくなりました。CI は専用のランナーなので `auto` で流しています。

並列のとき、子プロセスで落ちたテストのトレースバックは `tblib`（`requirements-dev.txt`）が親へ渡します。
イメージが古く `tblib` が無いと、1件でも落ちると `TypeError: cannot pickle 'traceback' object` で実行全体が止まり、
どれが落ちたか分かりません（`docker compose build --no-cache` でイメージを作り直し、WSL 側から `docker compose up -d` でコンテナを作り直す。急ぐときは `--parallel` を外して直列で流せば、どれが落ちたか出ます）。

時間の上限を見るテスト（シーズンの日程・オフの10年の計算）は、壁時計ではなくそのプロセスの CPU 時間（`time.process_time()`）で測ります。
並列実行や他の負荷で待たされた時間が入らないようにするためです。
所要時間の長いテストクラスは、テストランナー（[myapp/tests/runner.py](https://github.com/sumika157/baseball-league-manager/blob/main/myapp/tests/runner.py)）に足した
`--slowest-classes` で上から表示できます。

```bash
docker compose exec web python manage.py test --slowest-classes 20
```

Python 標準の `--durations` はテストメソッド単位で、`setUpTestData`（クラスで1回の準備）の時間が入らないため、
クラス単位で測ります。並列実行（`--parallel`）のときは表示されません。

速さのために、テストでは次のようにしています。

- テストの間だけ、パスワードのハッシュを速いもの（MD5）にしています（既定の PBKDF2 は1回約0.1秒）。本番の設定は変えていません。
- 重い準備（選手の登録・世界の分岐・シーズンを回す）はクラスで1回（`setUpTestData`）にしています。`BaseCase` と、世界を使う `WorldCase` もこの形です。
- 選手を何人も登録するときは `tests/helpers.py` の `register_players` でまとめます。集約の検査（背番号・支配下の上限）は
  サービスから1人ずつ登録するのと同じですが、ロスターの読み込みと保存が1回で済みます。

### カバレッジ

```bash
make coverage                            # フルスイート
make coverage t=myapp.tests.integration  # 範囲を絞る
```

計測対象は `myapp/` と `config/`（テストコードとマイグレーションは除く）で、設定は
[pyproject.toml](https://github.com/sumika157/baseball-league-manager/blob/main/pyproject.toml) の `[tool.coverage.*]` にあります。結果は通っていない行のある
ファイルだけを、カバレッジの低い順に未実行の行番号つきで表示します。計測データはコンテナの
`/tmp` に書くので、作業ツリーには何も残りません。テストが1件でも失敗すると表示まで進まないので、
worktree で E2E を含めて回すときは先に `make frontend-build WT=<名前>` を実行してください。

管理コマンドや起動口（`asgi.py`・`wsgi.py`）も**あえて除外せずに数えています**（除外すると
「テストが無い」ことが数字から見えなくなるため）。テストの無いファイルは 0% で表の先頭に並びます。

## CI（GitHub Actions）

[`.github/workflows/ci.yml`](https://github.com/sumika157/baseball-league-manager/blob/main/.github/workflows/ci.yml) が、
次のときに流れます。

| きっかけ | 流れるもの |
| --- | --- |
| Pull Request（宛先は main でも epic でも）・main と `epic/` の統合ブランチへの push | `test` ジョブ（下記）。push で流すのは、続けてマージした PR の組み合わせで先端が壊れていないかを確かめるため |
| main への push | `test` が通ったあと、`publish` ジョブが本番イメージを GHCR に置く |
| 手動実行（Actions タブの「Run workflow」） | `test` と `publish`。ブランチで試せるが、付くタグはコミットのハッシュだけで `latest` は動かない |

**テストに影響しないファイルだけの変更では、`test` をスキップします。** ワークフローは毎回動き、最初の `changes` ジョブが
変更されたファイルを `UNAFFECTED_BY_TESTS` の一覧（`docs/`・Markdown・`.claude/`・`infra/`・`scripts/` の `.ps1` と `.sh` など）と見比べます。
1つでも一覧から外れるファイルがあれば `test` が動きます。テストが読むファイル（`Makefile` など）は一覧に入れていません。
手元の手順も同じ一覧に従い、該当するときは push 前のフルテストを省きます。
docs だけの変更が main に入ったときは `publish` も動きません（`test` がスキップされ、それに続く `publish` もスキップされるため）。

トリガーの `paths-ignore` で流さない形にしていないのは、必須のチェック（下記）の `test` が報告されないと、
自動マージがいつまでも待つためです。スキップされたジョブは、必須のチェックとしては成功扱いになります。

### マージ（自動マージ）

main と `epic/` の統合ブランチには、リポジトリのルールセットで**必須のチェック `test`** を掛けています。
Claude は PR を作ると自動マージを予約し（`gh pr merge --auto --squash`）、`test` が通った時点でスカッシュマージされます（#244）。
次の PR だけは予約せず、ユーザーがマージします: `infra/` に触れる・epic を main に入れる・データの全再生成や既存データを書き換えるマイグレーションを含む
（規則の出典は [CLAUDE.md](https://github.com/sumika157/baseball-league-manager/blob/main/CLAUDE.md)「ブランチとコミット」）。
画面を変える PR は、一般公開までは自動です（PR 本文にプレビューの URL を書き、マージ後でも触って確かめられるようにする）。

Dependabot の PR は自動マージしていません。ワークフローの中で予約すると、マージが Actions の `GITHUB_TOKEN` で行われ、
その push では main の CI も `publish` も動かないためです（GitHub の仕様）。

`test` ジョブは開発用の `Dockerfile` をビルドし（依存と Playwright のレイヤーは Actions のキャッシュで使い回す）、
そのイメージの中でローカルの `make lint`・`make test` と同じものを順に流します。

1. `ruff check .`・`ruff format --check .`・`mypy .`
2. React のビルドと TypeScript の型検査（`node:22-bookworm-slim` で `npm ci && npm run build && npm run typecheck`）
3. フルテスト。domain + integration を `--parallel auto`（ランナーの CPU の数だけ並列）、続けて e2e を直列（React のビルドの後）

これとは別に [`.github/workflows/terraform.yml`](https://github.com/sumika157/baseball-league-manager/blob/main/.github/workflows/terraform.yml) が、
`infra/` が変わった PR と push でだけ、Terraform を検査します（`hashicorp/terraform` のコンテナで `fmt -check -recursive`、`init -backend=false` と `validate`）。
state や認証情報には触れず、`apply` は CI から流しません。手元では `make tf ARGS="fmt -recursive"` などで同じ検査ができます（[本番公開](本番公開)）。

`publish` ジョブは `Dockerfile.prod` をビルドして `ghcr.io/sumika157/baseball-league-manager` に push します
（タグはコミットのハッシュと、main のときだけ `latest`。認証は `GITHUB_TOKEN` で、個人のトークンは置いていません）。
`test` が落ちたコミットからは push しません。デプロイの手順は [本番公開](本番公開) です。

- **落ちたとき**: PR の「Checks」か、リポジトリの Actions タブで該当の実行を開き、赤くなった step のログを見る。
  手元で再現するときは、同じコマンドを `make lint`・`make test`（e2e の前に `make frontend-build`）で流す。
- PR に新しく push すると、その PR の古い実行は止まります。main と epic への push の実行は止めません。
- epic 向けの PR で CI が走るのは、統合ブランチに main を取り込んで `ci.yml` が入ってからです（PR のときは、PR を宛先に合わせた状態のワークフローが使われるため）。
- アクションの版はコミットのハッシュで固定してあります（コメントに版）。更新するときはハッシュを実際に引き直します。

## Lint / 型チェック

```bash
# Lint（静的解析）
docker compose exec web ruff check .

# フォーマット
docker compose exec web ruff format .

# 型チェック（django-stubs 併用）
docker compose exec web mypy .

# フロントエンドの型チェック（TypeScript）
make frontend-check
```

`requirements.txt` を変更した場合と同様、これらのツールを追加・更新した場合も
`requirements-dev.txt` の変更後にイメージの再ビルドが必要です。

### エディタ上の型チェック（Pylance）

**型チェックのゲートは mypy です。**Pylance（pyright）は編集中の補助という位置づけで、
水準を `pyproject.toml` の `[tool.pyright]` に固定しています（`typeCheckingMode = "standard"`）。

これを書いていないと、各自の VS Code ユーザー設定 `python.analysis.typeCheckingMode` が効いてしまい、
`strict` にしている人の画面だけ `reportMissingParameterType` などの警告が大量に出ます
（mypy は `disallow_untyped_defs` を有効にしていないため、CI もコミット前チェックも通るのに、です）。
`[tool.pyright]` がある限り `settings.json` の `python.analysis.*` は無視されるため、
このリポジトリでは全員が同じ水準になります。

水準を上げたい場合は `pyproject.toml` を変更してください（各自の VS Code 設定ではなく）。
