画面を確認するには、ある程度の量のデータが必要です。架空の選手と1シーズンぶんの試合を投入するコマンドと、生成の仕組みをまとめます。

画面を確認するには、ある程度の量のデータが必要です。順位表・タイトル・
月別成績・ボックススコアは、試合が無いと空のままになります。

```bash
# 各チームの支配下を60人台・育成を10〜30人まで架空の選手で埋める（既存の選手は残る。流し直しても帯を超えない）
docker compose exec web python manage.py seed_virtual_players --seed 42

# 1シーズンぶんの試合と成績を入れる（1チーム145試合）
docker compose exec web python manage.py seed_virtual_games --seed 42

# 作り直す場合（そのシーズンの既存の試合を消してから入れる）
docker compose exec web python manage.py seed_virtual_games --seed 42 --replace

# 投入したら主要画面の応答を実測する（件数が増えて初めて出る遅さがあるため）
docker compose exec web python manage.py measure_pages

# 既存の試合に守備成績（打席から導く）を付ける・導き直す（migrate の後に流す）
docker compose exec web python manage.py rebuild_fielding_lines

# 試合シミュレーションエンジン（ペナントモードの土台）を回して水準を確かめる（DB には書かない）
docker compose exec web python manage.py simulate_sample --games 2000 --seed 1
docker compose exec web python manage.py simulate_sample --season --seed 1
```

`simulate_sample` は `myapp/domain/simulation/` の確認と調整の道具です。能力50の2球団で N 試合を回して
1試合ぶんのボックススコアを文字で出し、水準の表を NPB の目標帯と並べて出します。`--season` は能力を
散らした12球団（2リーグ6球団ずつ）で、ペナントと同じ日程（1球団143試合・全858試合）の1シーズンを回し、
首位打者・本塁打王などのタイトルの水準も出します。`--from-real-leagues <リーグの id …>` は、実データの成績から
推定した能力で1シーズンを回し、元の水準と並べます。
`--from-real-leagues` に `--seasons N` を足すと、シーズンの間にオフ（成長・衰え・引退・戦力外・自動ドラフト。
`plan_offseason`）をメモリで回して N シーズンを続け、シーズンごとの水準・年齢と能力の分布・入れ替わり・
錨の補正（毎年、能力の分布を元の水準に戻す補正がどれだけ効いたか）を出します（DB には書きません）。

```bash
docker compose exec web python manage.py simulate_sample --from-real-leagues 1 2 --seasons 3
```

ペナントの世界を「1シーズン進める → 締める」で何年か回す（実データには触れない。世界の作成・進行・オフは各コマンド）:

```bash
docker compose exec web python manage.py pennant_create --name "検証" --league 1 --league 2 --managed-team 1 --year 2026 --seed 5
docker compose exec web python manage.py pennant_advance --world 1 --to season-end
docker compose exec web python manage.py pennant_close_season --world 1   # 引退・戦力外・新人の人数と所要時間を出す
```

同じ `--seed` なら同じ結果になります。`seed_virtual_games` はまだこのエンジンを使っていません。

### 投入する試合の開始・終了の時刻と観客数

`seed_virtual_games` が投入する試合には、開始・終了の時刻と観客数が付きます（ペナントのシミュレーションと同じ
`domain/simulation/game_day.py` のモデル。決め方は [ペナントモードの仕組み](ペナントモードの仕組み) の「時刻と観客数」）。
乱数は打席を進める乱数とは別の列（`--seed` から派生）なので、同じ `--seed` で得点・打席は変わりません。
観客数は球団の本拠地の収容人数から作り、本拠地が無い・収容人数が未設定の球団のホーム試合は空のままです。

**付くのは、これから投入する試合だけです。** 既に入っている試合には付きません（実データの試合に推定値を書き込むと
記録の捏造になるため、後から埋めるコマンドも作りません）。値が欲しければ `--replace` で作り直します。

`seed_virtual_players` の名前・出身・学校の生成は domain の `virtual_players/`（`generator.py`）を通ります
（ペナントのオフの自動ドラフトと同じ関数を共有）。乱数を `random.Random(--seed)` に切り替えたため、
同じ `--seed` でも、以前の版とは別の名前が作られます（開発用 DB は作り直さないので実害はありません）。

これらの投入・補正コマンドと `measure_pages` が対象にするのは**実データだけ**です。ペナントの世界
（[ペナントモードの仕組み](ペナントモードの仕組み)の「世界の分け方」）の球団・選手・試合には触れません
（`--replace` もペナントの試合を消しません）。

## 打席の記録ができる前のデータがあるとき（main に入れた後の手順）

打席の記録が無い古い試合（打席を記録する前に入れた試合）は、新しく加わった列（得点・三振・
失点・守備成績など）が**未記録なのに 0 と表示されます**。スコアブック画面で直すにも、
打席を入力し直さないと保存できません（打席が空のまま保存すると成績が消えるため、
サーバーが弾きます）。仮想データは打席つきで作り直します。

```bash
# 1. マイグレーションを流す
docker compose exec web python manage.py migrate

# 2. シーズンごとに作り直す（そのシーズンの既存の試合を消して、打席つきで入れ直す）
docker compose exec web python manage.py seed_virtual_games --seed 42 --replace --year 2026

# 3. 守備成績を打席から導く
docker compose exec web python manage.py rebuild_fielding_lines
```

作り直す前に `db.sqlite3` をコピーしてバックアップを取ってください（試合を消すため戻せません）。

どちらのコマンドも ORM に直接書き込むため、集約の検査を通りません。代わりに集約と同じ
規則を自前で守ります（在籍中の背番号の重複禁止、リーグの外国人枠）。架空選手の
約12%を外国人にしますが、1球団5人（`generator.FOREIGN_PLAYERS_PER_TEAM_MAX`。育成も数える）を超えるぶんは日本人選手にします
（協約は外国人の保有を縛らないので、これは生成の目安です。1軍に置けるのは4人まで）。試合ごとの外国人は、リーグの外国人枠
（協約第82条の2 の計4人・うち投手3人・野手3人。投手か野手かは登録位置で数える）を**先発投手を先に決めてから打順を組んで**守り、
組み立てた試合でもスコアブックの保存と同じ検査（`ForeignPlayerRules.ensure_within`）を通します。外国人の先発が投げる日に枠が足りなければ、
外国人の野手を控えと入れ替えます（打順を先に組むと、外国人の先発の代わりに毎回同じ投手が先発し、
年70試合に先発する投手が出ていました）。投入結果がこれらの規則と
スコアブックの辻褄（打点の合計が得点を超えない、被安打＝相手の安打など）を満たすことは
`tests/integration/test_seed_virtual_*.py` で確かめています。

**投げる手**は、捕手は全員右投げ、内野手の左投げは7%（一塁手として使う前提の少数）、外野手と投手は25%です。
NPB では捕・二・三・遊に左投げがほぼいないため、`seed_virtual_games` の守備位置の割り振りと
ペナントの AI のスタメン・代打は、**左投げをこの4つの守備位置に就かせません**
（規則の出典は `FieldingPosition.allows_left_handed_thrower`）。枠が埋まらないときは
規則を破らず、右投げの別の選手（控えを含む）を回します。投げる手の合う選手が1人もいないときだけ、
試合が組めなくなるのを避けて規則を曲げます（seed は先発に8つの守備位置と指名打者1人を重複なく揃えるため、控えの右投げを先発に回し、それも無いときだけ曲げます）。手入力の試合の記録と GM の手動の編成には制限をかけません。

`seed_virtual_games` は**打席を1つずつ組み立て、成績はそこから導出します。**
選手の能力だけを確率分布から引き（numpy）、あとは半回を3アウトまで進めるだけです。

| 対象 | 分布 |
| --- | --- |
| 打者の能力 | 多変量正規分布（打率・長打力・四球率には相関がある） |
| 投手の能力 | 対数正規分布（失点の倍率なので正の値だけ） |
| 1打席の結果 | 能力から作った確率での逐次判定 |

**得点・イニングスコア・勝敗・引分は引きません。** 打席を積み上げた結果として決まります。
延長は12回まで行い、決着しなければ引分。ホームがリードしていれば9回裏は行わず、
逆転すればその時点で終わります（サヨナラ）。以前は完成したボックススコアを乱数で作って
いたため、打点の合計を得点に一致させる・投手の被安打を相手打線の安打から逆算する、
といった配分の工夫が必要でしたが、**打席を先に作れば整合は自動的に取れます**
（打点は還った走者を数えるだけ、被安打は投げた打席の安打を数えるだけ）。

出てくる数字はNPBの水準に合わせてあります（投入の最後に実測値が表示されます。
下の表は `--seed 42`。シードを変えると1試合平均得点は 3.8〜3.9 台でばらつきます）。

| 指標 | 投入されるデータ | NPBの目安 |
| --- | --- | --- |
| 1試合平均得点 | 3.83 | 3.8〜4.0 |
| リーグ打率 | .251 | .250〜.260 |
| リーグ防御率 | 3.54 | 3.40〜3.60 |
| K/9 / BB/9 | 7.45 / 2.74 | 7.0〜8.0 / 2.5〜3.0 |
| HR/9 / 1試合の失策 | 0.87 / 1.26 | 0.9前後 / 1.2前後 |
| 首位打者 / 本塁打王 | .350前後 / 30〜40本 | 同程度 |
| 先発の投球回 | 180回前後 | 同程度 |
| セーブ / ホールドの最多 | 40前後 / 40前後 | 35〜45 / 35〜45 |
| 救援の登板の最多 / 1チーム1試合の登板投手 | 70〜80 / 4.0人 | 60〜70 / 4人前後 |

3,480試合の投入で打席が約27万件、進塁が約35万件になります（生成は70秒ほど）。

**継投には勝ちパターンがあります。** 救援の序列（能力順）の1位が抑え、2位がセットアッパーで、
**回の頭から1イニングを任されます**（前の投手の受け持ちが残っていても代わります）。
抑えは9回以降の3点差以内のリード、セットアッパーは8回の3点差以内のリードでほぼ出ます（同点では半分ほど）。
残りの中継ぎは、それ以外の場面で序列の上位から選ばれやすくなります。
以前は前の投手の受け持ちが尽きたときにしか代えなかったため、9回の途中から出た投手が
アウト3つに届かずセーブを逃し、セーブの最多が年11にとどまっていました。

## 1球団の人数と構成（支配下と育成）

`seed_virtual_players` は1球団を**支配下 62〜66人・育成 10〜30人**まで埋めます（[支配下と育成](チームと選手の管理#支配下と育成)）。

- **支配下の帯はペナントと共有**: 目標はペナントの開幕前の帯（`domain/pennant/roster.py` の `OPENING_REGISTERED_BAND`。
  [ペナントモードの仕組み](ペナントモードの仕組み)の「ドラフトと支配下の帯」）から引きます。帯を変えると投入も一緒に変わります。
  リーグの支配下の上限が帯の上端より低ければ、上限までにします。
- **育成**: 10〜30人（平均約20人）。NPB は育成の人数の球団差が大きい（数人〜50人超）ので幅を持たせています。
  年齢は若め（平均21.5歳・19〜28歳）。助っ人は支配下だけにします（1球団の外国人の上限は育成も数えるため、上限を支配下の助っ人に回す）。
- **位置の構成**: 支配下・育成それぞれに、投手 47.5%・捕手 6.25%・内野手 23.75%・外野手 18.75%・指名打者 2.5% を
  最大剰余法で配り、既存の人数との差を足します。
- **背番号**: 支配下は 00・0・1〜99、育成は3桁（100番台から）。支配下の番号が尽きたら3桁を配らずに止めます
  （以前は 100〜999 を支配下に配る分岐がありました）。
- **入団の経路**: 作った経路そのものを入れます（日本人の支配下は「ドラフト」、助っ人は「新外国人」、育成は「育成ドラフト」）。
  このコマンドは追加専用なので、以前に入れた選手の経路は空欄（不明）のままです。

**育成の選手は試合に出しません。** `seed_virtual_games` はその年に育成の選手を出場の候補から外し、
`simulate_sample --from-real-leagues` の1シーズンの確認も育成を1軍の候補に入れません（ペナントの進行と同じ）。

**今のデータに流し直して埋める**: 選手を足すだけなので、既存の試合はそのまま使えます。足した選手は1軍の試合に
出ていない2軍の選手になります（出場していた約34人の成績・セーブやホールドの水準は変わりません）。
開発用 DB の実測（2026-10-11、`--seed 42`。48球団）:

| 選手（在籍中） | 1,619人 | 3,975人（+支配下 1,447・+育成 909。うち助っ人 67） |
| 支配下／球団 | 28〜40人（平均33.7） | 62〜66人（平均63.9） |

**2軍の層として分布から引きます**（散らばりの調整の母集団は成績のある選手だけ。[ペナントモードの仕組み](ペナントモードの仕組み)の「実成績からの初期能力の推定」）。

コピーの DB で8リーグの世界を作って1シーズン進めた実測（`--seed 5`）も、1試合の両チームの得点 7.56（実データ 7.78）・打率 .252（.254）・
本塁打王 30.6本（32.6本）でした。世界の作成は 3,975人で 7.4秒、締める処理は 10.0秒（引退 302人・新人 285人）。
育成の補充（育成ドラフト #174）がまだ無いので、世界の人数は引退で少しずつ減ります（8年で 3,975 → 3,744人）。

**簡略化しているもの**: 代走・投手の打席（指名打者制のみ）・捕逸・暴投。
盗塁は「打者が打球を放たない打席」でだけ試みます（1打席にアウトが2つ記録されると
併殺と区別が付かず、打点の判定が変わってしまうため）。

明細どうしが食い違わないように、片方から他方を導いています。

- 打点の合計 ＝ その試合の得点
- **投手の被安打・被本塁打・与四死球 ＝ 相手打線が記録した安打・本塁打・四死球**
- 投手の失点 ＝ その投手が投げた回に相手が挙げた得点
- 勝敗・セーブ・ホールド ＝ イニングスコアと継投から、手動入力と同じ
  ドメインサービスが決める

`numpy` は投入コマンドだけが使うので `requirements-dev.txt` にあります
（本番の実行には要りません）。
