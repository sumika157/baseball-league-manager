アプリを一般公開するための構成と手順です。公開先は **AWS Lightsail の VM 1台に docker compose**、入口は **Cloudflare Tunnel** です。
開発用の構成は [開発環境](開発環境) を参照してください（`docker-compose.yml` と `Dockerfile` は開発専用で、本番には使いません）。

> AWS と Cloudflare のリソース（VM・ドメイン・トンネル・バックアップの置き場）は、この手順書に沿って手で作ります。リポジトリからは作りません。

## 構成

```
ブラウザ ──HTTPS──> Cloudflare ══トンネル══ cloudflared ──8000──> web (gunicorn) ──> /data/db.sqlite3 （ボリューム）
                   (HTTPS・証明書)        （VM の内側から接続）   (Django + WhiteNoise)
```

cloudflared が VM の内側から Cloudflare へ接続しに行くので、**VM のポート 80/443 は開けません**。証明書の取得と更新も要りません（HTTPS は Cloudflare が終端します）。

| ファイル | 役割 |
| --- | --- |
| [`Dockerfile.prod`](https://github.com/sumika157/baseball-league-manager/blob/main/Dockerfile.prod) | 本番イメージ（GitHub Actions がビルドして GHCR へ置く）。Node で React をビルドし、`python:3.10-slim` に `requirements.txt` だけを入れる。`collectstatic` はビルド時に済ませ、root 以外の利用者で gunicorn を動かす |
| [`docker-compose.prod.yml`](https://github.com/sumika157/baseball-league-manager/blob/main/docker-compose.prod.yml) | `web`（GHCR のイメージ。起動時に `migrate`）と `cloudflared`（トンネル。トークンは `.env`）。DB はボリューム、バックアップはホストのディレクトリ |
| [`deploy/entrypoint.sh`](https://github.com/sumika157/baseball-league-manager/blob/main/deploy/entrypoint.sh) | 起動のたびに `migrate` してから gunicorn に切り替える |

設定は開発と同じ `config/settings.py` 1本を**環境変数で切り替えます**。環境変数を与えなければ今までの開発・テストの動作のままで、本番の値は明示したときだけ効きます。

| 環境変数 | 効くこと | 設定する場所 |
| --- | --- | --- |
| `DJANGO_PRODUCTION_STATIC` | WhiteNoise で静的ファイルを配信。ファイル名にハッシュを付け、gzip / brotli で配信（manifest ストレージ） | `Dockerfile.prod` |
| `DJANGO_SQLITE_WAL` | SQLite を WAL・`synchronous=NORMAL` にし、書き込みを `IMMEDIATE` で始め、ロック待ちを 20 秒にする | `Dockerfile.prod` |
| `DJANGO_DB_PATH` | DB ファイルの場所（本番は `/data/db.sqlite3`） | `Dockerfile.prod` |
| `DJANGO_LOG_TO_STDOUT` | ログを標準出力へ（`docker compose logs` で読める） | `Dockerfile.prod` |
| `DJANGO_BEHIND_PROXY` | Cloudflare が付ける `X-Forwarded-Proto` を信用して HTTPS と判定する | `docker-compose.prod.yml` |
| `DJANGO_SSL_REDIRECT`・`DJANGO_SECURE_COOKIES`・`DJANGO_HSTS_SECONDS` | HTTPS への転送、Secure クッキー、HSTS（31536000 秒。サブドメインとプリロードも付く） | `docker-compose.prod.yml` |
| `DJANGO_DEBUG` | 本番では compose が `False` に固定する | `docker-compose.prod.yml` |
| `DJANGO_SECRET_KEY`・`DJANGO_ALLOWED_HOSTS`・`DJANGO_CSRF_TRUSTED_ORIGINS`・`CLOUDFLARE_TUNNEL_TOKEN` | ドメインや秘密に依存する値 | `.env` |

`python manage.py check --deploy` は、これらの値を与えると警告を出しません（`tests/integration/test_production.py` が別プロセスで確かめます）。

> **HSTS の注意**: 一度アクセスしたブラウザは、1年間そのドメインと**すべてのサブドメイン**に HTTPS でしか接続しなくなります。
> 同じドメインのほかのサブドメインを HTTP で使っているなら、公開用には専用のドメイン（またはサブドメインを持たないドメイン）を使ってください。
> プリロードの指定はブラウザのプリロードリストへの申請を許すだけで、申請しない限り効きません（申請はしません）。
> HSTS は Django が出すので、Cloudflare 側の HSTS の設定は有効にしません（二重になるため）。

費用の目安と、AWS 以外の選択肢は設計書（[docs/design/workspaces.md](https://github.com/sumika157/baseball-league-manager/blob/main/docs/design/workspaces.md) の「13. 公開先と費用」）にまとめてあります。

## 1. Lightsail の VM を作る

1. Lightsail で **Linux/Unix・Ubuntu 24.04 LTS**、**1 GB メモリ（IPv4 付き）**のインスタンスを作る。
   512 MB では主要画面と gunicorn の2本のワーカーが厳しい。
2. 静的 IP は**要らない**（外から VM へ直接つながないため）。SSH 先の IP が再起動で変わるのが面倒なら付けてもよい（インスタンスに付けている間は無料）。
3. **ファイアウォール**（ネットワーキング → IPv4 ファイアウォール）は **SSH（22）だけ**にする。既定で開いている HTTP 80 は消す。
   SSH は自分の IP に絞るのが望ましい。
   SSH を閉じる方法は「運用の目安」の[SSH を閉じる](#ssh-を閉じる)を参照。
4. **タイムゾーン**を日本時間にする（既定は UTC で、cron の時刻が9時間ずれて昼にバックアップが走る）。
   `sudo timedatectl set-timezone Asia/Tokyo && sudo systemctl restart cron`（cron は起動したときのタイムゾーンで動き続けるので再起動する）。設定後は `date` で確かめる。

## 2. Cloudflare でドメインとトンネルを用意する

1. **ドメイン**: Cloudflare Registrar で取るか、ほかで取ったドメインを Cloudflare に追加してネームサーバーを Cloudflare に向ける。
2. **SSL/TLS**: 「Always Use HTTPS」を有効にする。HSTS の設定は有効にしない（上の注意）。
3. **トンネル**: Zero Trust のダッシュボード → Networks → Tunnels → 「Create a tunnel」で cloudflared のトンネルを作る。
   表示されるトークンを控える（`.env` の `CLOUDFLARE_TUNNEL_TOKEN`）。インストールのコマンドは使わない（compose の `cloudflared` が動かす）。
4. **公開するホスト名**: トンネルの Public Hostname に、公開するドメインを足す。転送先（Service）は **`HTTP`・`web:8000`**。
   DNS のレコードは Cloudflare が自動で作る。

### 管理画面とログインを守る

`/admin/` と `/accounts/login/` は誰でも開けるので、Cloudflare の側で入口を絞ります（どちらもダッシュボードでの操作で、コードにはしません。Terraform 化は #89 で扱います）。

1. **`/admin/` を Cloudflare Access で自分だけにする**: Zero Trust → Access → Applications で「Self-hosted」を作り、
   公開するドメインのパス `/admin/` を対象にする。ポリシーは自分のメールアドレスだけを許可（Allow）にする。
   Access を通らないと Django の管理画面のログインにすら届かなくなる。
2. **`/accounts/login/` に回数制限をかける**（総当たり対策）: ドメインの Security → WAF → Rate limiting rules で、
   パスが `/accounts/login/`・メソッドが POST のリクエストを、同じ IP から短時間に何度も受けたら一定時間ブロックする規則を作る
   （回数と時間は自分の使い方に合わせて決める。使えるプランや無料枠の範囲はダッシュボードで確かめる）。

## 3. VM に Docker を入れる

```bash
ssh ubuntu@<VM の IP>
curl -fsSL https://get.docker.com | sudo sh
sudo usermod -aG docker ubuntu   # 入れ直しのあと再ログインすると sudo なしで使える
```

1 GB の VM でイメージをビルドすると、React のビルド（Node）でメモリが足りなくなることがあります。
スワップを 2 GB 足しておくと、VM でビルドする[代替の手順](#代替-vm-でビルドする)でも通りやすくなります（通常は CI が作ったイメージを pull するのでビルドしません）。

```bash
sudo fallocate -l 2G /swapfile && sudo chmod 600 /swapfile && sudo mkswap /swapfile && sudo swapon /swapfile
echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab
```

## 4. ソースと `.env` を置いて起動する

```bash
git clone https://github.com/sumika157/baseball-league-manager.git
cd baseball-league-manager
cp .env.example .env
```

`.env` の本番の節を埋めます（**値に `$` を含めない**。Docker Compose が展開して壊し、エラーにならずに気づけません）。

```
DJANGO_SECRET_KEY=<python3 -c "import secrets; print(secrets.token_urlsafe(64))" で作った値>
DJANGO_ALLOWED_HOSTS=example.com
DJANGO_CSRF_TRUSTED_ORIGINS=https://example.com
CLOUDFLARE_TUNNEL_TOKEN=<トンネルを作ったときに表示されたトークン>
```

バックアップの出力先を作り、コンテナの利用者（uid 10001）が書けるようにしてから起動します。

```bash
mkdir backups && sudo chown 10001 backups
docker compose -f docker-compose.prod.yml pull   # GHCR のイメージ。非公開のままなら先に docker login ghcr.io が要る
docker compose -f docker-compose.prod.yml up -d   # イメージが無いときは --build を付けて VM でビルドする
docker compose -f docker-compose.prod.yml logs -f   # migrate と gunicorn の起動、cloudflared の接続（Registered tunnel connection）を確認
```

`https://<ドメイン>/` が開けば成功です。手元から `curl -sI https://<ドメイン>/` を叩き、`200` が返ることも確かめます
（`301` が同じ URL へ返り続けるなら、Django が HTTPS と判定できていません。`X-Forwarded-Proto` が届いているか、`DJANGO_BEHIND_PROXY` を見直します）。
続けて管理者を作ります（ログインして試合などを登録するユーザー）。

```bash
docker compose -f docker-compose.prod.yml exec web python manage.py createsuperuser
```

開発のデータ（仮想の選手・試合）を本番に入れる場合は、手元の `db.sqlite3` を[復元](#復元する)の手順で置きます。

## 5. デプロイ（更新）

本番イメージは、main に入るたびに GitHub Actions がビルドして GHCR（`ghcr.io/sumika157/baseball-league-manager`）に置きます
（タグはコミットのハッシュと `latest`。[テストと品質](テストと品質)の「CI」）。VM はそれを取ってきて起動するだけです。

```bash
cd baseball-league-manager
# 先にバックアップを取る（起動時の migrate が失敗したときに、この写しへ戻す）
docker compose -f docker-compose.prod.yml exec -T web python manage.py backup_db /backups --keep 14
# compose と手順の更新を取る（イメージは取らない）
git pull
docker compose -f docker-compose.prod.yml pull
docker compose -f docker-compose.prod.yml up -d
# 古いイメージを消す（pull のたびに残ってディスクを埋める）
docker image prune -f
```

`web` だけが入れ替わり、起動時に未適用のマイグレーションが反映されます（DB のボリュームは残ります）。
`migrate` が失敗したときは、上で取った写しを[復元](#復元する)します。

**最初の push のあとに、パッケージを公開にします。** GHCR のパッケージは初回の push で**非公開**として作られます。
リポジトリのページの右側「Packages」→ `baseball-league-manager` → Package settings → Danger Zone の「Change visibility」で Public にします
（公開リポジトリなので公開にしてよい）。非公開のままなら、VM で一度 `docker login ghcr.io`（`read:packages` の個人用トークン）が要ります。

### 代替: VM でビルドする

GHCR を使わない（または CI がまだイメージを置いていない）ときは、`--build` を付けて VM でビルドします。

```bash
git pull
docker compose -f docker-compose.prod.yml up -d --build
docker image prune -f
```

1 GB の VM では React のビルド（Node）でメモリが足りなくなることがあります（スワップを足しておくと通りやすくなります）。

### 代替: 手元でビルドして送る

```bash
docker build -f Dockerfile.prod -t ghcr.io/sumika157/baseball-league-manager:latest .
docker save ghcr.io/sumika157/baseball-league-manager:latest | gzip | ssh ubuntu@<VM の IP> 'gunzip | docker load'
# VM 側: pull も --build も付けずに起動する
docker compose -f docker-compose.prod.yml up -d
```

## バックアップ

管理コマンド `backup_db <出力先ディレクトリ>` が、SQLite の**バックアップ API** で DB の写しを作ります。
WAL モードのまま、アプリを動かしたまま一貫した写しが取れます（`cp db.sqlite3` は `-wal` に残った分を取りこぼし、書き込み中だと壊れた写しになるので使わない）。
`db-YYYYmmdd-HHMMSS.sqlite3` の名前で書き、整合性（`PRAGMA integrity_check`）を確かめてから名前を付けます。
`--keep N` で新しい順に N 世代だけ残し、古い写しを消します。

```bash
docker compose -f /home/ubuntu/baseball-league-manager/docker-compose.prod.yml exec -T web \
  python manage.py backup_db /backups --keep 14
```

`/backups` はホストの `~/baseball-league-manager/backups/` です。VM の cron で毎日実行します（`crontab -e`）。

```
15 3 * * * cd /home/ubuntu/baseball-league-manager && docker compose -f docker-compose.prod.yml exec -T web python manage.py backup_db /backups --keep 14 >> /home/ubuntu/backup.log 2>&1
```

VM が壊れると同じ VM のバックアップも失うので、**VM の外にも置きます**。置き場は **Cloudflare R2**（無料枠に収まる）です。

1. Cloudflare のダッシュボードで R2 のバケットを作り、そのバケットだけに書き込める **API トークン**（アクセスキー ID とシークレット）を発行する。
2. VM に AWS CLI を入れ、R2 用のプロファイルを作る（R2 は S3 と同じ API で使える）。

```bash
sudo apt-get install -y awscli
aws configure --profile r2   # アクセスキー ID・シークレットを入力。リージョンは auto
```

3. cron に1行足し、`backups/` を R2 へ送る（`<アカウントID>` は R2 の画面に出ている）。

```
30 3 * * * aws s3 sync /home/ubuntu/baseball-league-manager/backups s3://<バケット名>/baseball-backups/ --profile r2 --endpoint-url https://<アカウントID>.r2.cloudflarestorage.com >> /home/ubuntu/backup.log 2>&1
```

R2 のバケットには**ライフサイクルの規則**を設定する（バケット → Settings → Object lifecycle rules。例: プレフィックス `baseball-backups/` のオブジェクトを30日で削除）。
`aws s3 sync` は R2 側のファイルを消さないので、規則が無いと写しが増え続け、無料枠（10GB）を超えたところから課金が始まる。
VM 側の `--keep 14` は VM のディスクのための上限で、R2 には効かない。

Lightsail の自動スナップショット（VM ごとの写し）は有料なので、使っていません。
VM が壊れたときは、新しい VM をこの手順で作り直し、R2 の写しを[復元](#復元する)します。

## 復元する

DB を戻す間は `web` を止めます。`-wal`・`-shm` が残っていると古い内容が混ざるので、写しを置く前に消します。

```bash
cd ~/baseball-league-manager
docker compose -f docker-compose.prod.yml stop web
docker compose -f docker-compose.prod.yml run --rm --no-deps --entrypoint sh web -c \
  "rm -f /data/db.sqlite3-wal /data/db.sqlite3-shm && cp /backups/db-<日時>.sqlite3 /data/db.sqlite3"
docker compose -f docker-compose.prod.yml up -d web
```

R2 から戻すときは、先に `aws s3 cp s3://<バケット名>/baseball-backups/db-<日時>.sqlite3 backups/ --profile r2 --endpoint-url https://<アカウントID>.r2.cloudflarestorage.com` で `backups/` に置きます。
起動時の `migrate` が、写しの時点より新しいマイグレーションを反映します。

## 運用の目安

- ログ: `docker compose -f docker-compose.prod.yml logs -f web`（gunicorn のアクセスログとアプリのエラー）。
- ログの量: compose が `web` と `cloudflared` のログに上限（10MB × 3 ファイル）を付けているので、ディスクを埋め続けることはありません。
  gunicorn のアクセスログの先頭は、cloudflared の IP ではなく利用者の IP（`CF-Connecting-IP`）です。
- ディスク: 古いイメージは[デプロイ](#5-デプロイ更新)の `docker image prune` で消します。ときどき `df -h` で空きを見ます。
- gunicorn のワーカーは同期 2 本（`--timeout 60`）です。1 GB の VM でメモリに余裕を残すためで、SQLite は書き込みが直列なので増やしても書き込みは速くなりません。
  書き込みが重なったときは 20 秒までロックを待ちます。読むだけの公開や少人数で遊ぶ範囲なら十分です。
  書き込みの待ちが目に見えるようになったら PostgreSQL へ移ります（設計書の「13. 公開先と費用」）。
- `docker compose down -v` はボリュームごと DB を消すので使いません。
- 範囲外: PostgreSQL・メール送信・VM へのデプロイの自動化は別に扱います（[ROADMAP](https://github.com/sumika157/baseball-league-manager/blob/main/docs/ROADMAP.md) フェーズ5）。

### SSH を閉じる

SSH（22）を誰からでも受け付けると、ポートスキャンと総当たりを受け続けます。接続元を絞るか、22 を閉じます。

- **Lightsail のブラウザからの SSH だけにする**: ファイアウォールの SSH の規則で、接続元を「Lightsail ブラウザ SSH/RDP」だけに制限する。
  ブラウザ SSH も 22 番を使うので、規則ごと消すとブラウザからも入れなくなる。
- **SSH も Cloudflare Tunnel 経由にして 22 を閉じる**: Zero Trust の Access で SSH のアプリケーションを作り、トンネルの Public Hostname に足す。
  cloudflared はコンテナの中で動くので、転送先に `ssh://localhost:22` と書くとコンテナ自身を指してしまい、VM には届かない。
  `docker-compose.prod.yml` の `cloudflared` に `extra_hosts: ["host.docker.internal:host-gateway"]` を足し、転送先を `ssh://host.docker.internal:22` にする。
  手元からは `cloudflared access ssh` を経由して接続する（手順は Cloudflare のドキュメント）。

### カーネルを更新したあとの再起動

`apt upgrade` でカーネルが更新されても、再起動するまで新しいカーネルは使われません。更新したあとは、空いている時間に VM を再起動します。
再起動しても compose の `restart: unless-stopped` で `web` と `cloudflared` は自動で戻ります（戻ったことを `docker compose ps` で確かめる）。
