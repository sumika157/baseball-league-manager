チームの勝敗・選手の成績・順位をどこから求めているか、試合の成績の出典を打席にした理由をまとめます。

**チームの勝敗も選手の通算成績も、テーブルに持ちません。** 試合（`Game`）を登録すると、
そこから集計して求めます。同じ事実の出典を2つ作らないためです。

```
試合を登録  →  スコア        →  チームの勝敗  →  順位
            →  選手の成績    →  通算成績      →  打率・OPS・防御率
```

- 試合の登録は `/games/new/`（対戦カードだけ。得点は受け取らず 0-0 で作ります）、記録は
  スコアブック画面（`/games/<id>/edit/`）で行います。管理画面の「試合」は閲覧用で、
  直せるのは試合日・シーズンなどの基本情報だけです（得点・イニングスコア・打撃/投球/守備の
  明細は読み取り専用で、行の追加・削除もできません。スコアブックの照合を通らないため）
- **登録しただけの試合は「未記録」で、集計に数えません。** 打席も打撃・投球の明細も無い試合
  （0-0 で入っているが、引分ではない）が未記録です。チームの勝敗・引分・試合数、順位表、
  対戦成績、チームの月別成績、規定打席・規定投球回の基準になる試合数に入りません。
  試合一覧・試合詳細・リーグ画面とダッシュボードの直近の試合には、0-0 や「引分」ではなく
  「未記録」と出し、勝敗の印も付けません。スコアブックを保存すると数えられるようになります。
  打席を記録する前の古い試合（明細だけがある）は記録済みです。**判定の出典は
  `Game.is_recorded`（ドメイン）の1か所**で、参照クエリは明細を読まずに SQL で同じ条件を書きます
  （`recorded_games_filter`。両者が食い違わないことを `test_unrecorded_games.py` が突き合わせます）
- 選手編集画面では成績を変更できません。表示は集計結果で、直せるようにすると
  試合の明細と食い違うためです
- 投球回の合計は「アウト数」で足します。`5.2 + 5.2` は `10.4` ではなく `11.1` です
- 率（打率・OPS・防御率）は試合ごとの率を平均せず、合算した実数から計算し直します

**さらにその試合の成績の出典は「打席」です。** 打数・安打・打点・投球回・失点は、
1打席ずつの記録（結果・走者の進塁・失策）から導きます。1試合ぶんの打撃成績・投球成績・守備成績・
イニングスコアはその集計結果を保存したもので、**通算成績を集計するためだけに持っています**
（自責点は走者ごとの経路を再生しないと出ず、SQL で集計できないため）。
同じ事実が2か所にあることになるので、**保存の前に集約が照合します** — 打席から数え直した
値と食い違う明細は保存できません。

**打席から1試合を組み立てる処理は1つだけです。** 得点・イニングスコア、打順ごとの打撃明細、初登板順の投球明細と登板順、
守備明細、勝敗・セーブ・ホールドは、[domain/services/scoring.py](https://github.com/sumika157/baseball-league-manager/blob/main/myapp/domain/services/scoring.py) の `assemble_game()` が
まとめて導きます。スコアブックの保存（`GameRecordingService`）と仮想データの投入（`seed_virtual_games`）は
どちらもこれを呼ぶだけなので、経路によって勝敗やセーブの付き方が食い違いません。

### 打席を出典にした理由

以前の試合の記録は「完成したボックススコアの転記」でした。編集画面にロスター全員（平均34人）の
行が並び、打数・安打・打点といった**本来スコアラーが試合後に数える値**を人が数えて入れていました。
そのうえ**検算が無い**ので、打点の合計とイニングスコアが矛盾しても気づけませんでした。

いまは実際のスコアラーと同じ手順で記録します。試合前に打順と守備位置を書き、試合中は
1打席ずつ結果と走者の進塁を書き、試合後の集計と検算は集約が行います。

- **記録の粒度は走者の進塁まで**です。失策も記録します（自責点の判定と、進塁の理由に要るため）
- **1球ごとの記録（投球数・球種・カウント）は入れません。** 入力が1球ずつになり負荷が跳ね上がる一方、
  「集計を人にやらせない・検算を入れる」という目的はこれ無しで達成できるためです
- `Game` 集約が保存前に確かめる検算（スコアブックの縦計・横計にあたるもの）:
  - 各回のアウトは3以下（最終回・サヨナラは3未満で終わりうる）
  - 同じ塁に2人の走者がいない。アウトになった走者はそれ以降進まない
  - 打者の到達塁が結果と合う（本塁打なら本塁、単打なら一塁以上）
  - **打順は1〜9を巡回する**（スコアブックを横に読む性質そのもので、入力ミスを強く捕まえる）
  - 打席の通し番号は1から欠けずに続く
  - 3つ目のアウトが打者の打球でのアウトか封殺のとき、その打席で本塁に達した走者の得点は記録できない
    （公認野球規則 5.08。打者が一塁に達した後の走者のアウト＝タイムプレーが3つ目なら、その前の得点や、暴投・盗塁などで還った得点は認める。
    アピールアウトは記録していないので扱わない）
  - 得点の合計 ＝ イニングスコア ＝ 最終得点
  - 1試合の打撃・投球・守備の明細（打点・投球回を含む）は、打席から数え直した値と一致する。
    失策・野選・暴投による得点は打点にならないので、打点の合計は得点を超えない

**1試合の明細テーブルを消さずに残した理由**は実測です（3,480試合・271,907打席）。打席から
数え直した値は旧テーブルと全選手で一致しましたが、通算の集計は4〜7倍遅くなり
（全選手の打撃 53ms → 375ms）、**自責点・失点は走者ごとの逐次再生でしか出せず、
3,480試合の再生に約68秒かかりました。** SQL の `GROUP BY` で表せる形ではないので、
明細は「打席から導いた値の保存」と位置づけ、集約が照合する形にしています
（[CLAUDE.md](https://github.com/sumika157/baseball-league-manager/blob/main/CLAUDE.md) の「同じ事実の出典を2つ作らない」の唯一の例外として明記しています）。

**自責点は推定値です。** 規則 9.16 の「失策・捕逸が無かったものと仮定した再構成」は記録員の
裁量が入るため、完全には自動で導けません。走者ごとの経路に失策・捕逸が絡んだかで近似しています
（[domain/services/scoring.py](https://github.com/sumika157/baseball-league-manager/blob/main/myapp/domain/services/scoring.py) の `runs_scored_in()`）。
推定と違う値に上書きする欄はまだありません（[docs/ROADMAP.md](https://github.com/sumika157/baseball-league-manager/blob/main/docs/ROADMAP.md) のフェーズ8）。
