## 層の分け方

ドメイン駆動設計（DDD）にもとづき、4つの層に分けています。
**依存の向きは常に内側（ドメイン）へ**で、ドメイン層は Django を一切知りません。

```
presentation  →  application  →  domain  ←  infrastructure
（HTTP・画面）    （ユースケース）  （業務ルール）  （Django ORM）
```

| 層 | ディレクトリ | 責務 |
| --- | --- | --- |
| ドメイン | [myapp/domain/](https://github.com/sumika157/baseball-league-manager/tree/main/myapp/domain/) | 野球の語彙とルール。Django 非依存 |
| アプリケーション | [myapp/application/](https://github.com/sumika157/baseball-league-manager/tree/main/myapp/application/) | ユースケースの手順・画面用 DTO・参照クエリのインターフェース |
| インフラ | [myapp/infrastructure/](https://github.com/sumika157/baseball-league-manager/tree/main/myapp/infrastructure/) | Django ORM、リポジトリ実装、参照用クエリ |
| プレゼンテーション | [myapp/presentation/](https://github.com/sumika157/baseball-league-manager/tree/main/myapp/presentation/) | HTTP の解釈とフォーム検証 |

## 集約

集約ルートは **`Team` と `Game`** の2つです。試合は2チームにまたがるため、
`Team` の内部には置けず独立した集約になります。

`Team` については「同一チーム内で背番号は重複しない」という不変条件は
チーム全体を見ないと判定できないため、`Team` がロスターを保持して自ら保証します。

## 更新と参照の分離

- **更新** はリポジトリ経由で集約単位に読み書きします（不変条件を守るため）
- **参照** は一覧表示のように不変条件を扱わないため、集約を組み立てず
  [infrastructure/queries.py](https://github.com/sumika157/baseball-league-manager/blob/main/myapp/infrastructure/queries.py) から直接 DTO を作ります

この分離は速度に直結します。試合一覧は当初リポジトリ経由で組み立てており、
3,480試合の一覧に **3.57秒** かかっていました。一覧に要るのは日付・チーム名・
スコアだけなのに、1試合ごとに打撃・投球・イニングスコアの明細（合わせて9万行超）
まで読んでいたためです。参照クエリ（`DjangoGameListQuery`）に移して **0.02秒** に
なりました。**一覧を作るときに集約を組み立てない**、が判断基準です。

勝敗の判定だけは両方の経路で必要になるため、`winning_team_id()` という純粋関数を
ドメインに置き、集約（`Game.winner_team_id`）と参照クエリの両方がそこを通ります。
参照側で「得点が多い方が勝ち」を書き直すと、同じ事実の出典が2つになるためです。

## 読む範囲を絞る

同じ分離を他の画面にも徹底したところ、主要画面が **6〜55倍** 速くなりました。

| 画面 | 前 | 後 | 何をやめたか |
| --- | --- | --- | --- |
| リーグ詳細 | 4,604ms / 297クエリ | 57ms / 5クエリ | 順位と対戦成績のために全試合の明細とロスターを読んでいた |
| 順位表 | 4,163ms / 295クエリ | 83ms / 3クエリ | 同上 |
| 選手一覧 | 4,580ms / 330クエリ | 257ms / 41クエリ | リーグ平均のために全48チームのロスターを読んでいた |
| ダッシュボード | 4,864ms / 298クエリ | 380ms / 10クエリ | ロスターをチームごとに引き直していた（N+1）。のちにチーム集約を全部組み立てていたのもやめ、選手の成績を参照クエリで集計 |
| リーグ成績 | 1,094ms / 581クエリ | 114ms / 15クエリ | 同上 |
| リーグタイトル | 5,003ms / 295クエリ | 135ms / 6クエリ | リーグ内の対戦を Python で絞っていた。のちにチーム集約と1シーズンぶんの試合の明細を組み立てていたのもやめた（950ms → 135ms） |

判断の基準は3つです。

- **参照では集約を組み立てない**（順位・対戦成績・試合数は得点と対戦カードだけで決まる）
- **絞り込みと集計は SQL 側で行う**（`count_by_team` / `find_between_teams` /
  `find_by_league_with_roster`。ランキングとタイトルの選手の成績は `PlayerStatsQuery` が集計する。
  投球回は（選手, 表記）ごとに集計してから `InningsPitched` で足すので、登板1回ごとには読まない）
- **マッピングの中で関連を引き直さない**（`_RosterData` に選手をまとめて渡す）

計測は専用コマンドで繰り返せます。**SQL 時間だけを見ても遅さには気づけません**
（4.8秒かかっていた画面の SQL は 38ms でした）。

```bash
docker compose exec web python manage.py measure_pages

MSYS_NO_PATHCONV=1 docker compose exec web python manage.py measure_pages --profile /games/
```

## 世界（ペナントモードのセーブデータ）の分離

ペナントモードは、実データのリーグを**分岐**した別の世界を作って遊びます。世界は実データと同じ
テーブルを使い、**リーグが属する世界で分けます**（`League.world`。空なら実データ）。球団・選手・試合は
リーグをたどって世界が決まるので、世界の出典はリーグの1か所だけです。

- **範囲は `WorldScope`（`real()` / `pennant(世界のid)`）で表し、全リポジトリと参照クエリが
  コンストラクタで必須の引数として受け取ります。** 既定値はありません（渡し忘れは型検査で落ちます）。
  読み出しは `find_by_id` も含めてすべて SQL でその範囲に絞られ、範囲の外の id は
  「見つからない」（404）になります。絞り方は [infrastructure/scoping.py](https://github.com/sumika157/baseball-league-manager/blob/main/myapp/infrastructure/scoping.py) に集めています
- `build_service()` などの既存の組み立て口は**実データの範囲に固定**で、引数を持ちません
  （既定値で範囲を切り替える形にすると、渡し忘れが「ペナントの画面に実データが出る」形で現れるため）
- 管理画面は実データだけを扱います（一覧・選択肢・フィルタ・id 指定の編集画面）。`PennantWorld` は登録しません
- 球場は世界と実データで共有します
- 分岐（`pennant_create`）で写すのは、リーグ・球団・選手のプロフィール・**現在の在籍だけ**（加入年は開幕年）です。
  試合と過去の在籍・主将の在任歴は写しません。**分岐した後は同期しません**（別の世界の初期状態であって、
  同じ事実の二重化ではないため）。保存は集約（`Team`）経由なので、背番号の一意性は集約が守ります
- 世界を作る前に、**どの球団も試合を組める名簿か**を検査します（野手9人以上・捕手1人以上・投手8人以上で、捕・一・二・三・遊・左・中・右を守れる選手がいること。数は手動の1軍登録の検査と同じ規則 `playable_shortfall` が出典）。足りない球団があれば、球団名つきの日本語のエラーで世界を作りません（作ってから進行が止まるのを防ぐ）
  外国人の出場枠も見ます（世界のリーグで最も厳しい枠 `strictest_game_limit` の中で、スタメン9人を組める人数 `lineup_capacity` が足りない名簿は作れません。規則の出典は `playable_shortfall` と `lineup_capacity`）。
- 試合を保存する処理（`GameRepository.prepare_add_all`）は、**検査と行の組み立てを書き込みトランザクションの外**で済ませ、返った関数だけをトランザクションの中で呼びます。本番の SQLite は書き手が1つなので、重い処理がロックを持つ時間を保存の間だけにするためです
- 分岐した選手には、実データの通算成績から**初期能力を推定して**保存します（`PennantPlayerRatings`。能力は入力、
  成績は出力で、推定は世界の作成の1回だけ）。推定した順位は保ったまま、散らばりを NPB らしい幅に広げます
- 世界の削除（`pennant_delete`）は、Django の CASCADE に任せず、子のテーブルから範囲で絞って消します
  （打席などは1シーズンで数十万行あり、collector は消す行を Python に集めてしまうため）
- `League.name` の一意性は世界の中で保ちます（実データ側と `(world, name)` の条件付き制約）。
  世界の中のリーグは実データと同名でもよいため

### 世界の画面は実データの画面と同じテンプレートを使う

ビューは実データの画面と**同じ関数**で、URL に世界の id（`world_id`）があるときだけ世界の範囲で読みます
（`presentation/views.py` の `_scope()`。`build_service()` に引数は足しません）。世界の画面のテンプレートへは
`WorldContext`（世界の id・名前・局面・今日・受け持つ球団・オーナーの id）を `world` として渡します。

- **URL の引き方はテンプレートタグ `{% scoped_url 'player_list' team_id %}` に集めています**
  （[templatetags/scoped.py](https://github.com/sumika157/baseball-league-manager/blob/main/myapp/templatetags/scoped.py)）。
  `world` があれば `pennant_<名前>`（世界の id が先頭の引数）を引き、無ければ `{% url %}` と同じ結果です。
  世界の中で引けない名前（編集など）は `NoReverseMatch` になり、黙って実データへ向きません。
  実データだけの画面（ダッシュボード・編集・登録）のテンプレートは `{% url %}` のままです
- **「今日」と局面は保存せず、試合と日程から導きます**（`domain/pennant/season.py` の `season_phase` / `world_today`）。
  最後に試合をした日が今日です。局面は最後の試合の日と次の対戦の日から決めます（試合がまだ無ければ開幕前、対戦が尽きていればシーズン終了、
  次の対戦が最後の試合より後の年なら翌年の開幕前、それ以外はシーズン中）。画面に出す「いまの年度」は `season_year`（能力を引く年 `ratings_year` と同じ規則）です
- 検査: `tests/integration/test_world_isolation.py`（世界の全画面のリンクが `/pennant/<世界>/` の中に留まる・他の世界や
  実データの id が 404）、`test_pennant_screens.py`（誰でも開ける・編集の導線が出ない・空の世界でも落ちない）、
  `test_scoped_url.py`

```bash
# 実データのリーグ 1・2 を分岐して世界を作る（--managed-team は必須。受け持つ球団を分岐元の球団 id で指す。名簿が試合を組めない球団があれば作れない）
docker compose exec web python manage.py pennant_create --name "2026年ペナント" --league 1 --league 2 --managed-team 1 --year 2026

# シーズンを進める（日程が無ければ、先に開幕年の日程を作る）。--to は day / week / next-game / month / season-end
docker compose exec web python manage.py pennant_advance --world 1 --to week

# シーズンを締める（日程をすべて消化した世界だけ。引退・新人・成長と衰え・翌年の日程。元に戻せない）
docker compose exec web python manage.py pennant_close_season --world 1

# 世界を、属する行ごと消す（実データには触れない）
docker compose exec web python manage.py pennant_delete --world 1
```

### シーズンの進め方

- **進行の状態は保存しません。** 「今日」は消化した最後の試合日、局面は最後の試合の日と未消化の対戦（`PennantFixture`）の
  最小の日（`WorldSummary.next_fixture_on`）から、日程と試合から導きます。未消化の対戦だけを持ち、**消化したら `Game` を作って対戦を消します**
  （試合のあとまで残すと、日付と対戦カードの出典が2つになるため）。保存と削除は同じトランザクションです
- **1日ずつ進めても1週間まとめて進めても、同じシーズンになります。** 試合ごとの乱数は
  `blake2b(世界のシード, 年, 日付とホーム・ビジターの球団 id)` から作り、疲労（先発の間隔・連投）は
  保存せず直近の登板（`SimulationContextQuery`）から導きます。1軍登録・スタメン・継投は AI 監督が決め、GM の上書き（下の「球団の編成」）があればそちらを使います
- 試合は `GameRepository.add_all`（新規の試合の一括保存。`save()` と同じ集約の照合を、書く前に全試合ぶん通す）で
  200試合ごと、**日の区切りで**書き出します（日の途中で切ると、残りの対戦が「今日」より前になり進められなくなる）
- 日程は世界のシードから作るので、同じ世界ならいつ作っても同じです。作るのは「日程も試合もまだ無い世界」の
  最初の「進める」のときだけで、シーズンを終えた世界に作り足しません

### シーズンを締める（オフ）

`PennantOffseasonService.close_season()`（管理コマンド `pennant_close_season`）が、**1つのトランザクション**で次を行います。
締める年 Y は最後に試合をした年です。

1. **検査**: 未消化の対戦が残っている（または試合を一度もしていない）→ `SeasonNotFinished`。次の対戦が翌年にある・翌年の能力がある・
   `expected_year` が Y と違う → `AlreadyClosed`。世界の最後のシーズン（`MAX_SEASONS_PER_WORLD` 番目）→ `SeasonLimitReached`。
   どれも何も書かない。**締めたかどうかは保存せず**、翌年の能力の行（と翌年の日程）の有無から導く
2. **計算**: domain の純粋な関数 `plan_offseason`（引退 → 球団ごとの新人 → 成長と衰え → 水準の錨）。DB に触れない
3. **書く**: 球団ごとに `Team.retire_player(year=Y)` → `Team.add_player(from_year=Y+1)`（年を省略しない）→ 外国人を足した球団だけ登録枠の検査 →
   `teams.save`。翌年の能力は `RatingsRepository.add_all` の1回。引退した選手を含む編成の区画は自動に戻す（`ClubPlan.release`。1軍登録を戻すときは依存する3区画も）。
   翌年の日程は開幕年と同じ関数 `season_schedule` で作る

二重実行は、トランザクションの中で検査を読み直し、すり抜けても**翌年の能力の保存（保存前の検査と、選手 × 年の一意制約）で後から来た方が丸ごと巻き戻る**ことで防ぎます（この制約を外さない）。
乱数は世界のシード・年・選手または球団の id から作るので、同じ状態から締めれば同じ結果になります。

### 球団の編成（GM の上書き）

AI 監督の編成を GM が上書きできます。**持つのは上書きだけ**です（`ClubPlan`。[domain/pennant/club_plan.py](https://github.com/sumika157/baseball-league-manager/blob/main/myapp/domain/pennant/club_plan.py)）。

- 球団ごとに1つ。4つの区画（1軍登録・オーダー・ローテーション・抑え）が、それぞれ「自動」か「手動の値」を持ちます。
  自動の区画は保存せず、進めるたびに AI 監督が決めます。持つのは**選手の id だけ**で、検査のたびにその時点のロスターを渡します
  （`Team` 集約に入れないのは、ロスターの読み込みが通算成績の集計まで連れてくるため）
- 上書きを**決めるとき**に不変条件を検査します（1軍29人まで・外国人は登録枠まで・在籍している選手だけ・
  オーダーは1軍の野手9人で守備位置が9つ・各選手は登録位置が就ける位置だけ（`can_play`。AI と同じ表だが手動は絶対の制約。1軍登録の段階で捕1・内4・外3を埋められることも検査する）・
  ローテーションは1軍の投手で5人以上・1軍の投手は8人以上・抑えは1軍の投手。下限は AI 監督の人数（`simulation/manager.py`）から導く）。
  **進めるときに例外で止まる組み合わせも、決めるときに弾きます**（捕手のいない1軍、外国人の出場枠の中でスタメン9人を
  組めない1軍、抑えのほかに先発できる投手がいない1軍）。オーダーとローテーションの組み合わせ（オーダーが出場枠を
  使い切り、ローテーションが外国人だけ）は、当てはめるときにオーダーを自動に落とします。オーダーが出場枠を使い切って
  外国人の抑えが投げられないときは、上書きを残したまま理由を注意に出します。
  外国人の**出場枠は世界のリーグの中で最も厳しい値**で検査します（交流戦はホーム球団のリーグの枠で行うため、
  自リーグの枠で検査すると、枠の厳しいリーグとの交流戦でスタメンを組めず止まる）
- 決めたあとにロスターが変わって使えなくなった上書き（登録を外した選手がオーダーにいる、など）は、
  **例外で進行を止めず、その区画だけ自動に落とし**、理由を `AdvanceReport.plan_notices` で返します（`resolve_club`）
- 上書きを渡さないとき、試合の結果は今までと同じです（`simulate_game` の `home_orders` / `away_orders` は任意）
- 保存は `PennantClubPlan`（球団ごと。抑えを持つ）と `PennantClubPlanEntry`（区画・順・選手の行）。
  世界の削除と範囲の絞り込みは、日程・試合と同じく球団のリーグをたどります
- **編成の画面 `/pennant/<世界>/club/`**（`views.pennant_club`）。読むのは `ClubManagementService.view()`
  （`ClubPlanView`。上限の数と守備位置の選択肢は `ClubLimitsView` で domain から受け取り、テンプレートに書かない）と、
  投手陣のタブだけが読む `pitching_usage()`（`ClubPitchingUsage`。直近の登板から導く疲労）。`TeamApplicationService` にはメソッドを足していません
- 区画ごとに自動か手動の**どちらかの操作だけ**を出します（`_club_section_head.html` が「手動にする」を、手動の本体が「保存する」「自動に戻す」を持つ）。
  POST は `section`（区画）と `action`（手動にする／保存する／自動に戻す）で受け、成功したら同じタブへリダイレクトします
- フォームの読み取りは `presentation/club_input.py`。**キーの欠落を「空」と扱いません**（空で保存すると既存の編成が消える）。
  1軍登録のチェックボックスは外すと何も送られないので、表示した全選手の id（`shown`）を送って今の在籍と突き合わせ、食い違えば保存しません。
  成り立つかの検査はドメイン（`ClubPlan`）で、画面は id と守備位置を取り出すだけです
- **手動の区画の編集欄は、保存済みの上書き**（`ClubPlanView.saved_*`）から始めます。使えなくなって自動に落ちた区画も、
  GM が決めた形のまま出し（1軍外の選手には「1軍外」の印）、保存するとドメインの検査で弾かれます。
  解決後の値から始めると、保存したときに上書きが AI の形で置き換わるためです
- 連投の規則（`PitchingHistory.can_pitch_on`）と直近の登板を読む日数（`RECENT_PITCHING_DAYS`）は domain が出典で、
  救援の選択・直近の登板の読み込み・投手陣タブの表示が同じものを使います
- GM ホームの「注意」は、オーナーのときだけ `ClubManagementService.view(受け持つ球団).notices`（いま進めたら自動に落ちる区画）を読みます。
  応答は 8リーグ 48球団で、編成の各タブが 22〜39ms（14〜20クエリ）、ホームのオーナーの上乗せは約 20ms。
  能力は受け持つ球団の選手だけ読みます（`find_by_players`）
- 検査: `tests/integration/test_club_screen.py`（権限・区画ごとの排他・往復・不正な入力・注意・投手陣の状態）、
  `test_world_isolation.py`（編成のフォームとリンクが世界の中に留まる）


### GM ホームと進める操作

- **GM ホームは新しい小さなサービス `PennantHomeService`**（[application/pennant_home.py](https://github.com/sumika157/baseball-league-manager/blob/main/myapp/application/pennant_home.py)）が作ります。
  `TeamApplicationService` にはメソッドを足していません（順位・主力・タイトルは世界の範囲のサービスの既存の参照を使う）。
  材料の DTO は `PennantHome`・`OwnTeamSummary`・`AdvanceOption`・`AdvanceSummary`（結果のまとめ。設計書の名前は `AdvanceReport` だが、
  進めた結果を返す既存の `AdvanceReport` と別物なので改めた）など（`application/dto.py`）
- **世界の全試合を毎回集約として組み立てません。** 自軍の試合・期間の試合は `GameListQuery`（試合の一覧の SQL。明細は読まない。
  `after` / `through` で期間を絞れる）、責任投手・本塁打・期間の打撃と投球は `PennantActivityQuery`（明細の SQL 集計）で読みます。
  応答は 60〜250ms、クエリは 38〜49本で、世界の試合数が増えても変わりません
- **勢い（直近10試合・連続）と、結果のまとめの期間は保存せず導きます**（`domain/pennant/form.py`・`season.py` の `summary_period`）。
  進める前の順位は、`get_league_standings(year, through=<日付>)` でその日までの試合だけから順位を作り直します
- **「進める」の選択肢は日程から導きます**（終わる日付と試合数は `dates_to_play`）。1回の上限（`MAX_GAMES_PER_ADVANCE` = 150試合）を超える範囲と、
  ほかの選択肢と同じ範囲になるものは出しません。上限は `PennantSeasonService.advance(target, max_games=...)` でも守り、超えると何も作らずに
  `InvalidSchedule` にします（画面だけが渡す。管理コマンドは渡さない）
- **進める・削除はオーナーだけ**（`WorldContext.owner_id` とログイン中のユーザーを比べる。管理ユーザーでも通らない）。
  進めるのは POST だけで、GET はホームへ戻します。hidden の `expected_today`（いまの今日）が世界の今日とずれていたら進めません
  （二重送信・別の画面で先に進めた場合）。進めた後は `?since=<進める前の今日>` つきでホームへ戻ります
- 世界の作成は `PennantWorldForm`（`presentation/forms.py`）で検証し、`PennantWorldService.create_world` のあとに
  日程も作ります（開幕前のホームが、進める範囲と試合数を出せるように）。元にするリーグは8つまで・1人5世界まで
  （`domain/pennant/world.py` の `MAX_SOURCE_LEAGUES` `MAX_WORLDS_PER_OWNER`）
- 検査: `tests/integration/test_pennant_home.py`（ホーム・進める・権限・上限・`expected_today`・結果のまとめ）、`test_pennant_worlds.py`（作成・削除）、
  `test_pennant_activity.py`、`tests/e2e/test_pennant_flow.py`（作る → 進める → 順位表とボックススコア → リンクが世界の外に出ない）

混ざっていないことは [tests/integration/test_world_isolation.py](https://github.com/sumika157/baseball-league-manager/blob/main/myapp/tests/integration/test_world_isolation.py) が検査します
（実データの主要画面に世界の名前が出ない・世界の id で実データの URL を開くと 404・管理画面に出ない・
全モデルを「世界にどう属すか」で分類した表に未分類が無い）。

実装がインターフェースを満たしているか、組み立てに欠けが無いかは
[tests/integration/test_wiring.py](https://github.com/sumika157/baseball-league-manager/blob/main/myapp/tests/integration/test_wiring.py) が機械的に検査します
（`Protocol` は静的型検査では実装側に何も強制しないため、実行時にも確かめます）。
