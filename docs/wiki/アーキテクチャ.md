## 層の分け方

**依存の向きは常に内側（ドメイン）へ**で、ドメイン層は Django を一切知りません。

```
presentation  →  application  →  domain  ←  infrastructure
（HTTP・画面）    （ユースケース）  （業務ルール）  （Django ORM）
```

## 集約

集約ルートは **`Team` と `Game`** の2つです。試合は2チームにまたがるため、
`Team` の内部には置けず独立した集約になります。

`Team` については「同一チーム内で背番号は重複しない」という不変条件は
チーム全体を見ないと判定できないため、`Team` がロスターを保持して自ら保証します。
移籍の受け入れ（`accept_transfer`）・選手の追加・昇格も同じで、背番号と区分の照合、
**支配下の上限**も集約の操作の中で検査します（外国人の保有の人数は協約どおり縛りません。外国人枠は1軍の登録にかかる
`ForeignPlayerRules` で、スコアブックの保存とペナントの編成が検査します）。上限はリーグが持つので、
操作の**省略できない引数**（`RosterLimits`）で受けます（呼び出し側が事前に検査する約束にすると、呼び忘れが黙って上限を超えるため。
検査しない呼び出しは `RosterLimits.UNLIMITED` を明示します）。

在籍の検査は置き場所を使い分けています。**経路と加入時の区分の整合**は `Stint.__post_init__` に置きます（経路を持たない既存の行は検査されないので、読み込みで落ちません）。
一方、**背番号と区分の整合は `__post_init__` に置きません**（検査を通らずに書かれた既存の行が、読んだだけで例外になるため）。集約の操作と管理画面が `ContractStatus.ensure_number_fits` を呼びます。
その年の区分・背番号は `ContractStatus.in_year` と `jersey_number_in` が出典で、集約の `Stint` も参照クエリ（在籍の値をそのまま DTO に載せ、年ごとの導出は application がこの2つで行う）も同じ関数を使います。
FA 宣言の結果（残留・移籍）は保存せず、在籍の期間と経路だけを見る `fa_origin` / `fa_destinations` が出典です。集約の外（管理画面の送信後の全体、参照クエリの行）からも同じ規則で呼べます。

## 更新と参照の分離

- **更新** はリポジトリ経由で集約単位に読み書きします（不変条件を守るため）。
  `TeamRepository.save()` は集約の全体を受け取りますが、**今の行と比べて変わった行だけを書き**、集約が持っていない行は消しません（#176。全員を書き直していたころは、シーズンを締める処理が引退した選手まで約1.3万行を書き直していた）
- **参照** は一覧表示のように不変条件を扱わないため、集約を組み立てず
  [infrastructure/queries.py](https://github.com/sumika157/baseball-league-manager/blob/main/myapp/infrastructure/queries.py) から直接 DTO を作ります

この分離は速度に直結します。試合一覧は当初リポジトリ経由で組み立てており、
3,480試合の一覧に **3.57秒** かかっていました。一覧に要るのは日付・チーム名・
スコアだけなのに、1試合ごとに打撃・投球・イニングスコアの明細（合わせて9万行超）
まで読んでいたためです。参照クエリ（`DjangoGameListQuery`）に移して **0.02秒** に
なりました。**一覧を作るときに集約を組み立てない**、が判断基準です。

勝敗の判定だけは両方の経路で必要になるため、`winning_team_id()` という純粋関数を
ドメインに置き、集約（`Game.winner_team_id`）と参照クエリの両方がそこを通ります。
参照側で「得点が多い方が勝ち」を書き直すと、同じ事実の出典が2つになるためです。

## 読む範囲を絞る

同じ分離を他の画面にも徹底したところ、主要画面が **6〜55倍** 速くなりました。

| 画面 | 前 | 後 | 何をやめたか |
| --- | --- | --- | --- |
| リーグ詳細 | 4,604ms / 297クエリ | 57ms / 5クエリ | 順位と対戦成績のために全試合の明細とロスターを読んでいた |
| 順位表 | 4,163ms / 295クエリ | 83ms / 3クエリ | 同上 |
| 選手一覧 | 4,580ms / 330クエリ | 257ms / 41クエリ | リーグ平均のために全48チームのロスターを読んでいた |
| ダッシュボード | 4,864ms / 298クエリ | 345ms / 10クエリ | ロスターをチームごとに引き直していた（N+1）。のちにチーム集約を全部組み立てていたのもやめ、選手の成績を参照クエリで集計。部門の首位をシーズン集計にしたとき（#179）は、全リーグぶんを年ごとに1回で集計する（`list_season_by_league`。リーグごとに引くと 689ms / 29クエリだった。ペナントの epic を取り込んだ後は、交流戦を含めて数えるため球団の試合数を年ごとに1回読むので 10クエリ） |
| リーグ成績 | 1,094ms / 581クエリ | 114ms / 15クエリ | 同上 |
| リーグタイトル | 5,003ms / 295クエリ | 135ms / 6クエリ | リーグ内の対戦を Python で絞っていた。のちにチーム集約と1シーズンぶんの試合の明細を組み立てていたのもやめた（950ms → 135ms） |

判断の基準は3つです。

- **参照では集約を組み立てない**（順位・対戦成績・試合数は得点と対戦カードだけで決まる）
- **絞り込みと集計は SQL 側で行う**（`count_by_team` / `find_between_teams` /
  `find_by_league_with_roster`。ランキングとタイトルの選手の成績は `PlayerStatsQuery` が集計する。
  投球回は（選手, 表記）ごとに集計してから `InningsPitched` で足すので、登板1回ごとには読まない）
- **マッピングの中で関連を引き直さない**（`_RosterData` に選手をまとめて渡す）

計測は専用コマンドで繰り返せます。**SQL 時間だけを見ても遅さには気づけません**
（4.8秒かかっていた画面の SQL は 38ms でした）。

## 依存の組み立て

アプリケーションサービスは実装ではなく**インターフェース**（`Protocol`）だけに依存します。
更新側と参照側で置き場所が分かれます。

| インターフェース | 置き場所 | 実装 |
| --- | --- | --- |
| `TeamRepository` `GameRepository` `LeagueRepository` `WorldRepository` `RatingsRepository` `FixtureRepository` `ClubPlanRepository` | [domain/repositories.py](https://github.com/sumika157/baseball-league-manager/blob/main/myapp/domain/repositories.py) | `infrastructure/repositories.py` |
| `TeamListQuery` `GameListQuery` `PlayerFieldingQuery` `PlayerStatsQuery` `TeamAnalysisQuery` `ServiceHistoryQuery` `SimulationContextQuery` `WorldSummaryQuery` `SeasonPlayingTimeQuery` `PostseasonQuery` `PostseasonStatsQuery` | [application/queries.py](https://github.com/sumika157/baseball-league-manager/blob/main/myapp/application/queries.py) | `infrastructure/queries.py` |

参照クエリだけドメイン層に置けないのは、戻り値が画面向けの DTO（`application/dto.py`）で、
ドメイン層から参照できないためです。

実装を差し込むのは [presentation/views.py](https://github.com/sumika157/baseball-league-manager/blob/main/myapp/presentation/views.py) の組み立て口（`build_*()` 関数）**だけ**です（サービスを増やすときは組み立て口もここに足します）。

**組み立て口はすべて、範囲（`scope: WorldScope`）を既定値なしで受け取ります**（世界の台帳だけを読む `build_pennant_world_view(workspace_id)` はワークスペースの id を受け取る）。範囲は views の `_real_scope(request)`（今の URL のワークスペースの実データ）と `_world_scope(request, 世界のid)`（ペナントの世界）で作ります。今の URL のワークスペースは、URL の key から `workspace_view` が1つの要求で1回だけ解決したもの（`request.workspace`。下の「ワークスペースの URL と入口」）で、`workspace_view` を通っていない要求で範囲を作ろうとすると `WorkspaceNotResolved`（黙って既定のワークスペースに落とさない）。範囲の取り違えは組み立てるところで `InvalidWorld` になります。分類は次のとおりです。

- **実データでもペナントでも**: `build_league_view_service(scope)`・`build_team_view_service(scope)`・`build_game_view_service(scope)`・`build_team_analysis_service(scope)`（年齢の基準日・既定の年の「今日」は、実データなら暦の今日、世界ならその世界の日付）
- **実データ専用**（ペナントの範囲を渡すと `InvalidWorld`）: `build_recording_service`・`build_roster_service`・`build_permission_query`・`build_player_search_query`・`build_pennant_world_service`
- **ペナント専用**（実データの範囲を渡すと `InvalidWorld`）: `build_pennant_season_service` ほか世界の名がつく表の下11行
- **台帳だけ**: `build_pennant_world_view(workspace_id)`（範囲ではなくワークスペースの id を取り、台帳をそのワークスペースで絞って、世界ごとの範囲をそのワークスペースで作る）
- **ワークスペースの台帳**（何も取らない）: `build_workspace_access_query()`（URL の key と利用者から、ワークスペースと権限 `WorkspaceAccess` を引く。`workspace_view` と `/` の見本のリンクが使う）・`build_workspace_list_query()`（`/` の、自分が入っているワークスペースの一覧）。key・利用者からワークスペースそのものを引く台帳で、ワークスペースの中のデータは読みません

## ワークスペースの URL と入口

ワークスペースの中の画面は `/w/<key>/...` です（[config/urls.py](https://github.com/sumika157/baseball-league-manager/blob/main/config/urls.py)）。
key の形はパスコンバータ `wskey`（[presentation/converters.py](https://github.com/sumika157/baseball-league-manager/blob/main/myapp/presentation/converters.py)。
正規表現はドメインの `KEY_LENGTH`・`KEY_ALPHABET` から作る）が受け、形の合わない key は DB を読まずに 404 です。`/` はワークスペースの外のトップ（`home`）。

`myapp/urls.py` の登録は補助 `_w(route, view, name, *, login=False, json=False)`（ペナントの世界の画面は `_pennant()`）を通し、
補助が**必ず** `workspace_view` で包みます（包み忘れを形で防ぐ。全パターンが包まれていることは `test_workspace_isolation.py` が検査します）。
`workspace_view`（[presentation/views.py](https://github.com/sumika157/baseball-league-manager/blob/main/myapp/presentation/views.py)）は、ビューの手前で次を行います。

1. URL の key と利用者から、`build_workspace_access_query().resolve(key, user_id)` でワークスペースと権限を引く（1要求で1回。未ログイン・持ち主・編集者は1クエリ、ほかのログインした人は担当チームの id を読む2クエリ）。無い key は 404
2. 読めない（非公開でメンバーでない）なら、未ログインはログインへ（`next` つき。ログイン後に同じ URL へ戻る）、ログインしていれば 404（あることを明かさない）。未ログインの人には、無い key は 404・ある非公開の key はログインへ、と応答が分かれる（計画どおり。key は推測しにくい10文字なので、ログインへ送る便利さを取った）
3. `login=True` の画面（試合の登録・編集・選手の編集）と、未ログインの POST はログインへ
4. `request.workspace`（`WorkspaceContext`。id・key・名前・権限の値オブジェクト `WorkspaceAccess`）を載せて、ビューを `key` 抜きの引数で呼ぶ

`json=True`（スコアブックの保存 API）は、リダイレクトや 404 の画面の代わりに、ほかのエラーと同じ形の JSON を返します（未ログイン 403・無い／見えないワークスペース 404）。
CSRF の失敗も、API かどうかをパスではなく URL 名（`api_` で始まる）で決めて JSON を返します。
権限の**事実**は参照クエリ `DjangoWorkspaceAccessQuery`（持ち主・編集者の行・担当チーム）、**規則**は domain の `WorkspaceAccess`
（`can_view`・`can_edit_all`・`can_edit_teams`・`can_create_world`。`is_staff` は引数に無い）、**適用**は `workspace_view` とビューです。
チームごとの書き込みの判定はビューに残します（どのチームかは POST の本文を読むまで決まらない画面があるため）。
ペナントの世界の作成は `can_create_world()`（持ち主・編集者）で絞ります。

## 世界（ペナントモードのセーブデータ）の分離

ペナントモードは、実データのリーグを**分岐**した別の世界を作って遊びます。世界は実データと同じテーブルを使い、
**リーグが属する世界で分けます**（`League.world`。空なら実データ）。球団・選手・試合はリーグをたどって世界が決まるので、世界の出典はリーグの1か所だけです。

- **範囲は `WorldScope`（`real(ワークスペースのid)` / `pennant(ワークスペースのid, 世界のid)`）で表し、全リポジトリと参照クエリがコンストラクタで必須の引数として受け取ります。** 実データの範囲は「そのワークスペースの実データ」です。既定値はありません（渡し忘れは型検査で落ちます）。世界の台帳（`WorldRepository`・`WorldSummaryQuery`）は範囲の代わりにワークスペースの id を必須で受け取り、そのワークスペースの世界だけを読み書きします（`count_by_owner` だけは1人あたりの上限のため全ワークスペースで数える）。例外は管理画面専用の `admin_real_queryset`（全ワークスペースの実データ。`admin.py` 以外は使わない）です。管理画面のトップの運営向けの概況も、この例外の中（`admin.py` の `operator_overview()`）で数え、テンプレートタグは呼ぶだけです。
  読み出しは `find_by_id` も含めてすべて SQL でその範囲に絞られ、範囲の外の id は「見つからない」（404）になります
- 組み立て口はすべて範囲を必須の引数に取ります（上の表）。実データ専用・ペナント専用の口に逆の範囲を渡すと `InvalidWorld` になり、渡し忘れや取り違えが画面で気づかれずに混ざる形を防ぎます
- 世界の画面は実データの画面と同じビュー関数とテンプレートで、URL はテンプレートタグ `{% scoped_url %}` が世界の中に留めます
- ワークスペースの中の画面（[myapp/urls.py](https://github.com/sumika157/baseball-league-manager/blob/main/myapp/urls.py) の `workspace_urlpatterns`。`/w/<key>/` の下）への URL は、補助を通して組みます。補助がワークスペースの key を先頭の引数に足します。テンプレートは `{% scoped_url %}`（実データと世界で引き分ける）か `{% workspace_url %}`（名前を切り替えない。ペナント専用・実データ専用の画面）で、key は context の `workspace`（コンテキストプロセッサが渡す今の要求のワークスペース）から取り、`workspace` が無い描画（ワークスペースの外）では例外にします（key の無い URL を黙って作らない。外の画面のテンプレートは `{% if workspace %}` で囲む）。`/` の一覧は行ごとの key で入口を引く `{% workspace_entry_url key %}`。views・API は `_url(request, 名前, ...)`（今の要求の key）、テストは `helpers.ws_url(名前, ..., workspace=...)`（省けば既定のワークスペース）、`measure_pages` は `_url(key, 名前, ...)`。素の `{% url %}`・`reverse` はワークスペースの外（`/`・ログイン・管理画面）だけに使います。テンプレートの素の `{% url %}` は `test_templates.py`、views・API の `reverse` は `test_workspace_urls.py` が検査します
- 混ざっていないことは [tests/integration/test_world_isolation.py](https://github.com/sumika157/baseball-league-manager/blob/main/myapp/tests/integration/test_world_isolation.py) が検査します
- **試合の区分も範囲と同じ形で絞ります。** 試合は区分（`Game.stage`。公式戦・ポストシーズン）を持ち、試合を読む入口（`infrastructure/scoping.py` の `games_in(scope, *, stages)` など）と
  成績の集計（`batting_totals`・`pitching_totals`・`game_counts`）は区分 `StageFilter`（`REGULAR_ONLY` / `POSTSEASON_ONLY` / `ALL_STAGES`）を**既定値を持たない必須の引数**で受け取ります。
  「None なら全部」の形は作りません（外し忘れると、公式戦の成績・順位・タイトルにポストシーズンが黙って混ざるため）。公式戦の参照クエリには区分の引数を足さず、ポストシーズンの個人成績は別の参照クエリ（`PostseasonStatsQuery`）が `POSTSEASON_ONLY` で同じ集計を呼びます
- 混ざっていないことは [tests/integration/test_postseason_isolation.py](https://github.com/sumika157/baseball-league-manager/blob/main/myapp/tests/integration/test_postseason_isolation.py) が検査します
  （極端な成績のポストシーズンの試合を足しても、世界の参照画面と公式戦の参照クエリの答えが変わらない。区分を指定せずに試合と明細のモデルを読む関数を静的に落とす）。
  どの読みをどの区分にしたかは [ペナントモードの仕組み](ペナントモードの仕組み#ポストシーズン)

分岐・試合シミュレーション・日程と進め方・編成・オフ・書き込みとロック、決めたことと実測値は [ペナントモードの仕組み](ペナントモードの仕組み) にまとめています。管理コマンド:

```bash
# 実データのリーグ 1・2 を分岐して世界を作る（--managed-team は必須。受け持つ球団を分岐元の球団 id で指す。名簿が試合を組めない球団があれば作れない）

# （公式戦の日程を消化した後の day / next-game / postseason-end はポストシーズンを進める）

# シーズンを締める（日程をすべて消化し、ポストシーズンも終わった世界だけ。引退・戦力外・新人・成長と衰え・翌年の日程。元に戻せない）
```
