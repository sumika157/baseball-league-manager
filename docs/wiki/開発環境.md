起動後の日常的な開発作業（コマンド・ビルド・エディタ・データベース・トラブルシューティング）をまとめます。初回のセットアップと起動は [README](https://github.com/sumika157/baseball-league-manager#readme) を参照してください。

## ホットリロード

ソースコードはコンテナにマウントされているため、**ファイルを編集して保存すると自動でリロードされます**。
コンテナを再起動する必要はありません。

```
baseball-web  | /app/myapp/views.py changed, reloading.
```

## フロントエンドのビルド（React）

リッチな編集画面は React（`frontend/`）で実装し、ビルド成果物を Django の静的ファイルとして
配信します（アイランド構成。詳細は [フロントエンド](フロントエンド#react-アイランド)）。

- `docker compose up` で `frontend` コンテナも一緒に起動し、**watch ビルドが回り続けます**。
  `frontend/src/` を編集して保存すると `myapp/static/myapp/dist/` に自動で再出力されるので、
  ブラウザをリロードすれば反映されます（HMR はありません）。
- ホストに Node.js は不要です。npm の操作はすべて `frontend` コンテナで行います。
- `myapp/static/myapp/dist/` と `frontend/node_modules/` は Git 管理外です。
  **クローン直後や E2E テストの前は `make frontend-build` で成果物を作ってください。**

## 静的ファイルのキャッシュ

開発サーバーは静的ファイル（CSS・JS）の応答に `Cache-Control: no-cache`（使う前に毎回サーバーに確かめる）を付けています
（`myapp/management/commands/runserver.py`）。**CSS を直したら再読み込みするだけで新しい CSS が当たります**。
変更が無ければサーバーは 304 を返すので重くなりません。本番は WhiteNoise がファイル名にハッシュを付けて長期キャッシュするため、この指示は付きません。

## よく使うコマンド

`manage.py` のコマンドは、起動中のコンテナに対して `docker compose exec` 経由で実行します。

| 目的 | コマンド |
| --- | --- |
| マイグレーションファイルの作成 | `docker compose exec web python manage.py makemigrations` |
| マイグレーションの適用 | `docker compose exec web python manage.py migrate` |
| マイグレーションの適用状況を確認 | `docker compose exec web python manage.py showmigrations` |
| 管理ユーザーの作成 | `docker compose exec web python manage.py createsuperuser` |
| 設定ミスの検査 | `docker compose exec web python manage.py check` |
| テストの実行 | `docker compose exec web python manage.py test myapp.tests.domain myapp.tests.integration --parallel 4`（e2e は別に流す。[テストと品質](テストと品質)） |
| Django シェル | `docker compose exec web python manage.py shell` |
| コンテナ内のシェルに入る | `docker compose exec web bash` |
| ログを見る | `docker compose logs -f web` |
| 状態を確認する | `docker compose ps` |

### 短縮コマンド（Makefile）

上記の定型コマンドは Makefile に短縮コマンドとして定義してあります。
WSL のターミナルからリポジトリのルートで実行します（Windows 側の PowerShell からは使えません）。

```bash
make            # ターゲット一覧を表示（make help と同じ）
make test       # フルスイート（t=myapp.tests.xxx で個別指定）
make test-domain # domain 層のみ（DB 不要・最速）
make coverage   # カバレッジ計測付きでテストを実行（t= で範囲指定可）
make lint       # ruff check + ruff format --check + mypy（コミット前に必須）
make format     # ruff format で整形（lint が整形漏れを指摘したとき）
make frontend-build # React 画面のビルド（E2E テストの前提）
make frontend-check # TypeScript の型チェック
make up / make down / make logs
make where      # どの作業ツリーを対象にしているか表示
```

並行作業のために git worktree（`.claude/worktrees/<名前>`）を使っているときは、
**main の作業ツリーから `WT=<名前>` を付けて実行します**（例: `make test WT=player-nationality`）。
バインドマウントは main の作業ツリー全体なので、worktree のコードも同じコンテナから
`/app/.claude/worktrees/<名前>` として扱えます。`WT` を付け忘れると main のコードを
テストしてしまい、エラーにならないぶん気づけません。worktree の中から `WT` 無しで
`make` を呼んだ場合は止まるようにしてあります（詳細は [worktree スキル](https://github.com/sumika157/baseball-league-manager/blob/main/.claude/skills/worktree/SKILL.md)）。

### worktree の画面を見る（プレビュー）

`localhost:8000` が配信するのは main の作業ツリーです。worktree の変更をマージ前にブラウザで確かめるときは、
8001〜8009 番の空いているポートで別に立てます。

```bash
make frontend-build WT=<名前>   # React の画面の成果物（初回だけ。無いと画面の一部が動かない）
make preview WT=<名前>          # URL が表示される（例: http://localhost:8001/）
make preview-list               # 動いているプレビューの一覧
make preview-stop WT=<名前>     # 止める（worktree を消す前に止める）
```

- DB は worktree の `db.sqlite3` です。無ければ main の `db.sqlite3` を写してから migrate します（main のデータは変わりません）。
  main の最新のデータで見直したいときは、止めてから worktree の `db.sqlite3` を消し、もう一度 `make preview` します。
- ログインはプレビューごとに別です（セッションのクッキー名をポートごとに変えています。同じ名前だと、localhost のクッキーは
  ポートで分かれないので、プレビューでログインしたときに 8000 番のログインが切れます）。
- worktree のコードを直すと、自動で読み込み直します（8000 番と同じ）。
- 中身は [scripts/preview.py](https://github.com/sumika157/baseball-league-manager/blob/main/scripts/preview.py)。
  8001〜8009 番は `docker-compose.yml` がホストへ公開しています。

## worktree と置き去りのプロセスの自動の片付け

Windows のタスクスケジューラが1時間ごとに
[scripts/cleanup.ps1](https://github.com/sumika157/baseball-league-manager/blob/main/scripts/cleanup.ps1)
を実行し、次のものを片付けます。消したものは `%LOCALAPPDATA%\baseball-cleanup\cleanup.log` に記録します。

| 対象 | 消す条件 |
| --- | --- |
| `.claude/worktrees/` の worktree | PR がマージ済みかクローズ済みで、開いている PR が無く、HEAD が PR の先端と一致し、未コミットの変更が無い。`epic/` ブランチとロックされたものは残す。ローカルブランチも消す |
| 登録の外れた残骸ディレクトリ | `git worktree list` に無く、更新から24時間を超えた |
| `safe.directory` の登録 | 指している worktree のディレクトリがもう無い |
| web・frontend コンテナのプロセス | `docker exec` で始めたテスト・検査・e2e（`manage.py`・Playwright の Chromium・`mypy`・`vite` など）で、起動から3時間を超えた。子プロセスもまとめて止める |
| Windows 側の自動操作用の Chrome | 起動オプションに `--headless`・`--remote-debugging-port`（`-pipe`）・`--enable-automation` を持つか、Playwright・Puppeteer が起動したもので、起動から3時間を超えた。レンダラなどの子プロセスもまとめて止める |

compose が起動したサービス本体（`runserver 0.0.0.0:8000`・`npm run watch`）、Dev Container の VS Code Server、
普段使いの Chrome（上の起動オプションを持たない）、別プロジェクトのコンテナには触りません。

PowerShell から手で実行することもできます（引数なしなら対象を表示するだけです）。

```powershell
powershell -ExecutionPolicy Bypass -File scripts\cleanup.ps1          # 対象を表示するだけ
powershell -ExecutionPolicy Bypass -File scripts\cleanup.ps1 -Apply   # 実際に消す
powershell -ExecutionPolicy Bypass -File scripts\register_cleanup_task.ps1              # タスクを登録する（上書き）
powershell -ExecutionPolicy Bypass -File scripts\register_cleanup_task.ps1 -Unregister  # タスクを外す
```

### コンフリクトした PR の自動の解消

同じタスクの最後に
[scripts/resolve_conflicts.ps1](https://github.com/sumika157/baseball-league-manager/blob/main/scripts/resolve_conflicts.ps1)
が動き、base（main・epic）とコンフリクトした PR を探します（#267）。見つけたら、手元の Claude Code（`claude -p`）を**1本だけ**
切り離して起動し、[resolve-conflicts スキル](https://github.com/sumika157/baseball-league-manager/blob/main/.claude/skills/resolve-conflicts/SKILL.md)
の手順で直させます。PR を出したエージェントも、マージを待つ間にコンフリクトに気づけば同じスキルで自分で直すので、
これは取りこぼしの受け皿です。

- 直し方は、一時的な作業場所で最新の base を **merge で取り込み**、lint とフルテストを通してから、追加だけの push をします。
  rebase と force push はしないので、そのブランチを開いている別のセッションの作業は消えません（スカッシュマージなので main には1コミットで入ります）
- 判断が要るコンフリクト（同じ処理を両方が別の形に変えた・マイグレーションの番号がぶつかった など）は直さず、PR にコメントで状況を書いて止めます
- 動いている解消のエージェントがあれば新しく起動しません。90分を超えて終わらないものは止めます。
  一度試して止まった PR は、PR の先端か base が動くまで試し直しません
- 記録は `%LOCALAPPDATA%\baseball-conflicts\`（`conflicts.log`・1回ごとの Claude の出力の `runs\`）

```powershell
powershell -ExecutionPolicy Bypass -File scripts\resolve_conflicts.ps1          # 対象を表示するだけ
powershell -ExecutionPolicy Bypass -File scripts\resolve_conflicts.ps1 -Apply   # 1本だけ直させる
```

## GitHub の @claude への自動の対応

Issue・PR に `@claude` とメンションして書くと、手元の Claude Code がそれを拾って対応します
（質問への回答、Issue → worktree → PR の流れでの実装、既存の PR の修正）。結果はそのスレッドに返信されます。
GitHub Actions ではなく手元で動かすので、検査とテストは普段どおり手元の Docker 環境で流れます。
その代わり、**PC がログオンしていて Docker Desktop が動いている間だけ**対応します（止まっていた間の依頼は、次に動いたときに拾います）。

Windows のタスクスケジューラが1分ごとに
[scripts/claude_mentions.ps1](https://github.com/sumika157/baseball-league-manager/blob/main/scripts/claude_mentions.ps1)
を実行し、前回以降に書かれた次のものを探します。

- Issue・PR の会話のコメント、PR のレビューコメント（差分の行に付けたもの）、Issue・PR の本文
- レビューの総評（Approve などと一緒に書く本文）は拾いません。会話のコメントか行のコメントに書いてください

対応するのは、**リポジトリの持ち主（gh の認証ユーザー）が書いたものだけ**です。リポジトリが公開なので、
他人のメンションでは動きません。コードブロック・インラインコードの中の `@claude` も拾いません。

| リアクション | 意味 |
| --- | --- |
| 👀 | 受け付けた（対応中か、対応済み）。この印があるものは二度と拾わない |
| 🚀 | 対応が終わった（結果は返信を見る） |
| 😕 | 失敗した（終了コードが0でないか、120分で終わらなかった）。ログの場所を書いた返信が付く |

- 対応は1件ずつです。対応中は次の見回りが起動せず、終わってから溜まった依頼を古い順に拾います。
- やり直させたいとき（失敗した・途中で PC を落とした）は、その依頼の 👀 を外すと次の見回りで拾い直します。
- Claude は `--permission-mode auto` で動きます。危ない操作は自動で止まり、止まったことは返信か失敗として現れます。マージはしません。
- 前の依頼の会話は引き継ぎません。続きを頼むときは、同じスレッドで `@claude` を付けて書けば、スレッドを読み直して続けます。

状態とログは `%LOCALAPPDATA%\baseball-claude-mentions\` にあります（`mentions.log` が受け付けと結果、
`runs\` が1件ごとの Claude の出力。30日で消えます）。

### 初めて使うとき

1. スタンドアロン版の Claude Code を入れる（VSCode 拡張に同梱のものは、拡張を更新するとパスが変わるため）。
   入っていなければ、スクリプトは拡張に同梱の最新版を使います。

   ```powershell
   irm https://claude.ai/install.ps1 | iex   # %USERPROFILE%\.local\bin\claude.exe に入る
   ```

2. 作業ディレクトリを一度だけ信頼済みにする。ヘッドレスの実行では信頼の確認を出せず、
   未信頼のままだと `.claude/settings.json` の許可の設定が無視されます（`runs\*.err.log` に `this workspace has not been trusted` と出る）。
   PowerShell で `U:\home\sumika\work\develop\my_django_project` に移り、`claude` を対話で起動して信頼の確認に同意してから閉じます。
3. タスクを登録する。初回の見回りは過去のコメントを拾わず、時刻を記録するだけで終わります。

```powershell
powershell -ExecutionPolicy Bypass -File scripts\claude_mentions.ps1          # 対応する対象を表示するだけ
powershell -ExecutionPolicy Bypass -File scripts\claude_mentions.ps1 -Apply   # 対応させる
powershell -ExecutionPolicy Bypass -File scripts\register_claude_mentions_task.ps1              # タスクを登録する（上書き）
powershell -ExecutionPolicy Bypass -File scripts\register_claude_mentions_task.ps1 -Unregister  # タスクを外す（止める）
```

## イメージを作り直す

`requirements.txt` を変更したときは、イメージのビルドし直しが必要です。

```bash
docker compose build --no-cache

```

## 本番用のファイル

このページの `docker-compose.yml` と `Dockerfile` は**開発専用**です（`runserver`・Playwright 入り・ソースをマウント）。
一般公開用の `Dockerfile.prod`・`docker-compose.prod.yml`・`deploy/entrypoint.sh` は別に用意してあり、
開発では使いません。手順は [本番公開](本番公開) を参照してください。

リポジトリの `infra/` は、その本番の構成（AWS Lightsail・Cloudflare）を作る Terraform です。開発では使いません。`make tf ARGS="plan"` のように、Terraform もコンテナ（`hashicorp/terraform`）で動かします。手順は [本番公開](本番公開)。

## VS Code で開発する（Dev Container）

`.devcontainer/` を用意しているため、VS Code からコンテナ内に直接接続して開発できます。
**コンテナ内の Python を参照するので、補完や型チェックがそのまま効きます。**

1. 拡張機能 **Dev Containers** をインストールする
2. コマンドパレット（`F1`）から **「Dev Containers: Reopen in Container」** を選ぶ

初回は自動で Python / Pylance / Django の拡張機能が入ります。

> VS Code を閉じてもコンテナは動き続ける設定（`"shutdownAction": "none"`）です。
> 一緒に停止させたい場合は `.devcontainer/devcontainer.json` を `"stopCompose"` に変更してください。

## データベースについて

`db.sqlite3` は**イメージには含めず、ホスト側のファイルをマウントして使っています**。
そのため次のようになります。

- コンテナを作り直しても **データは消えません**
- ホスト側の `db.sqlite3` を直接バックアップできます
- Git 管理外です（`.gitignore` で除外）

バックアップを取る場合は、コンテナを停止してからファイルをコピーします。

```bash
docker compose down
cp db.sqlite3 db.sqlite3.bak
```

## トラブルシューティング

### `docker: command not found`（WSL 上で）

Docker Desktop の WSL 統合が無効です。[README](https://github.com/sumika157/baseball-league-manager#事前準備初回のみ) の「事前準備」の手順2を実施してください。

### `Cannot connect to the Docker daemon`

Docker Desktop が起動していません。タスクバーのアイコンが「Running」になるまで待ってから再実行します。

### ブラウザで「接続できません」と表示される

コンテナが起動しているか確認します。

```bash
docker compose ps
```

`Up` と表示されない場合はログを確認します。

```bash
docker compose logs web
```

### ポートが既に使われている（`port is already allocated`）

8000 番（またはプレビュー用の 8001〜8009 番）を別のプロセスが使っています。停止するか、`docker-compose.yml` の `ports` を
`"8010:8000"` のように変更してください（8001〜8009 番はプレビューが使うので避けます）。

### ソースを編集してもリロードされない

`docker compose ps` でコンテナが `Up` か確認してください。
それでも反映されない場合はコンテナを再起動します。

```bash
docker compose restart web
```
