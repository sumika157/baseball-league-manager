# 実装ロードマップ

このアプリを「野球の成績を管理・閲覧するツール」として仕上げるための計画。
フェーズ単位で実装し、都度確認してから次へ進む。

## 現在地

実装済みの土台。

- ドメイン駆動設計による4層構成（domain / application / infrastructure / presentation）
- リーグ・チーム・選手・**試合**の登録
- 試合を唯一の出典として、チームの勝敗・順位・選手の通算成績を集計
- 選手の**在籍（経歴）**。所属と背番号は在籍が持ち、移籍しても成績は残る
- 選手のプロフィール（生年月日・投打・出身・プロ入り前の経歴）と**球場**
  （所在地・収容人数・グラウンド・屋根）、チームの本拠地
- **主将**（チームに同時に1人、在籍していない選手は指名できない）と
  **外国人選手枠**（野球協約 第82条の2 に合わせ、リーグ単位で1軍登録の枠＝計4人・うち投手3人・野手3人を設定できる。
  保有は縛らない。実データは試合の出場者で検査する。FA 取得で枠の対象外（第82条 (4)）は #204 の段階B）
- **試合の記録**（イニングスコア・打順・守備位置・継投）。勝敗・セーブ・ホールドは
  日本プロ野球の規則で導出する
- ダッシュボード（全リーグの最新シーズンの順位表と主な部門の首位、最新の試合日の結果を
  1画面に並べる入口。上位3人と過去の年はタイトル一覧へ送る）、チーム一覧、
  選手一覧、順位表、リーグ画面（対戦成績つき）、リーグのタイトル一覧、
  リーグの成績一覧（全選手の通算成績を列ソートで見る）、試合一覧
  （リーグ・月のタブで切り替え）・試合詳細（ボックススコア）、
  選手個人ページ（月別成績つき）
- **一覧は参照クエリで作る**（集約を組み立てない）。件数が増えると差が出るため
- サイトの一覧は列を押して並べ替え。チームとリーグの表示順は管理画面で
  ドラッグして手動で決める（この2つの一覧に列の並べ替えは無い）
- 閲覧は誰でも、書き込みはログインした人だけ
- 認証（ログイン・新規登録・パスワード変更。メールを送らないので再設定は無い）、サイトと管理画面のテーマ、
  管理画面のダッシュボード
- **戦力分析**（球団×年度のデプス表・年齢構成・入退団・起用マップ・FA 取得・成績一覧。`/analysis/`）
- **ペナントモード**（実データから分岐した別の世界で、GM として編成してシーズンをシミュレーションで回す。1〜8リーグ・143試合・交流戦・ポストシーズン（CS と日本シリーズ）・オフの成長と引退とドラフト。`/pennant/`）
- **リッチな編集画面は React アイランド**（`frontend/`。参照系は Django テンプレートの
  まま、編集画面だけ React をマウントする）。第一弾は試合の記録の編集画面

## フェーズ1: 試合を見えるようにする ✅ 完了

**なぜ:** 試合をすべての出典にしたにもかかわらず、サイト側に試合を見る画面が無い。
管理画面からしか確認できず、中核データが閲覧不能な状態になっている。

| 画面 | 内容 |
| --- | --- |
| 試合一覧 `/games/` | リーグ・月のタブで切り替え、年・チームで絞り込み、日付順 |
| 試合詳細 `/games/<id>/` | スコアと、その試合の出場選手の成績 |
| 選手個人ページ `/team/<id>/player/<id>/` | 通算成績と、試合ごとの成績の推移 |

導線として、選手一覧から個人ページへ、個人ページから編集へ、という流れに整える。

## フェーズ2: リーグの確立 ✅ 完了（Season は保留）

**なぜ:** `League` は実質「名札」で、ユースケースを持たなかった。順位表も全チーム横断で、
別のリーグどうしのチームが同じ表に並んでいた。

- ✅ **リーグ別の順位表**。順位はリーグの中で争われるので、リーグごとに分けて算出する
- ✅ リーグ画面 `/league/<id>/`（所属チーム・順位表・直近の試合）
- ✅ `League` のユースケース（`get_league_detail`）と `LeagueNotFound`
- ✅ **外国人枠を野球協約に合わせた**（#204 段階A）。登録枠（保有の上限）と出場枠（1試合の上限）をやめ、
  1軍登録の枠（計4・投手3・野手3。`ForeignPlayerRules`）1つにした。実データのスコアブック・ペナントの1軍と試合・仮想データの投入が同じ規則を使う
- 段階B（第82条 (4)。国内 FA を取得した外国人を翌年から枠の対象外にする）は #108 の後

### 保留: `Season` のエンティティ化

当初は開幕日・終了日・参加チームを持つエンティティにする案だったが、着手前に
見直したところ費用に対する効果が薄いと判断し、いったん保留とした。

- 「参加チーム」は `Team` の所属リーグから導けるため、別に持つと出典が二重になる
- 開幕日・終了日は試合日の妥当性検査にしか使わない
- シーズンの一覧は試合から導けている（`seasons_of`）

必要になる場面（シーズン開始前に日程を組む、期の途中でチームが入れ替わる、
シーズンに名前を付ける）が出てきた時点で入れる。

**なぜ:** 試合の登録が管理画面だけで、運用が重かった。

- ✅ サイトからの試合登録 `/games/new/` → `/games/<id>/edit/`

下書き保存は見送った。試合は作成した時点で保存されており、成績は後から
何度でも直せるため、別の下書き状態を設ける必要が無い。

## フェーズ4: 分析の深化 ✅ 完了

**なぜ:** 成績管理アプリとしての価値はここにある。

- ✅ **規定打席・規定投球回**。日本プロ野球の規則にならい、打者は 試合数 × 3.1 打席、
  投手は 試合数 × 1.0 投球回。これを入れる前は1打数1安打の選手が打率10割で
  首位に立っていた。本塁打と奪三振は本数そのものが記録なので規定を設けない
- ✅ **チーム成績**（チーム打率・チーム防御率）。率は選手ごとの率を平均せず、
  合算した実数から計算し直す
- ✅ **対戦成績**（チーム間の相性）。リーグ画面に、順位表と同じ並びの表で表示
- ✅ **期間別成績**（選手の月別成績）。通算値では見えない調子の波を選手個人ページに出す
- ✅ **指標の拡充**。FIP（守備に左右されない投球内容）・IsoP（長打力）・BB/9（与四球率）
- ✅ **対リーグ相対指標**（OPS+・ERA+）。リーグ平均を100とした指数で、
  リーグの得点環境が違っても選手を比べられる
- ✅ **チームの月別成績**。個人の月別成績と対になる、チーム単位の月別の勝敗・打率・防御率
- ✅ **リーグのタイトル一覧ページ**。打率・本塁打・打点・防御率・勝利・セーブ・奪三振の
  部門別首位者を、リーグ・シーズンで絞って見られる専用ページ（ダッシュボードの
  ランキングは全体の概況、ここは部門を掘り下げて確認する場所と役割を分ける）
- ✅ **ダッシュボードの部門を NPB の個人成績ページに合わせた**。打者は打率・本塁打・打点、
  投手は防御率・勝利・セーブの各上位5人。リーグのタブを1本にまとめ（内容ごとに
  タブバーを分けると左右で別リーグが表示される状態が生まれるため）、右カードは
  順位表（最新シーズン）を初期表示にしてチーム一覧とタブで切り替える
- ✅ **リーグの成績一覧ページ**（`/league/<id>/stats/`）。所属する全選手の通算成績を
  1つの表に並べ、列で並べ替える。ダッシュボードの各ランキングカードの
  「成績一覧を見る」から、その部門で並べた状態で遷移する
- ✅ **ダッシュボードとタイトル一覧の役割を分けた**（#179）。ダッシュボードの通算ランキングが
  タイトル一覧（シーズン）と同じ部門名で別の数字を出し、リーグのタブはリーグ画面の上半分と
  同じだった。ダッシュボードは全リーグを1画面に並べる入口にして、部門は最新シーズンの首位だけを
  タイトル一覧と同じ集計から出す。上部の登録数（リーグ・チーム・選手）はやめた（管理画面の概況にある）

## フェーズ4.5: 試合の記録を本格化する ✅ 完了

**なぜ:** 試合が唯一の出典なのに、記録が「誰が何本打ったか」だけだった。
打順も守備位置も継投も持たないため、スコアブックとして読めなかった。

- ✅ **イニングスコア**（回ごとの得点、延長も可）。`LineScore` 値オブジェクト
- ✅ **打順・交代の順・守備位置**。スタメンと途中出場を区別できる。「スタメンか」は
  旗を持たず打順の先頭かで判断する（旗を持つと食い違いが起こりうる）
- ✅ **試合で就いた守備位置**（`投捕一二三遊左中右指` ＋ 代打・代走）。選手の登録位置
  （5区分）とは別概念として持つ
- ✅ **継投**（登板順と登板した回）
- ✅ **勝敗・セーブ・ホールド・HP を日本プロ野球の規則で導出**。手入力させない。
  判定はドメインサービスにあり、手動入力と仮想データの投入で同じ関数を使う
- ✅ 試合詳細をスポーツナビのボックススコアと同じ構成に
- ✅ 仮想の試合データを投入するコマンド（`seed_virtual_games`）。確率分布から
  成績を引き、NPBの水準に合わせてある

## フェーズ4.6: チームの戦力分析 ✅ 完了

**なぜ:** チームページ（`/team/<id>/`）には在籍中の選手の通算成績しか並ばず、先発の左腕が何人いるか・遊撃を主に守っているのは誰か・
年齢が上に偏っていないか、といった編成の形が見えない。球団×年度で一目で読める「戦力分析」ページを作る
（[NPB Analytics Lab](https://npb-analytics-labo.vercel.app/tigers/2025) の球団ページを参考にする）。
集計結果は保存せず、表示のたびに試合・在籍・生年月日から導く。保存するのは試合から導けない入力の事実だけ（契約の区分・加入の経路）。
設計は親 Issue #114。

- ✅ **A: デプス表と年齢構成**（#121）。投手は先発・救援・登板なし×左右、野手は守備位置のグループ×左右。年齢は4月1日時点。参照だけでスキーマ変更なし
- ✅ **B: 起用マップ**（#122）。守備位置ごとの先発出場数をダイヤモンドの形に並べるタブ（`?tab=usage`）。「投」は投球明細の先発数から。参照だけでスキーマ変更なし
- ✅ **C: 入退団**（#123）。その年の加入（新入団・移籍・再入団）と退団（移籍・退団）を在籍から導いて、デプス表タブに出す。引退・自由契約は区別できない。参照だけでスキーマ変更なし
- ✅ **D: 年度で絞った成績一覧**（#124）。その年に在籍した選手のその年の成績を、選手一覧と同じ表で見せるタブ（`?tab=stats`）。年と在籍の期間で区切った集計（#95）の上に作った。参照だけでスキーマ変更なし
- ✅ **E: 支配下／育成の区別**（#125）。在籍に契約区分・昇格・背番号の規則・リーグごとの支配下の上限を持たせ（E1 #126）、デプス表に総数・支配下・育成を出して育成選手の出場を拒否する（E2 #127）。上限は集約が必須の引数で守る（#145）
- ✅ **F: FA 取得**（#125 の続き）。加入の経路と FA 宣言を記録し、宣言の結果は在籍から導く（F1 #128）。登録日数を試合から推定する FA 取得タブ（F2 #129）
- ✅ **G: ペナントの世界の中に置く**（#130）。戦力分析を `/pennant/<世界>/team/<id>/analysis/` にも置いた。組み立てを世界の範囲にし（`build_world_team_analysis_service`）、FA タブの「記録のある最初の年」と試合の無い球団の既定の年は世界ごとになる。`fork_roster` などの宿題は #26 に記載
- ✅ **入団年をドラフト年と順位に置き換えた**（#108）。プロフィールは `DraftPick`（年・順位・育成）を持ち、FA の短縮規則をドラフト年そのもので判定する。ドラフトの無い外国人選手は記録の最初の年から数え（海外リーグの年数は数えない）、国内FAは8シーズン。ペナントの新人の順位は指名の順の仮置き（ドラフト会議 #198 で置き換える）

## フェーズ6: リッチな編集画面（React アイランド） ✅ 完了

**なぜ:** 試合の記録は入力の構造が深く（イニングスコア × 打撃 × 投球 × 継投）、
テンプレート＋formset では「全部入力して保存を押すまでエラーが分からない」
「導出できる値も手で入れる」という入力体験の限界があった。全面 SPA 化はせず、
編集画面だけを React にする（参照系は Django テンプレートのまま。検証と
業務ルールの出典はドメイン層から動かさない）。

- ✅ ビルド基盤（Vite + React + TypeScript。`vite build --watch` の常時出力方式で、
  web イメージに Node を持ち込まない。Python 側の依存追加も無し）
- ✅ 試合の記録の編集画面を React 化。得点はイニングスコアから自動導出（手入力させない）、
  被本塁打＞被安打はその場で警告、保存は JSON API（検証は既存フォームを行単位で再利用）

次に React 化する画面は、運用して入力が苦しい画面が見えた時点で決める
（`frontend/src/` にエントリを追加する方式で画面単位に増やせる）。

## フェーズ7: 件数に耐える一覧 ✅ 完了

**なぜ:** 1シーズンぶんの試合を投入したところ、試合一覧が 3,480件で 3.57秒かかり
実用にならなくなった。原因は一覧が参照なのに集約（`Game`）を組み立てていたこと。
日付・チーム・スコアしか使わないのに、1試合ごとに打撃・投球・イニングスコアの
明細（合わせて9万行超）まで読んでいた。

- ✅ **試合一覧を参照クエリに移した**（`DjangoGameListQuery`）。3.57秒 → 0.02秒。
  「一覧を作るときに集約を組み立てない」という既存の規則を、実際に効く形で適用した
- ✅ 勝敗の判定は `winning_team_id()` としてドメインに切り出し、集約と参照クエリの
  両方がそこを通る（参照側で書き直すと同じ事実の出典が2つになるため）
- ✅ **リーグと月をタブで切り替える**。開いた直後は最新シーズンの最後に試合が
  あった月だけを見せる。チームの選択肢は選んでいるリーグに連動する
- ✅ タブを移った先に試合が無い月・他リーグのチームが選ばれたままになる場合は、
  エラーにせず既定へ落とす

他の一覧（選手一覧・成績一覧）は現状の件数では問題ないが、同じ兆候（集約を
組み立てている参照）が出たら同じ手当てをする。

## フェーズ8: 打席を出典にする ✅ 完了（一部保留）

**なぜ:** 試合の記録が「完成したボックススコアの転記」で、打数・安打・打点といった
スコアラーが数える値を人に数えさせていた。検算も無く、打点の合計とイニングスコアが

- ✅ **打席の記録**（結果・走者の進塁・失策・代走）。1試合の成績・イニングスコア・
  勝敗はすべてここから導き、集約が検算する
- ✅ **スコアブック形式の入力画面**（React）。結果を選ぶと走者の進塁が既定値で埋まる
- ✅ 成績項目の拡充（得点・盗塁・盗塁刺・犠打・故意四球・三振・併殺打・失点）と、
  選手個人ページ・ボックススコアへの表示
- ✅ **守備成績**（刺殺・補殺・失策・併殺参加）。途中出場の選手に出場した打席を記録し、
  正しい選手に付ける
- ✅ スコアボードの安打・失策と、スコアブックの読み取り専用表示
- ✅ 仮想データを打席から作り直した
- ✅ **試合の開始・終了の時刻と観客数**（#44）。段階1: 手入力・表示・収容人数を超えたときの警告。段階2: ペナントのシミュレーションと仮想データの投入が、時刻（平日18:00・土日14:00開始、打席数と継投から導く試合時間）と観客数（収容人数×入場率）を作る。試合時間は保存せず導出、中断は手入力だけ

### 保留

設計時に挙げたが、成績の正しさには効かないか、規則の限界の折り合いとして後回しにしたもの。

## フェーズ8.5: ペナントモード ✅ 完了（拡張は保留の表）

**なぜ:** 今のアプリは試合を記録して読む道具で、成績を生む仕組みは開発用の投入コマンドの中に閉じている。
フェーズ8 で打席・勝敗の導出・順位とタイトルの集計が揃ったので、能力 → 打席 → 既存の導出という経路を本番の機能にし、
GM として編成してシーズンを見守るゲーム（プロスピのペナントモードに相当）にする。
段階単体では動かないので、統合ブランチ `epic/pennant-mode` に段階を積み、最後に1本で main に入れる。
仕様は Wiki の「ペナントモード」、仕組みと決めたこと・実測値は「ペナントモードの仕組み」（原稿は `docs/wiki/`）、親 Issue は #26。

決めたこと:

- 遊び方の重心は GM（編成して見守る）。1試合ごとの采配はしない
- 実データとは別の「世界」として分ける。世界は実データのリーグを1〜8選んで分岐し、分岐した後は同期しない
- 日程はリーグ内の総当たり＋交流戦で1球団143試合。全試合 DH。ポストシーズンは初期範囲では入れず（順位表とタイトルで1年の区切りは付くため）、オフまで遊べるようになってから世界ごとに方式を選べる形で足した（#39）
- 成績・順位は保存せず、実データと同じく試合から集計する。能力は入力、成績は出力（初期能力だけ実データの成績から推定する）

段階（✅ は統合ブランチに入ったもの。main に入るのは全段階を終えてから）:

- ✅ 試合の組み立てを1か所にまとめる（P0。これだけは単体で main に入れた）
- ✅ シミュレーションエンジン（能力・1打席の確率・進塁・AI 監督）。NPB の水準に合わせた（P1。推定した能力での調整し直しは #63）
- ✅ 世界の分離と分岐、実成績からの初期能力の推定（P2）
- ✅ 日程の生成と保存、シーズンの進行（P3）
- ✅ ペナントの画面（世界の作成・GM ホーム・世界の中の参照画面・能力の表示。P4）
- ✅ 球団の編成を GM が上書きする（1軍登録・オーダー・投手陣。自動と手動は切り替えで、同じ画面に並べない。P5）
- ✅ オフの規則（成長・衰え・引退・自動ドラフト。P6a）
- ✅ シーズンを締めて翌年へ進める（#54。P6b・P6c）。1世界10シーズンまで

2026-10-05 の設計精査で足したもの。次の4つは epic を main に入れる前にやる（2シーズン目以降で画面とタイトルが崩れる・入力で 500 になるなど、P6 で表に出るため）:

- ✅ 成績を年と在籍の期間で区切る（#95）。2シーズン目から通算が出る・引退した選手が過去のタイトルから消える・タイトルが交流戦を数えない、の3つを直す。オフの画面より先に入れる
- ✅ 編成画面に能力・年齢・今季の成績を出す（#102）
- ✅ 開幕年を範囲で絞る（#103）
- ✅ 設計書と文言を実装に合わせる（#101）

初期範囲の中で入れる:

- ✅ 手動の編成にも AI と同じ検査を当てる（#99）。1人のローテーションで回しても成績が落ちない抜け道を、疲労を成績に効かせるのではなく人数の下限で塞ぐことにした（下限の内側の酷使の代償は、後から #97 で疲労として足した）
- ✅ 進める単位に「月末まで」「上限まで」を足し、優勝・マジック・終了の印を出す（#104）
- ✅ 世界の作成時に名簿を検査し、重い処理が書き込みを止める時間を縮める（#100）。フェーズ9 で利用者が自分のリーグから世界を作る前に要る
- ✅ ドラフトの指名数で開幕前の支配下を 62〜66人の帯に入れ、新人の入団経路を記録する（#167）。実データから分岐した球団（約34人）は1年に10人までで追いつく（一度に埋めると年齢の分布と水準が崩れるため）
- ✅ 設計書を Wiki（「ペナントモード」「ペナントモードの仕組み」）に吸収して削除する（#178）
- ✅ 歴代の記録と球団史（#105）。終わったシーズンの優勝とタイトルの受賞者、球団の年ごとの成績。優勝の決め方（`league_champion`）を世界の終了と共有し、何も保存しない

ペナントが main に入った後に足すもの:

- ✅ 戦力外の段階A（#168）: AI が新人を迎える空きまで戦力外にし、外国人は新しく迎える外国人の見込みと比べて入れ替え（主力でも、全員でも）、在籍に退団の経路を記録し、オフの結果に「戦力外」を出す。引退の表は自分の意思の引退だけに下げ、引退＋戦力外で入れ替わり約10%に合わせ直した
- ✅ 締める処理を速くする（#176）: 集約の保存（`Team.save()`）を、今の行と比べて変わった行だけ書く形にした。8リーグの9シーズン目で全体 11.8 → 3.2秒・書き込みロック 9.2 → 0.7秒。在籍中の選手だけを読む案は、外側が条件の3秒に届かず見送り
- ✅ 戦力外の段階B（#168）: 自軍の戦力外を編成画面の「戦力外」タブで選ぶ（シーズン終了の局面だけ。締める操作は1つのボタンのまま）。ベテランの能力で測れない価値（世界の通算の実績・在籍年数・生え抜き・主将）を残す価値に加点して外されにくくした（保存しない。タイトルは導き直しが重いので入れず、外国人の入れ替えの比較には足さない）
- ✅ 表彰（#248）: シーズンを締めるときにその年のタイトル受賞者を「表彰」として保存し（CLAUDE.md の「集計を保存しない」の例外。範囲は締めたシーズンのタイトル受賞者だけ）、選手ページに「獲得タイトル」を出し、戦力外の実績の加点にタイトルの数を足した（外国人の入れ替えの比較にもタイトルの分だけ足す）。歴代の記録・球団史は締めた年を表彰から読む（#203 の時間の大半だった年ごとのタイトルの集計が、締めていない1年ぶんだけになった）
- ✅ 投手の疲労の段階1（#97）: 休養の足りない先発（中4日以下）と、目安を超えた続投を、能力の目減りとして率に効かせる。AI の普段の起用では疲労0で、リーグの水準は動かない（#99 の下限の内側の酷使に代償を付けた）
- ✅ 投手の疲労の段階2（#97）: 救援の連投（3連投目）と直近5日の登板数を、スタミナの係数つきで効かせる。連投の上限をスタミナで変え（55以上は3連投まで）、AI は疲労の重い救援を後回しにする。直近の登板を読む日数を3日 → 5日に
- ✅ 投手の疲労の段階3（#97）: 編成の投手陣タブに次の試合日の疲労の区分（なし・軽い・重い）を出す。ローテーションは先発したら、救援は救援で投げたらの区分で、エンジンと同じ式から引く
- ✅ ポストシーズン（#39。統合ブランチ `epic/postseason`）: 公式戦の後に CS と日本シリーズを行う。方式は世界ごとに「NPB 方式」（新しい世界の既定）・「優勝球団で日本シリーズ」・「なし」（既存の世界）から選び、開始前なら後から変えられる。
  3リーグ以上の日本シリーズは勝率で種を付けたトーナメント（2026-10-12 決定）。保存するのは試合の区分・世界の方式・締めた年の日本一だけで、勝ち上がりは順位と試合から毎回導く。
  **ポストシーズンの試合は公式戦の成績・順位・タイトル・通算に数えない**（区分を範囲と同じく必須の引数にした）。個人成績は表を出すが保存しない。
  段階は、試合の区分と集計の分離（S1）→ 勝ち上がりの規則（S2）→ 進行と締める処理（S3）→ 画面から進めて締める（S4a）→ 方式の設定と個人成績（S4b）→ 歴代・球団史と Wiki への吸収（S5）

## フェーズ9: 一般公開とワークスペース（未着手）

**なぜ:** 一般公開して、来た人それぞれが自分のチーム・選手・試合で遊べるようにする。
今はデータの置き場所が1つしかなく、新規登録した人は何も書けない。書けるようにすれば、全員が同じリーグを書き換えることになる。
全データの上に「ワークスペース」という区切りを足し、持ち主がその中で全権を持つ形にする。
設計は `docs/design/workspaces.md`、親 Issue は #74。

- ✅ 本番構成（W0、#76）。公開先は AWS Lightsail の VM 1台＋docker compose、入口は Cloudflare Tunnel、DB は当面 SQLite。フェーズ5 の本番構成とバックアップはここで片付けた
- ✅ CI（#88）。テストを GitHub Actions で流し、本番イメージを GHCR に置く
- ✅ 本番の構成を Terraform で作る（#89）。`infra/`。手で作る手順は付録に移した（実機では未確認。`validate` までで、`plan`・`apply` は未実施）
- ⬜ データをワークスペースに属させ、範囲で絞る（W1）
- ⬜ ワークスペースを URL（`/w/<key>/`）で開き、ワークスペースの権限で判定する。公開/非公開を切り替えられる（W2）
- ⬜ リーグ・チーム・球場をサイトの画面で登録する（W3）。一般の利用者には管理画面を渡せないため
- ⬜ ワークスペースの作成・削除・上限（1人3つ）・招待リンクによる共同編集（W4）
- ⬜ 新しいワークスペースに小さい見本を生成する（W5）
- ⬜ ペナントをワークスペースの中へ移す（W6）

W0 以外は、ペナントモード（フェーズ8.5、#26）を最後の段階まで終えて main に入れてから着手する
（データを範囲で絞る仕組みを2回、別々のブランチで書くことになるのを避けるため）。
