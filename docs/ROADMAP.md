# 実装ロードマップ

このアプリを「野球の成績を管理・閲覧するツール」として仕上げるための計画。
フェーズ単位で実装し、都度確認してから次へ進む。

## 現在地

実装済みの土台。

- ドメイン駆動設計による4層構成（domain / application / infrastructure / presentation）
- リーグ・チーム・選手・**試合**の登録
- 試合を唯一の出典として、チームの勝敗・順位・選手の通算成績を集計
- 選手の**在籍（経歴）**。所属と背番号は在籍が持ち、移籍しても成績は残る
- 選手のプロフィール（生年月日・投打・出身・プロ入り前の経歴）と**球場**
  （所在地・収容人数・グラウンド・屋根）、チームの本拠地
- **主将**（チームに同時に1人、在籍していない選手は指名できない）と
  **外国人選手枠**（リーグ単位で登録人数・試合出場人数の上限を設定できる）
- **試合の記録**（イニングスコア・打順・守備位置・継投）。勝敗・セーブ・ホールドは
  日本プロ野球の規則で導出する
- ダッシュボード（概況とランキング。部門は NPB の個人成績ページにならい、
  リーグごとのタブ1本でランキング・順位表・チームを切り替える）、チーム一覧、
  選手一覧、順位表、リーグ画面（対戦成績つき）、リーグのタイトル一覧、
  リーグの成績一覧（全選手の通算成績を列ソートで見る）、試合一覧
  （リーグ・月のタブで切り替え）・試合詳細（ボックススコア）、
  選手個人ページ（月別成績つき）
- **一覧は参照クエリで作る**（集約を組み立てない）。件数が増えると差が出るため
- サイトの一覧は列を押して並べ替え。チームとリーグの表示順は管理画面で
  ドラッグして手動で決める（この2つの一覧に列の並べ替えは無い）
- 閲覧は誰でも、書き込みはログインした人だけ
- 認証（ログイン・新規登録・パスワード再設定）、サイトと管理画面のテーマ、
  管理画面のダッシュボード
- **リッチな編集画面は React アイランド**（`frontend/`。参照系は Django テンプレートの
  まま、編集画面だけ React をマウントする）。第一弾は試合の記録の編集画面

## フェーズ1: 試合を見えるようにする ✅ 完了

**なぜ:** 試合をすべての出典にしたにもかかわらず、サイト側に試合を見る画面が無い。
管理画面からしか確認できず、中核データが閲覧不能な状態になっている。

| 画面 | 内容 |
| --- | --- |
| 試合一覧 `/games/` | リーグ・月のタブで切り替え、年・チームで絞り込み、日付順 |
| 試合詳細 `/games/<id>/` | スコアと、その試合の出場選手の成績 |
| 選手個人ページ `/team/<id>/player/<id>/` | 通算成績と、試合ごとの成績の推移 |

導線として、選手一覧から個人ページへ、個人ページから編集へ、という流れに整える。

## フェーズ2: リーグの確立 ✅ 完了（Season は保留）

**なぜ:** `League` は実質「名札」で、ユースケースを持たなかった。順位表も全チーム横断で、
別のリーグどうしのチームが同じ表に並んでいた。

- ✅ **リーグ別の順位表**。順位はリーグの中で争われるので、リーグごとに分けて算出する
- ✅ リーグ画面 `/league/<id>/`（所属チーム・順位表・直近の試合）
- ✅ `League` のユースケース（`get_league_detail`）と `LeagueNotFound`

### 保留: `Season` のエンティティ化

当初は開幕日・終了日・参加チームを持つエンティティにする案だったが、着手前に
見直したところ費用に対する効果が薄いと判断し、いったん保留とした。

- 「参加チーム」は `Team` の所属リーグから導けるため、別に持つと出典が二重になる
- 開幕日・終了日は試合日の妥当性検査にしか使わない
- シーズンの一覧は試合から導けている（`seasons_of`）

必要になる場面（シーズン開始前に日程を組む、期の途中でチームが入れ替わる、
シーズンに名前を付ける）が出てきた時点で入れる。

## フェーズ3: 入力の効率化 ✅ 完了

**なぜ:** 試合の登録が管理画面だけで、運用が重かった。

- ✅ サイトからの試合登録 `/games/new/` → `/games/<id>/edit/`
- ✅ 両チームのロスターを並べた一括入力。野手は打撃欄、投手は投球欄に自動で振り分ける
- ✅ 空欄の行は記録しない。すべて0の行を残すと「出場して無安打」と
  「出場していない」が区別できなくなるため
- ✅ 一度入力した選手を空欄に戻すと記録を取り消す（集約に無い行は削除する）
- 書き込みはログインを必須にした

下書き保存は見送った。試合は作成した時点で保存されており、成績は後から
何度でも直せるため、別の下書き状態を設ける必要が無い。

## フェーズ4: 分析の深化 ✅ 完了

**なぜ:** 成績管理アプリとしての価値はここにある。

- ✅ **規定打席・規定投球回**。日本プロ野球の規則にならい、打者は 試合数 × 3.1 打席、
  投手は 試合数 × 1.0 投球回。これを入れる前は1打数1安打の選手が打率10割で
  首位に立っていた。本塁打と奪三振は本数そのものが記録なので規定を設けない
- ✅ **チーム成績**（チーム打率・チーム防御率）。率は選手ごとの率を平均せず、
  合算した実数から計算し直す
- ✅ **対戦成績**（チーム間の相性）。リーグ画面に、順位表と同じ並びの表で表示
- ✅ **期間別成績**（選手の月別成績）。通算値では見えない調子の波を選手個人ページに出す
- ✅ **指標の拡充**。FIP（守備に左右されない投球内容）・IsoP（長打力）・BB/9（与四球率）
- ✅ **対リーグ相対指標**（OPS+・ERA+）。リーグ平均を100とした指数で、
  リーグの得点環境が違っても選手を比べられる
- ✅ **チームの月別成績**。個人の月別成績と対になる、チーム単位の月別の勝敗・打率・防御率
- ✅ **リーグのタイトル一覧ページ**。打率・本塁打・打点・防御率・勝利・セーブ・奪三振の
  部門別首位者を、リーグ・シーズンで絞って見られる専用ページ（ダッシュボードの
  ランキングは全体の概況、ここは部門を掘り下げて確認する場所と役割を分ける）
- ✅ **ダッシュボードの部門を NPB の個人成績ページに合わせた**。打者は打率・本塁打・打点、
  投手は防御率・勝利・セーブの各上位5人。リーグのタブを1本にまとめ（内容ごとに
  タブバーを分けると左右で別リーグが表示される状態が生まれるため）、右カードは
  順位表（最新シーズン）を初期表示にしてチーム一覧とタブで切り替える
- ✅ **リーグの成績一覧ページ**（`/league/<id>/stats/`）。所属する全選手の通算成績を
  1つの表に並べ、列で並べ替える。ダッシュボードの各ランキングカードの
  「成績一覧を見る」から、その部門で並べた状態で遷移する

## フェーズ4.5: 試合の記録を本格化する ✅ 完了

**なぜ:** 試合が唯一の出典なのに、記録が「誰が何本打ったか」だけだった。
打順も守備位置も継投も持たないため、スコアブックとして読めなかった。

- ✅ **イニングスコア**（回ごとの得点、延長も可）。`LineScore` 値オブジェクト
- ✅ **打順・交代の順・守備位置**。スタメンと途中出場を区別できる。「スタメンか」は
  旗を持たず打順の先頭かで判断する（旗を持つと食い違いが起こりうる）
- ✅ **試合で就いた守備位置**（`投捕一二三遊左中右指` ＋ 代打・代走）。選手の登録位置
  （5区分）とは別概念として持つ
- ✅ **継投**（登板順と登板した回）
- ✅ **勝敗・セーブ・ホールド・HP を日本プロ野球の規則で導出**。手入力させない。
  判定はドメインサービスにあり、手動入力と仮想データの投入で同じ関数を使う
- ✅ 試合詳細をスポーツナビのボックススコアと同じ構成に
- ✅ 仮想の試合データを投入するコマンド（`seed_virtual_games`）。確率分布から
  成績を引き、NPBの水準に合わせてある

## フェーズ5: 運用の整備（進行中）

**なぜ:** 実運用に耐える形にする。他フェーズと独立していて、いつでも着手できる。

- ✅ **権限管理（チーム担当者制）**。現状はログインすれば誰でも全チームの選手・試合を
  編集できる。チームに「担当者」を割り当て、担当者は自チームが関わる範囲だけ
  編集できるようにする。管理者（Django の管理ユーザー）は変わらず全権を持つ
- ⬜ 本番構成（PostgreSQL、gunicorn、静的ファイル配信）
- ⬜ CI（GitHub Actions でテスト実行）
- ⬜ バックアップ手順

本番構成・CI・バックアップは、実際に本番公開する段になってから着手する。
現状は Docker + SQLite でのローカル運用が前提で、公開先が決まっていないため。

## フェーズ6: リッチな編集画面（React アイランド） ✅ 完了

**なぜ:** 試合の記録は入力の構造が深く（イニングスコア × 打撃 × 投球 × 継投）、
テンプレート＋formset では「全部入力して保存を押すまでエラーが分からない」
「導出できる値も手で入れる」という入力体験の限界があった。全面 SPA 化はせず、
編集画面だけを React にする（参照系は Django テンプレートのまま。検証と
業務ルールの出典はドメイン層から動かさない）。

- ✅ ビルド基盤（Vite + React + TypeScript。`vite build --watch` の常時出力方式で、
  web イメージに Node を持ち込まない。Python 側の依存追加も無し）
- ✅ 試合の記録の編集画面を React 化。得点はイニングスコアから自動導出（手入力させない）、
  被本塁打＞被安打はその場で警告、保存は JSON API（検証は既存フォームを行単位で再利用）

次に React 化する画面は、運用して入力が苦しい画面が見えた時点で決める
（`frontend/src/` にエントリを追加する方式で画面単位に増やせる）。

## フェーズ7: 件数に耐える一覧 ✅ 完了

**なぜ:** 1シーズンぶんの試合を投入したところ、試合一覧が 3,480件で 3.57秒かかり
実用にならなくなった。原因は一覧が参照なのに集約（`Game`）を組み立てていたこと。
日付・チーム・スコアしか使わないのに、1試合ごとに打撃・投球・イニングスコアの
明細（合わせて9万行超）まで読んでいた。

- ✅ **試合一覧を参照クエリに移した**（`DjangoGameListQuery`）。3.57秒 → 0.02秒。
  「一覧を作るときに集約を組み立てない」という既存の規則を、実際に効く形で適用した
- ✅ 勝敗の判定は `winning_team_id()` としてドメインに切り出し、集約と参照クエリの
  両方がそこを通る（参照側で書き直すと同じ事実の出典が2つになるため）
- ✅ **リーグと月をタブで切り替える**。開いた直後は最新シーズンの最後に試合が
  あった月だけを見せる。チームの選択肢は選んでいるリーグに連動する
- ✅ タブを移った先に試合が無い月・他リーグのチームが選ばれたままになる場合は、
  エラーにせず既定へ落とす

他の一覧（選手一覧・成績一覧）は現状の件数では問題ないが、同じ兆候（集約を
組み立てている参照）が出たら同じ手当てをする。
